Part I — The project in plain English

1. One-sentence explanation

Booklet saves articles, books, and documents you want to read, strips away everything that is not the text, and then gives you the tools to actually read them — offline, read aloud, searchable by meaning, highlighted, and resurfaced later — while working completely without an account if you want it to.

2. A nontechnical analogy

Imagine you clip interesting articles out of newspapers and magazines. Over time you accumulate a box of clippings. The box has three problems:

  1. The clippings are cluttered with advertisements, navigation, and cookie banners printed around the text.
  2. You cannot find anything unless you remember the exact headline.
  3. You never re-read any of them, so the box is a graveyard rather than a library.

Booklet is like an assistant who:

  1. Takes each clipping and retypes just the article onto clean paper.
  2. Files it with the author, the source, and how long it takes to read.
  3. Will read it aloud to you if your eyes are busy.
  4. Lets you underline passages and write notes in the margin.
  5. Can find a clipping when you describe what it was about, not just what it was called.
  6. Hands you an old clipping now and then, and asks whether you still remember what it said.
  7. Keeps the whole box in your house, so it works with the power out.
  8. Will keep a copy at the library too — but only if you ask.

In the real project:

  • A "clipping" is an article.
  • "Retyping onto clean paper" is extraction.
  • "Reading aloud" is text-to-speech, generated by a neural model.
  • "Finding by what it was about" is semantic search over embeddings.
  • "Asking whether you remember" is resurfacing with recall prompts.
  • "Keeping it in your house" is IndexedDB in your browser.
  • "A copy at the library" is the optional synced account.

3. The problem Booklet addresses

Saving something to read later is nearly frictionless. Reading it is not. The result is a backlog that grows faster than it drains, which produces several distinct problems that most "read it later" tools address only partially:

  • The page is not the article. A modern web page wraps a few thousand words of prose in navigation, related-content rails, newsletter interstitials, consent dialogs, and analytics. Reading it later means re-encountering all of that.
  • The article may not survive. Sites reorganize, paywalls descend, domains lapse. A bookmark is a pointer to something you do not control.
  • Search by title fails. Six months later you remember that you read something about how constraints make people inventive. You do not remember the title, the author, or the site. Keyword search over titles cannot help you.
  • Reading requires eyes and stillness. A long queue and a commute are a bad match unless the text can be listened to.
  • Highlights go nowhere. Underlining a passage feels productive and then the passage is never seen again.
  • Accounts are a tax. Requiring a login to read your own saved text makes the tool dependent on a server that may go away, and on a company you have to trust.

Booklet's position is that these are one problem, not six, and that solving them separately produces a worse tool than solving them together.

4. What Booklet does

Booklet can:

  • Save an article from a URL, a browser extension, an uploaded file, or an RSS feed.
  • Extract readable text and clean HTML from web pages using Mozilla's Readability algorithm.
  • Extract text from PDF and EPUB files, including OCR for scanned pages.
  • Inline images as data URIs at save time, so a saved article survives the original going offline.
  • Store everything in the browser's IndexedDB so the library works with no account and no network.
  • Optionally synchronize to a Postgres-backed server when you sign in.
  • Render a distraction-free reader with typography controls, progress tracking, and resume-where-you-left-off.
  • Read articles aloud with a neural text-to-speech model, with word-level read-along highlighting.
  • Track listening position across devices.
  • Support highlighting, colored highlight categories, and margin notes.
  • Provide ranked full-text search (Postgres tsvector on the server, MiniSearch in the browser).
  • Provide semantic search over local embeddings, so a query can match meaning rather than words.
  • Resurface old highlights on a spaced-repetition schedule, with recall prompts.
  • Generate a personal podcast feed so the queue can be listened to in any podcast app.
  • Produce reading statistics, digests, and a periodic recap.
  • Export and import the whole library.
  • Share a highlight or article publicly by link.
  • Expose a small versioned public API with personal access tokens and webhooks.

5. What Booklet explicitly does not do

Being precise about non-goals is as important as listing features, because most misunderstandings about a system come from assuming it does something adjacent to what it does.

Booklet does not:

  • Bypass paywalls. It extracts what the fetching client is served.
  • Require an account. Local mode is the default, not a degraded trial.
  • Send your library to a third party for analysis. Embeddings and speech are generated locally or on your own server.
  • Use a hosted large language model to summarize, rewrite, or answer questions about your articles.
  • Guarantee that extraction is perfect. Some pages defeat any extractor.
  • Act as a general web archiver — it stores the article, not the whole site.
  • Provide multi-user collaboration, shared libraries, or team workspaces.
  • Sync playback position back from a third-party podcast app, which has no way to report it.
  • Implement its own authentication primitives where a reviewed library exists.
  • Run as a mobile-first product yet — the mobile app is real but narrower than the web app.

Part II — The web from the beginning

6. What is HTML, and what is a web page really?

HTML (HyperText Markup Language) is a text format that describes the structure of a document using nested elements written as tags. A paragraph is <p>…</p>; a heading is <h1>…</h1>; a link is <a href="…">…</a>.

Three separate technologies make up a typical page:

  • HTML — structure and content.
  • CSS (Cascading Style Sheets) — presentation: color, spacing, typography, layout.
  • JavaScript — behavior: code that runs in the browser and can change the page after it loads.

This separation matters to Booklet because the article lives in the HTML, while most of what makes a page unpleasant to read lives in CSS and JavaScript — or in HTML elements that are structurally present but editorially irrelevant.

7. The DOM, and why "the page" is not "the file"

When a browser loads HTML it builds a tree of objects in memory called the DOM (Document Object Model). JavaScript on the page can then add, remove, or rewrite parts of that tree.

This creates a practical distinction with real consequences:

  • The HTML source is what the server sent.
  • The DOM is what exists after scripts have run.

For a site that renders its article text on the server, the two are nearly the same and a simple fetch retrieves the article. For a site that ships an empty shell and fetches its content with JavaScript, the source contains no article at all. This is precisely why Booklet has both a server-side extraction path and a browser extension: the extension can read the DOM of a page you are actually looking at, including content that only exists after scripts ran, and including anything behind a session you are already logged into.

8. Article extraction and Readability

Extraction is the process of deciding which parts of a document are the article and discarding the rest.

Booklet uses Mozilla Readability (@mozilla/readability), the algorithm behind Firefox's Reader View. In outline, it:

  1. Parses the HTML into a DOM (server-side, Booklet uses jsdom to provide that DOM outside a browser).
  2. Removes elements that are structurally unlikely to be article content — navigation, headers, footers, forms, scripts.
  3. Scores remaining candidate containers using heuristics: density of text versus links, paragraph count, comma count, and class/ID names that suggest content or clutter.
  4. Selects the highest-scoring container as the article body.
  5. Extracts a title, byline, excerpt, and site name.

Readability is heuristic, not semantic. It has no understanding of what the article means; it counts and scores. That is why it works on a large fraction of the web and fails outright on the rest — for example on pages that are mostly image, mostly interactive, or structured so unusually that the heuristics pick the wrong container.

Sanitization is a separate concern from extraction

Extraction decides what to keep. Sanitization decides what is safe to keep. Extracted HTML from an arbitrary website will be rendered inside Booklet's own page, so any script, event handler, or hostile embed that survives becomes code running in the reader's browser with the reader's session. Booklet sanitizes with DOMPurify (see packages/shared/src/sanitize-html.ts), and this is not optional defense — it is the difference between a reader and an exploit.

9. EPUB, PDF, and why they are harder

EPUB

An EPUB file is, structurally, a ZIP archive containing XHTML documents, stylesheets, images, and a manifest describing reading order. Because the content is already HTML, extracting text is comparatively tractable: unzip, follow the spine, concatenate.

Rendering it faithfully is harder, because an EPUB reader is expected to paginate, respect embedded styles, and preserve internal links. Booklet uses epubjs in the web reader for this, and jszip to work with the archive.

PDF

PDF is fundamentally different. It is a page description format: it specifies that a particular glyph should be drawn at a particular coordinate. It does not necessarily record words, sentences, paragraphs, or reading order at all.

Consequences that shape the code:

  • Text extraction means reconstructing reading order from positioned glyphs, which is why extracted PDF text sometimes interleaves columns.
  • A "text layer" for selection and highlighting must be rendered separately from the visual canvas — Booklet uses pdfjs-dist, which does exactly this, and the end-to-end tests must explicitly wait for the text layer because it lags the canvas.
  • A scanned PDF contains no text at all, only images of text.

That last case is why the project includes an OCR path (apps/api/src/services/ocr-service.ts). OCR — Optical Character Recognition — infers characters from an image of a page. It is slow and imperfect, so it is a fallback for documents that yield no text, not a default.

IndexedDB deserves specific attention because two of its properties caused real bugs in this project.

Versioned schemas

An IndexedDB database has an integer version. Object stores can only be created inside an onupgradeneeded event, which fires only when code opens the database with a higher version than the one stored. Booklet's database is currently at version 6, and the comments in apps/web/src/lib/local/db.ts record why each bump happened — including one bump made specifically because some browsers had reached version 4 without ever receiving a store that was added later.

The corresponding hazard: any code that opens the database with a hardcoded version breaks the moment the version increases. That is exactly what happened when the embeddings store pushed the version from 5 to 6, and an end-to-end spec that opened with indexedDB.open("booklet", 5) began failing with "The requested version (5) is less than the existing version (6)" — in a test about rendering highlights, which had nothing to do with the store that changed.

Transactions commit later than requests succeed

This one is subtle and worth stating precisely, because it is a correctness trap rather than an inconvenience.

An IndexedDB write produces a request object. Its onsuccess event fires when the operation has succeeded within the transaction. The data is not durable until the enclosing transaction fires oncomplete. Code that awaits the request therefore returns while the write is still pending, and anything that tears the page down in between — a navigation, a reload, closing the tab — discards it.

// Resolves too early: the write may still be discarded.
await promisify(store.put(value));

// Resolves when the data is actually durable.
tx.objectStore(storeName).put(value);
await commit(tx);   // resolves on tx.oncomplete

Every local-mode write in Booklet — article status, tags, favorites, reading progress, highlights, collections — passes through this helper, so the distinction applied to all of them. See §46.

Part III — Local-first architecture

11. What "local-first" means here

Local-first software keeps the authoritative copy of your data on your device, and treats the network as an enhancement rather than a prerequisite.

The usual arrangement is the reverse: the server holds the data, the client is a window onto it, and losing the network means losing the application. Local-first inverts that. The practical differences are large:

  • The application works offline because there is nothing to be offline from.
  • Latency is disk latency, not network latency.
  • The product continues to function if the company operating it disappears.
  • Privacy is structural rather than promised: data that never leaves the device cannot be mishandled centrally.

The costs are equally real: synchronization becomes a genuine distributed-systems problem, storage is bounded by a browser quota, and any feature that needs server compute has to be reconsidered for the local case.

The governing rule

Signed-in mode may not be a better product; it may only be a synced one. When a feature can be built on the server but not in the browser, the correct response is to find a browser equivalent, not to ship the feature only for accounts.

This rule has been applied and, importantly, has been enforced against features that were already convenient. Full-text search was originally rejected because Postgres tsvector had no local equivalent; it shipped only once the browser side had a real ranked index of its own. Semantic search followed the same path: the server half landed first, and the browser half — a Web Worker running the same model, storing vectors in IndexedDB, fused with the same ranking algorithm — followed before the feature was considered done.

13. Synchronization

When a user signs in, the local library and the server library must be reconciled. The relevant concepts:

  • Last-write-wins is a conflict-resolution policy: when two devices change the same field, the most recent write is kept. It is simple and lossy. Booklet uses it deliberately in places where no better answer exists — notably listening position, where there is no correct reconciliation of "two devices were playing this at once", so the newest is as good an answer as any.
  • Server-stamped timestamps matter more than they appear to. If a client supplies the timestamp, a device with a wrong or dishonest clock decides what "most recent" means for every other device. Booklet's API stamps its own now() for listening position and for trash/restore, rather than trusting the client's value.
  • Idempotence — an operation that can be repeated without compounding its effect — is what makes retrying a failed sync safe.

15. Architectural principles

15.1 Shared code is shared deliberately, not incidentally

packages/shared holds logic that must behave identically everywhere: TTS chunking, read-along timing, highlight anchoring, search fusion, resurfacing schedules, URL canonicalization, sanitization. Two of the bugs this project has fixed were caused by the same algorithm existing in two places and drifting — which is the reason the chunker was moved into shared in the first place.

15.2 Degrade, never fail

Optional capabilities are wrapped so that their absence reduces quality rather than breaking the feature. Semantic search falling back to keyword-only is the clearest example: a model still downloading, an unindexed library, or unreachable weights all produce a slightly worse ranking rather than an error. A search box that errors is a far worse outcome than one that ranks less well.

15.3 The expensive thing goes off the critical path

Embedding an article, generating audio, and building a podcast enclosure are all seconds-to-minutes of CPU. None of them are awaited where a user is waiting. Indexing happens after the save returns; podcast audio is generated behind the feed poll; text-to-speech is chunked so the first sentence can play while the rest is still being produced.

15.4 Comments carry the reasoning, not the mechanics

The codebase's comments are unusually dense and are largely explanations of why — including why alternatives were rejected and what was measured. This is a deliberate choice with a real payoff: several defects in this project were found by reading a comment that no longer matched the code.

15.5 Measure before changing

Performance and quality claims in this project are expected to come with numbers. The read-along timing research (§49) is the clearest case: an initial measurement appeared to justify a second machine-learning model, and reading the per-word data underneath showed that most of the error came from trailing silence in the generated audio instead.

16. Runtime paths are not identical

A critical implementation detail, and a common source of false confidence: the interfaces do not all take the same path to the same data.

  • The web app in local mode reads and writes IndexedDB directly. No API involvement at all except extraction.
  • The web app signed in calls the Fastify API, which uses Prisma against Postgres.
  • Extraction always goes through the API, even in local mode — the browser cannot fetch arbitrary cross-origin pages, and the SSRF protections belong on the server anyway.
  • The extension submits the DOM of the current page rather than a URL, so it can capture script-rendered and authenticated content.
  • The mobile app is a separate React Native client with its own narrower data layer.

The practical consequence: "it works in the web app" does not establish that the mobile client works, and "the API tests pass" does not establish that local mode works. The test suite is organized to reflect this, which is why there are both API integration tests and browser-level end-to-end specs.

Part V — How the project was made

17. Intended development approach

The repository shows a product built feature-first against a written issue tracker, with each substantial change accompanied by tests and by commentary explaining the reasoning. Work is organized around numbered issues (#150–#168 in the recent period), and commits reference them.

Three habits are visible throughout and are worth naming because they explain the shape of the code:

  1. Non-goals are recorded. Rejected approaches are documented where the code would otherwise invite them again.
  2. Uncertainty is labeled. At least one script shipped with a prominent banner stating that it had never been executed and that its numbers should not be trusted — which turned out to be exactly right.
  3. Green tests are distrusted. Several tests in this repository were verified by deliberately breaking the code to confirm the test fails, because a test that passes for the wrong reason is worse than no test.

18.5 Stage 6 — Making the project verifiable

This stage deserves its own treatment because it explains a real quality gap.

For most of the project's life, continuous integration could not run:

  1. GitHub Actions' hosted-runner allowance was exhausted. Red CI was a billing state, not a code state — which is corrosive, because a permanently red signal stops being a signal.
  2. A complete GitLab CI pipeline was built as an alternative (453 lines, 7 jobs). GitLab's free tier then also ran out (ci_quota_exceeded).
  3. The GitLab pipeline was ultimately removed in favor of a self-hosted GitHub Actions runner, on the correct reasoning that GitHub meters only hosted runners — a runner you host yourself is unmetered.
  4. That runner came online on 2026-08-11, running in a WSL2 Ubuntu 26.04 distro with Docker installed inside it and the runner managed as a systemd service.

On its first real run it passed 6 of 7 jobs and immediately caught two genuine defects — one a regression from the IndexedDB version bump, one an environmental limitation of the runner's browser. Both are documented in Part XVI.

What this means when reading the history

Four end-to-end specs were failing on main and nobody knew, because nothing was gating. They had been read as flakiness. When CI is unavailable for an extended period, the absence of a failure signal is not evidence of correctness, and this repository is a concrete demonstration of that.

Why nodeLinker: hoisted is set, and why it matters

pnpm's default layout uses symlinks and, on Windows, NTFS junctions. Metro — the bundler React Native uses — did not traverse those junctions correctly, so the mobile app's entry import could never resolve. Rather than fight Metro's resolver, the workspace switched to a flat node_modules layout.

That fix has a consequence worth knowing: with a flat layout, a package can successfully import a dependency it never declared, because some other package hoisted it to the root. This is how @huggingface/transformers was available to the web app before it was a declared dependency of the web app. The same flat layout is also why the workspace pins react and react-dom with explicit overrides — three copies of React otherwise coexisted, and rendering across two React instances fails with an opaque error.

Part VII — Concepts you need for the rest

26. TypeScript, and what it does and does not guarantee

TypeScript is JavaScript with static type annotations. It is checked at build time and then erased — the running program is plain JavaScript with no type information.

Two consequences matter here:

  1. Types cannot validate data arriving from outside the program. An API response typed as Article is a claim, not a check. Runtime validation is separate work.
  2. A type error is a compile-time failure, so tsc --noEmit across all four apps is a genuine gate — it catches whole classes of mistake before any test runs. That is why it is a distinct CI job.

27. Asynchrony, promises, and why ordering bugs happen

JavaScript runs on a single thread with an event loop. Operations that would block — network, disk, database — return a Promise: an object representing a value that will exist later. await suspends the surrounding function until it settles, letting other work proceed meanwhile.

This is the root of a bug class that appears repeatedly in this document. A function can return before its effects are durable; a page can navigate away while a write is still pending; two operations started in one order can finish in another. Several defects in Booklet's history are exactly this shape, including the IndexedDB durability issue in §46 and four end-to-end tests that navigated before the write they depended on had committed.

28. Web Workers, and why the model runs in one

A Web Worker is a separate JavaScript thread in the browser. It cannot touch the DOM; it communicates with the page by passing messages.

Booklet runs its embedding model in a Worker because embedding is dense numerical computation that runs for tens of milliseconds per chunk and for minutes across a library. On the main thread that is a frozen page — no scrolling, no typing in the very search box the work exists to serve.

Two implementation details in the message protocol are worth extracting as general lessons:

  • Requests carry an id. Indexing and querying are both in flight at once, so replies must be matched to their request rather than assumed to arrive in order.
  • Errors are messages, not throws. An uncaught throw inside a Worker surfaces as an error event with no way to tell which request failed, which would leave every other request's promise hanging forever.

29. Embeddings, in plain terms

An embedding is a list of numbers that represents a piece of text's meaning, produced by a neural network trained so that texts with similar meanings get similar lists.

Booklet uses all-MiniLM-L6-v2, which produces 384 numbers per text. Two properties make it usable:

  • Mean pooling: the model produces one vector per token; averaging them yields one vector for the whole passage.
  • Normalization: each vector is scaled to length 1, which makes comparison cheap (see below).

Cosine similarity

Cosine similarity measures the angle between two vectors, ignoring their magnitudes. It ranges from −1 (opposite) through 0 (unrelated) to 1 (identical direction).

cosine(a, b) = (a · b) / (|a| × |b|)

where a · b = Σ aᵢbᵢ   (the dot product)
      |a|   = √(Σ aᵢ²)  (the magnitude)

When both vectors are already unit length, the denominator is 1 and cosine similarity is just the dot product. Booklet's shared implementation still divides by the magnitudes — a deliberate choice, because it makes the function correct for callers that pass un-normalized vectors rather than silently wrong.

A measured example

30. Full-text search concepts

Postgres's full-text search converts documents into a tsvector: a sorted list of normalized words (lexemes) with their positions.

  • Stemming reduces words to a root so that "running" matches "runs". Postgres uses Snowball; the browser side uses Porter. They disagree on a handful of words, which is accepted as long as behavior a reader would notice matches.
  • Weighting assigns each part of a document a class from A (most important) to D. Booklet weights title A, author and site name B, excerpt C, and body text D, so a title hit outranks a passing mention in a long body.
  • websearch_to_tsquery parses a query the way a search engine user expects: bare words are combined with AND, quotes make phrases, OR and -exclusion work.
  • A GIN index makes matching a tsvector fast.
  • ts_headline produces a snippet with matches marked.
A security detail that is easy to get wrong

ts_headline does not escape the document it quotes from. Asking it to wrap matches in <mark> and then rendering the result as HTML feeds arbitrary article text straight into the DOM — a cross-site scripting vulnerability delivered by any page a user saves.

Booklet instead asks ts_headline to mark matches with two C0 control characters ( and ), which cannot appear in real prose and are not HTML. The client turns them into markup after escaping. The constants live in packages/shared so both ends agree.

31. Reciprocal Rank Fusion

RRF combines several ranked lists into one without needing their scores to be comparable — which is essential here, because a ts_rank value and a cosine similarity have no common scale.

score(document) = Σ  1 / (k + rankᵢ(document))
                 lists

k = 60   (the conventional default, used here)

Each list contributes based only on position. A document ranked first in one list and absent from another still scores well; a document ranked middling in both can beat it. Two properties make it a good fit for Booklet:

  1. It needs no calibration. No tuning of how much a keyword point is worth against a similarity point.
  2. With one list it is the identity. RRF over a single ranked list preserves that list's order exactly, so every degraded path — semantic search disabled, nothing indexed, model unavailable — is a genuine no-op rather than a special case that must be maintained separately.

32. Spaced repetition and SM-2

Spaced repetition exploits the spacing effect: information reviewed at increasing intervals is retained far better than information reviewed repeatedly in one sitting. Retrieval practice adds a second finding — actively recalling something strengthens memory more than re-reading it.

Together these explain why Booklet does not simply show you an old highlight. It asks you to recall it first.

SM-2 is the scheduling algorithm from SuperMemo, and the basis of most flashcard software. Each item carries:

  • an easiness factor — how easy the item is, starting at 2.5 and floored at 1.3;
  • an interval — days until the next review;
  • a repetition count.

After each review the grade adjusts the easiness factor and the interval grows roughly geometrically; a poor grade resets the interval. Booklet's implementation lives in packages/shared/src/resurface.ts and caps intervals at 36,500 days, which is a hundred years — a deliberate guard against overflow rather than a meaningful schedule.

An approximate-nearest-neighbor index would be complexity bought for a scale that does not exist here.

36. Search: keyword, semantic, and fusion

Server path (apps/api/src/routes/search.ts)

  1. Run one SQL query that ranks with ts_rank against the generated searchVector column, matching with websearch_to_tsquery('english', q), and additionally matching q against the tags array as an exact element.
  2. Ask ts_headline for a snippet, but only for rows that already matched and are already limited — never as part of the scan.
  3. Embed the query and cosine-rank the user's stored chunk vectors, best chunk per article.
  4. Fuse the two id lists with RRF and take the top 25.
  5. Hydrate through Prisma, then restore the fused order — findMany does not preserve the order of an IN list, and that order is the entire point.

Step 3 is wrapped in a try/catch that logs a warning and continues. Semantic failure must degrade the ranking, not fail the request.

Why the tsvector excludes tags

Tags are matched as exact array elements rather than folded into the tsvector, for two reasons. A tag is a label rather than prose, so stemming it is wrong. And more decisively, the natural way to include it — array_to_string(tags, ' ') — is only STABLE, not IMMUTABLE, and Postgres refuses to build a generated column from a non-immutable expression. The attempt fails with "generation expression is not immutable".

Browser path

The local index uses MiniSearch with the Porter stemmer and these field boosts:

The index is cached against a signature of ${articles.length}:${newestUpdatedAt}, so it is rebuilt when the library changes and reused otherwise. Trashed articles are excluded at query time rather than at index time, so trashing something does not invalidate the whole index.

Chunking for embedding

chunkForEmbedding(text, maxChars = 1200, overlapChars = 200)

Long articles exceed the model's input window, so they are split. The overlap exists so that a passage spanning a boundary is still wholly present in one chunk; without it, the most relevant sentence in an article could be cut in half and match nothing well.

An article is scored by its single best-matching chunk, not the average. Relevance lives in a passage — averaging lets a long article dilute a strong hit into invisibility.

Results below a cosine of 0.2 are discarded, because beating an unrelated document is easy when both scores are noise near zero.

37. Why the embedding worker is bundled outside Next.js

This is a piece of hard-won knowledge that will otherwise be rediscovered painfully.

The canonical way to reference a Worker in a bundled application is:

new Worker(new URL("./embedding-worker.ts", import.meta.url), { type: "module" })

Turbopack, the bundler Next.js 16 uses, does not compile this. It treats the file as a static asset and copies the TypeScript source into .next/static/media verbatim. The build exits 0, the URL resolves, and the browser then fails to parse what it is served. This was confirmed against Next 16.2.11 with and without the options object, and with the module marked "use client" — raw .ts every time.

The worker is therefore bundled by a small esbuild script into public/workers/embedding-worker.js, wired to predev and prebuild, and referenced by plain URL. This has a second and larger benefit: left in Next's module graph, @huggingface/transformers and onnxruntime-web were landing in a shared client chunk — megabytes of WASM glue shipped to every visitor, including everyone who never enables semantic search. Out of the graph, it is one file fetched only when a Worker is actually constructed.

The general lesson

A green build says nothing about whether an artifact runs. This failure is invisible to tsc, invisible to next build, and invisible to unit tests. The only thing that catches it is executing the artifact in a real browser — which is why a Playwright test exists specifically to load the worker and check it returns a 384-dimension unit vector.

38. Text-to-speech: the pipeline

Text-to-speech (TTS) converts text into audio. Booklet uses Kokoro, a neural TTS model, running through the same @huggingface/transformers + onnxruntime stack as the embedding model.

The dominant design constraint is time to first audio (TTFA): how long the user waits between pressing play and hearing a voice. Generation runs at roughly 1–2× realtime on CPU, so generating a whole article before playing any of it would mean minutes of silence.

The pipeline:

  1. Chunk the article into short speakable spans (§47).
  2. Generate the first chunk immediately, deliberately smaller than the rest so it arrives sooner.
  3. Play it while generating subsequent chunks ahead of playback.
  4. Prefetch to a fixed depth so playback never catches the generator.
  5. Cache at two tiers — in the browser, and on the server keyed by content.

The worker pool

Model inference is CPU-bound and would block Node's event loop, so generation happens in separate worker processes (tts-worker-process.ts) managed by a pool (tts-pool.ts). The pool exists so several chunks can be produced concurrently; that concurrency is why timing information is carried back with each result rather than stored in a module-level variable, which the next completing request would clobber.

Caching

The server cache is content-addressed: the key is a SHA-256 of voice, speed, and text. Identical text spoken with identical settings is generated once, ever, for anyone. It is an LRU bounded by TTS_CACHE_MAX_MB, defaulting to 200 MB.

The key carries a version prefix (tts:pcm16:v1:). Any change to what is stored under a key — for example adding word timings alongside the audio — requires bumping that prefix, because otherwise old entries would be read as if they had the new shape.

40. Read-along highlighting, and a research result

Read-along highlights each word as it is spoken. Doing it properly requires knowing when each word occurs in the audio. Kokoro does not provide that — generate() returns audio samples, and even the streaming API exposes phonemes as an untimed string.

The shipped estimate

Booklet maps character position to time linearly:

charPos = (audioEl.currentTime / audioEl.duration) × chunkText.length

and highlights the last word whose span begins before charPos. Using the full chunk length as the denominator — rather than only the words' own lengths — leaves inter-word gaps their proportional share of time, so words do not run together.

The assumption is that speech is paced evenly per character. It is not. "Through" and "thought" are seven characters and one syllable; "a" is one character and one syllable; a comma adds time no character accounts for.

The measurement

Issue #159 asked whether this matters enough to pay for forced alignment — a second model pass that locates each word in the audio. The measurement was run on 2026-08-12 by generating real Kokoro audio and taking word timestamps from whisper-base.en as ground truth.

The finding, and why reading the raw data mattered

The summary statistic said the estimate drifts 221–451 ms RMS (837 ms worst), which on its face justifies a second model. The per-word output said something more specific: the error grows monotonically with word position — 0, 130, 268, 425, 575, 770 ms across a single chunk. That is a systematic scale error, not speech pacing unevenly.

The cause is trailing silence. Kokoro ends every clip with a mean 457 ms of near-silence (401–512 ms, strikingly consistent), and the player spreads the text across the whole audio duration, silence included. Anchoring the same estimate to the spoken interval — one number, no second inference — roughly halves the drift.

The original conclusion was right in direction and about twice too strong in magnitude. Alignment remains justified for tap-to-seek, but on the residual rather than on a padding artifact.

Measured costs of alignment, for completeness: 831 ms per chunk mean (1059 ms worst) on CPU, and 0.019% storage overhead — 396 bytes of timings against 1990 KB of audio. Storage is a non-issue; the latency is real, which is why it belongs off the critical path.

The perceptibility threshold used throughout is PERCEPTIBLE_DRIFT_MS = 100, fixed in the source before any measurement was taken — which is what stops it from being chosen afterwards to suit the result.

41. Highlight anchoring

A highlight must survive re-extraction. If it were stored as "characters 4,102 through 4,180", any change to the extracted text — a fixed extractor, a re-save, an updated article — would silently move every highlight in the document.

packages/shared/src/highlight-anchor.ts therefore stores enough context to find the passage again: the selected text plus surrounding prefix and suffix, so the anchor can be re-located even if its offset has shifted.

The related DOM problem: a browser selection can begin and end inside text nodes that do not correspond to the plain-text offsets used for storage. Bridging offsets to nodes is fiddly enough that this repository fixed a real bug where a section anchor resolved to the wrong element at a text-node boundary.

42. Resurfacing and recall prompts

Resurfacing selects highlights to show you again. Two mechanisms combine:

  1. Scheduling — SM-2 (§32) decides when an item is due.
  2. Prompting — recall-prompt.ts turns the highlight into a question rather than simply displaying it, so the interaction is retrieval practice rather than re-reading.

The scheduling state lives on the highlight, and — following the local-first rule — exists in both IndexedDB and Postgres, so review works signed out.

43. The personal podcast feed

A podcast feed is an RSS 2.0 XML document where each <item> carries an <enclosure> pointing at an audio file. Any podcast client can subscribe to a URL and will poll it for new items.

Booklet mints a per-user feed URL containing a 32-byte opaque token. That token:

  • authenticates only the feed and enclosure routes — it cannot be used against the ordinary API or the versioned public API;
  • is revocable independently of the account's other credentials;
  • cannot be created through the personal-access-token flow, and does not appear in the token list.

Because the URL is the credential, an unknown token returns 404 rather than 401 — a 401 confirms that a feed exists and invites retrying.

Feed correctness details that are easy to get wrong

  • itunes:image is required by Apple at channel level. A feed without it is rejected from the directory — not with an error a client shows the user, but by silently refusing the show. Booklet emits both itunes:image and the RSS 2.0 <image> block, since older clients read the latter.
  • guid is keyed on the article, not the audio, so regenerating audio does not appear as a brand-new episode.
  • pubDate must be parseable. A date a client cannot parse sorts the episode to the epoch, burying it permanently.
  • Enclosures declare Accept-Ranges: none. The storage layer exposes no offset read, so honoring a range request would mean buffering the whole file to slice it. Podcast clients download enclosures whole and seek locally, so this costs nothing they actually do.
  • An unready episode returns 503 with Retry-After, not 404. A client that receives 404 marks the download permanently failed and stops asking; 503 is precisely the "come back later" that is true.
  • Stored audio is evicted when an article leaves the feed window, and deleted outright when the feed is turned off — because no future poll will ever come to clean it up.

44. The IndexedDB durability helper

Restating §10 as implementation, because it applies to every local write:

function commit(tx: IDBTransaction): Promise<void> {
  return new Promise((resolve, reject) => {
    tx.oncomplete = () => resolve();
    tx.onerror    = () => reject(tx.error);
    tx.onabort    = () => reject(tx.error ?? new Error("IndexedDB transaction aborted"));
  });
}

Reads still await the request, because their result is available at onsuccess and there is nothing to make durable. Writes await the transaction.

An honest note about what this did and did not fix

This change was made while investigating four failing end-to-end tests, on the theory that it was the cause. It was not: applying it alone left them failing at the same rate. The actual cause was that the tests issued page.goto on the line after a click, inside the ~1 ms window before the write committed — a synchronization bug in the tests, not a product race, since no human can navigate that fast.

The helper was kept anyway, on its own merits: await localArticles.put(…) now means what every caller already assumed. But the record should show that the measurement contradicted the hypothesis, and that the hypothesis was abandoned rather than defended.

50. SSRF, and why the extractor is the risky part

Server-Side Request Forgery is an attack where a user persuades a server to make a request on their behalf to somewhere they could not reach themselves — typically an internal service, a cloud metadata endpoint, or localhost.

Booklet's extractor is exactly this shape by design: it accepts a URL from a user and fetches it. The mitigation (apps/api/src/lib/private-address.ts) resolves the hostname first and rejects private or reserved addresses — 10/8, 127/8, 169.254/16, 172.16/12, 192.168/16, and CGNAT 100.64/10, plus IPv6 equivalents. Resolution happens before the fetch, so a hostname that resolves to a private address is caught even though the URL looks public.

There is one escape hatch, EXTRACTION_ALLOW_PRIVATE_ADDRESSES, which exists so the end-to-end suite can fetch fixtures from 127.0.0.1. It logs a warning on startup and is ignored entirely when NODE_ENV=production — the guard is structural rather than a matter of remembering not to set it.

51. Privacy as an architectural property

The strongest privacy claim Booklet makes is not a policy but a consequence of where computation happens:

  • In local mode, the library never leaves the device. There is no server to trust.
  • Embeddings are computed by a model running on the user's own machine or their own server. No text is sent to a third-party embeddings API.
  • Speech is generated by a model the project runs, not by a hosted TTS service.
  • The only unavoidable external contact for extraction is fetching the page being saved, which the user asked for.

The honest caveats: model weights are downloaded from Hugging Face on first use, which is a request to a third party (for the file, not with your data); and optional error reporting and analytics exist, which is why they are behind configuration rather than on by default.

Setup notes that are not obvious, recorded because each cost time to discover:

  • The runner needs libicu for its bundled .NET runtime. Registration fails without it, and the registration script does not check.
  • WSL tears a distro down when its last session ends, which stops systemd and takes the runner offline with it. vmIdleTimeout=-1 governs the VM, not the distro; holding a session open (wsl -d Ubuntu -u root -- sleep infinity) is what actually keeps it alive.
  • WSL2 shares localhost with Windows, so CI's servers on 3000/4000 collide with anything a developer is running on those ports.
  • One runner executes one job at a time, so the seven jobs serialize. Registering more runners parallelizes them.
  • concurrency: cancel-in-progress means every push cancels the run in flight — including your own.

Part XIII — A worked example

57. Saving and finding one article, end to end

A user, signed in, saves an essay about working under constraint. Following it through every layer:

1. Capture

The user pastes a URL. The web app POSTs it to /api/articles.

2. SSRF check

The hostname is resolved. Its addresses are checked against the private/reserved ranges. A public address passes.

3. Fetch and extract

The page is fetched with a size cap and a redirect limit. jsdom builds a DOM; Readability scores containers and selects the article; title, byline, excerpt, and site name are extracted.

4. Sanitize and inline

DOMPurify strips scripts, event handlers, and hostile markup. Images are fetched and inlined as data URIs, so the article survives the source going away.

5. Persist

A row is written. Postgres computes the searchVector column automatically, since it is GENERATED ALWAYS … STORED:

setweight(to_tsvector('english', coalesce(title, '')),        'A') ||
setweight(to_tsvector('english', coalesce(author,'') || ' ' ||
                                 coalesce(siteName,'')),      'B') ||
setweight(to_tsvector('english', coalesce(excerpt, '')),      'C') ||
setweight(to_tsvector('english', coalesce(extractedText,'')), 'D')

6. Respond, then index

The response returns immediately. Embedding is started after, not awaited: the text is chunked at 1200 characters with 200 of overlap, each chunk is embedded to 384 dimensions, and the vectors replace any previous ones for that article in a single transaction. Embedding a long article is seconds of CPU; nobody should watch a spinner for optional work.

7. Six months later

The user searches "why deadlines make people creative". The essay never uses those words.

  • Keyword side: websearch_to_tsquery produces deadline & make & people & creative. The essay matches poorly or not at all.
  • Semantic side: the query is embedded; cosine similarity against the essay's best chunk scores around 0.44, far above the 0.2 floor and far above unrelated text at roughly −0.02.
  • Fusion: RRF merges both id lists. The essay appears because the semantic list ranks it highly, while an exact keyword match — had there been one — would still rank first.

8. Render

Ordered ids are hydrated through Prisma and re-sorted into the fused order. Snippets containing the control-character sentinels are converted to markup after escaping. The user finds the article they could not name.

The point of the example

Every step is either cheap or off the critical path, and every step degrades rather than fails. Extraction failure still saves a record with an error status. Embedding failure leaves search keyword-only. Semantic failure at query time is caught and logged. There is no step whose absence produces an error page.

Part XIV — Limitations and honest gaps

58. Current limitations

  1. The web unit suite is red on Node 25. Five failures, all from the built-in localStorage shadowing jsdom's. An environment problem, but a real one — the suite does not currently pass on the maintainer's machine.
  2. Extraction is heuristic. Readability fails on some pages, and nothing detects when it has silently selected the wrong container.
  3. Read-along drifts perceptibly. Measured at 110–265 ms RMS after correcting for trailing silence, against a 100 ms threshold. Tap-to-seek is therefore not shipped.
  4. Trailing silence is not yet trimmed. The measurement in §40 identifies a free, roughly-halving improvement that has not been implemented.
  5. The podcast feed has no artwork. The code emits itunes:image when PODCAST_ARTWORK_URL is set, but no cover art exists — the repo has only an SVG icon, and Apple requires a 1400×1400–3000×3000 JPEG or PNG. Until one exists, Apple would reject the show.
  6. No end-to-end proof of a real podcast subscription. Everything testable from a CI box passes; "subscribable in a real client, and audio actually plays" needs a phone.
  7. Mobile is narrower than the web app. No real PDF or EPUB pagination.
  8. @live tests do not run in CI. Chromium on the self-hosted runner has no outbound network, so live extraction, the dictionary, and model downloads are excluded. That is lost coverage, recovered only by running them by hand.
  9. One runner, so CI serializes. Seven jobs run one at a time.
  10. Semantic search in local mode is opt-in and per-device. The index is built on the device that enabled it; there is no sharing.
  11. No conflict resolution beyond last-write-wins. Adequate for one person on several devices; not a general sync solution.
  12. Storage is bounded by browser quota in local mode, and eviction is the browser's decision, not the app's.
  13. The 397 KB TECHNICAL_DOCUMENTATION.html has drifted in places. It has been corrected where this document found conflicts, but it is large and hand-maintained.

59. High-value next steps

  • Trim trailing silence from generated audio — free, halves read-along drift, improves what ships today.
  • Pin Node to an LTS release for the test suite, or isolate jsdom's localStorage from Node's built-in.
  • Produce podcast cover art and set PODCAST_ARTWORK_URL.
  • Give the runner's browser outbound network, or run @live on a schedule from somewhere that has it.
  • Register a second CI runner to parallelize.
  • Implement forced alignment as a background pass, cached beside the audio, with the cache prefix bumped — enabling tap-to-seek.
  • Bring the mobile client closer to parity on document rendering.
  • Detect low-confidence extraction and surface it, rather than silently storing a bad result.

Part XV — Troubleshooting

118. TypeError: localStorage.clear is not a function

Accompanied by Warning: --localstorage-file was provided without a valid path. Node 25 ships an experimental built-in localStorage that shadows the one jsdom provides, so tests operate on the wrong object. Use Node 22 or 24 for the web suite, or isolate the global in the test setup.

119. The requested version (5) is less than the existing version (6)

Code opened IndexedDB with a hardcoded version lower than the database's current one. Open without a version — the app has already opened it, so the stored version is the right one. Never pin a version number in a test.

120. EADDRINUSE, or servers behaving strangely

Ports 3000 and 4000 are used by CI's end-to-end job. Because WSL2 shares localhost with Windows, a CI run and a local dev server collide on them. Run development servers on other ports; CORS accepts any localhost port in development.

Note also that pkill does not reliably kill a Node server on Windows. Kill by port instead — find the listener and stop that PID.

121. The CI runner shows offline

Check whether the WSL distro is running at all (wsl -l -v). If it is Stopped, the systemd service inside it stopped with it. The durable fix is a held-open session plus vmIdleTimeout=-1; see §56.

122. Semantic search silently does nothing

In order of likelihood: the setting is off (it is opt-in and off by default in local mode); nothing has been indexed yet; the worker bundle was not built (pnpm --filter @booklet/web build:worker); or the model download failed. All four degrade to keyword-only by design, so the symptom is "results look ordinary" rather than an error.

123. Saving an article fails with "private or reserved network address"

The SSRF guard rejected the target. This is correct for real private addresses. For the e2e fixture server on 127.0.0.1, set EXTRACTION_ALLOW_PRIVATE_ADDRESSES=true — it is ignored in production.

124. Prisma reports pending migrations, or the API 500s on signup

Run pnpm --filter @booklet/api exec prisma migrate deploy. A PrismaClientKnownRequestError with code ECONNREFUSED means the database is not reachable at DATABASE_URL, not that the query is wrong.

125. A CI run was cancelled and I did not cancel it

Expected. concurrency: cancel-in-progress: true cancels the run in flight whenever a newer one starts on the same ref — including your own next push.

Anchoring: Storing enough context around a highlight to re-locate it if the text changes.

App Router: Next.js routing where folders are routes and page.tsx is the content.

Cosine similarity: The angle between two vectors, used to compare meanings; −1 to 1.

CORS: Cross-Origin Resource Sharing — browser rules governing which origins may call an API.

COEP / COOP: Headers that isolate a page so SharedArrayBuffer may be used.

CTC: Connectionist Temporal Classification — a speech-model output structure usable for forced alignment.

DOM: Document Object Model — the browser's in-memory tree for a page, after scripts run.

DOMPurify: Library that strips dangerous constructs from untrusted HTML.

Embedding: A vector representing a text's meaning.

EPUB: An e-book format; a ZIP of XHTML documents plus a manifest.

Extraction: Deciding which part of a document is the article.

Fastify: The Node HTTP framework the API is built on.

Forced alignment: Locating each word of a known transcript within audio.

GIN index: A Postgres index type suited to tsvector matching.

Hoisted node_modules: A flat dependency layout; here it lets undeclared imports accidentally resolve.

IndexedDB: The browser's transactional database; Booklet's local source of truth.

Idempotent: Safe to repeat without compounding effects.

Kokoro: The neural text-to-speech model used for read-aloud.

Last-write-wins: Conflict resolution keeping the most recent write.

Local-first: Architecture where the device holds the authoritative copy.

Lexeme: A normalized word stored in a tsvector.

MiniLM: all-MiniLM-L6-v2, the 384-dimension embedding model used here.

MiniSearch: The in-browser full-text index library.

Monorepo: One repository holding several applications and shared packages.

OCR: Optical Character Recognition — reading text out of an image.

ONNX Runtime: The engine that executes the neural models.

Playwright: The browser automation framework used for end-to-end tests.

Prisma: The typed ORM generating a database client from a schema.

Porter / Snowball: Two stemming algorithms; the browser uses the first, Postgres the second.

Promise: An object representing a value that will exist later.

Readability: Mozilla's article-extraction algorithm.

Retrieval practice: Recalling information actively, which strengthens memory more than re-reading.

RRF: Reciprocal Rank Fusion — merging ranked lists by position rather than score.

Sanitization: Removing unsafe constructs from untrusted markup.

Self-hosted runner: A CI machine you operate; unmetered, unlike hosted runners.

SSRF: Server-Side Request Forgery — making a server fetch somewhere it should not.

Stemming: Reducing words to a root so related forms match.

Structured clone: The browser's algorithm for copying values, which handles typed arrays natively.

tsvector / tsquery: Postgres's full-text document and query types.

Turbopack: Next.js 16's bundler; does not compile first-party TypeScript workers.

Final summary

Booklet is best understood as a reading environment that refuses to depend on anyone:

a page on the web
    -> extracted to text you own
    -> stored on your device first
    -> readable, listenable, searchable by meaning
    -> resurfaced so it is not merely stored
    -> synced only if you ask

The web publishes the articles. Readability separates prose from furniture. IndexedDB keeps your copy. Postgres keeps a synced copy if you want one. Kokoro reads it aloud. MiniLM makes it findable by meaning rather than by wording. SM-2 brings it back before you forget it.

None of those parts is unusual on its own. What the project is actually asserting is that they belong together, that the local copy is the real one, and that a feature which only works when you are signed in is not finished.
