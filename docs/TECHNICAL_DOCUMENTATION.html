Part IThe Big Picture

What Booklet Is

Booklet is a read-it-later and annotation app: save an article, PDF, or EPUB from anywhere; read it in a clean, distraction-free view; highlight and annotate as you go; and — the part most apps in this space skip — actually see those highlights again later, through a real spaced-repetition schedule instead of a pile that quietly grows forever.

It's a monorepo containing a real backend API, a web app, a browser extension, and a mobile app, all built around one architectural commitment: everything works with zero account. Saving, reading, highlighting, resurfacing, PDF/EPUB rendering, search, OCR, and text-to-speech all run entirely client-side against the browser's own IndexedDB when signed out. An account exists for exactly one reason — syncing a library across devices — and nothing product-facing is gated behind creating one.

Why It Exists

Read-it-later apps have a well-known failure mode. You save something interesting, fully intending to read it later, and it joins a queue that only ever grows. Occasionally you do read something and highlight a passage that actually mattered to you — and then that highlight disappears into a list you never open again, indistinguishable from the hundred other things you saved and forgot.

Booklet's actual thesis is that the second half of that problem — highlights vanishing — is the more interesting one to fix, and that fixing it properly means borrowing the one piece of technology that already solved "how do you make sure you actually remember something": spaced repetition. A highlight in Booklet isn't a stored string; structurally, it's a flashcard whether the person who made it thought of it that way or not. It resurfaces later on a real SM-2 schedule (the same algorithm behind Anki, see Resurfacing), with interval growth on recall and a reset on a miss — not a random reminder, not "here's five things from your library," an actual memory-scheduling algorithm making the call.

Everything else about the project follows from taking a handful of related opinions further than most similar tools bother to: that a saved PDF or EPUB should be rendered, not flattened into plain text; that read-aloud should feel instant, not like a novelty; and that the entire save → read → highlight → resurface loop should work the same way whether or not you've ever created an account.

Design Principles

Offline is the default

Not a fallback mode, not a degraded experience — the primary, first-class way to use the app. See The Offline-First Model.

Render, don't flatten

A PDF's pages and an EPUB's chapters are rendered as themselves — real canvas output, real pagination — not reduced to plain text and re-flowed.

Real algorithms, not heuristics

Where a real, well-understood algorithm exists for a problem (SM-2 for spaced repetition), it's used directly rather than approximated with a simpler-looking heuristic.

The integration surface is a product

The public API, personal access tokens, and webhooks aren't an afterthought bolted onto the internal routes — they're a deliberately separate, versioned surface.

Measure, don't assume

Performance and architecture decisions in this codebase are backed by real, hand-run measurements — see the TTS section for the most extensive example of this discipline.

Fix root causes

When something breaks, the instinct throughout this project's history has been to find the actual mechanism, not to route around the symptom with a workaround.

Part IIArchitecture

The Monorepo

Booklet is one pnpm workspace containing five real packages: 

apps/
  api/            # Fastify API + Prisma schema — the one backend
  web/            # Next.js web app
  extension/      # Browser extension (Manifest V3, Chrome + Firefox)
  mobile/         # Expo / React Native app
packages/
  shared/         # Types + pure logic shared by every app above
                  # (request/response DTOs, highlight anchoring, SM-2, tts-voices, ...)
Why a monorepo

Four real clients (web, extension, mobile, plus the API itself) need to agree on the exact same request/response shapes, highlight-anchoring math, and SM-2 scheduling logic. Splitting those into separate repositories would mean either duplicating that logic four times (and letting the copies drift, silently, the moment one gets fixed and the others don't) or publishing it as a versioned package with all the release-and-bump ceremony that implies for what is, in practice, one team iterating on one product. packages/shared exists specifically so "the highlight-anchoring algorithm" and "what an ArticleSummary looks like on the wire" are each defined exactly once.

The Offline-First Model

Every product surface in the web app is built against one repository-style interface, with two real implementations behind it:

  • Local mode (no account) — reads and writes IndexedDB directly in the browser, via apps/web/src/lib/local/db.ts.
  • Synced mode (signed in) — talks to the real Fastify API, which persists to PostgreSQL.

apps/web/src/lib/data/*.ts is the seam: every page and component calls functions like loadArticles(isAuthenticated) or createHighlight(...) from that layer, and the layer itself decides which backend actually answers, based on whether the caller is authenticated. The UI code never branches on "am I signed in" itself — it just calls the same function either way.

Why this isn't just a demo mode

The local implementation isn't a stripped-down preview meant to get someone to sign up — it implements the exact same contract as the server-backed one: the same save/highlight/ resurface behavior, the same SM-2 scheduling math (imported directly from packages/shared, not reimplemented), the same search semantics. Signing in for the first time migrates whatever's already in IndexedDB onto the new account rather than discarding it, which only makes sense if the two modes were genuinely equivalent the whole time.

Anatomy of Saving an Article

Concretely, here's what happens end to end when a signed-in user pastes a URL and clicks Save — a useful worked example of how the pieces above actually fit together:

  1. Client (web app) — lib/data/articles.ts's saveArticleByUrl POSTs to /api/extract.
  2. API (routes/extract.ts) — hands off to extraction-service.ts's fetchAndExtract.
  3. SSRF guard — before fetching anything, the target host is DNS-resolved and checked against private/ loopback/link-local ranges, on every redirect hop, not just the first request.
  4. Fetch + parse — the raw HTML is fetched server-side and run through @mozilla/readability (via jsdom) to pull out the actual article content.
  5. Image inlining — every <img> in the extracted HTML is fetched server-side and re-embedded as a base64 data: URI, so the saved copy survives even if the original page (or its images) later disappears.
  6. Client (again) — the extracted content comes back to the browser, which then POSTs it to /api/articles to actually persist the row (a deliberate two-step split: extraction is a stateless, unauthenticated operation shared with local/anonymous mode; only the second step needs a real account).
  7. Persistence — a new Article row is written, duplicate-checked against both the raw URL and its canonicalized form (so a tracking-param or AMP-link variant of something already saved is caught).

The same /api/extract stateless-extraction step is reused, unmodified, by local/anonymous mode — it just skips step 6 and writes straight to IndexedDB instead.

Part IIIThe Technology Stack

Every major tool this project depends on, and the actual reasoning behind picking it — not just a list of logos.

TypeScript, Everywhere

Every line of application code in this repository — API, web app, extension, mobile, shared package — is TypeScript. There is no plain-JavaScript escape hatch anywhere in the product code.

Why

The most concrete reason is the monorepo itself: packages/shared's whole purpose is to be a single source of truth for shapes — the Article, Highlight, and HighlightPosition types, the request/response DTOs every route and every client agree on. That only actually works as a guarantee (not just a convention someone has to remember to follow) if the compiler is the one enforcing it. A JSON shape drifting silently between the API and one of four different clients is exactly the class of bug static types exist to catch before it ships.

What "TypeScript" means for a beginner: JavaScript is the language web browsers (and Node.js) actually execute — it has no concept of a variable's "type" being checked before the code runs. TypeScript is a superset of JavaScript that adds an optional type system on top: you can annotate a function as taking a string and returning a number, and a separate tool (tsc, the TypeScript compiler) checks that every call site actually respects that before compiling it down to plain JavaScript. The types themselves don't exist at runtime — they're erased during compilation — they exist purely to catch mistakes before the code runs, which is exactly what tsc --noEmit (used throughout this project's CI) does: type-check without even producing output, purely as a correctness gate.

Node.js + Fastify

The API (apps/api) runs on Node.js, using Fastify as the HTTP framework.

Why Fastify over Express

Fastify was designed from the ground up around JSON Schema-based request/response validation and a plugin architecture with explicit encapsulation, both of which matter more as an API surface grows past a handful of routes. It's also meaningfully faster in real benchmarks (schema-compiled serialization instead of generic JSON.stringify), though for an app at this project's actual traffic scale, that's a secondary benefit next to the developer-experience one: Fastify's plugin (app.register(...)) model is what makes it natural to compose the exact set of concerns this API needs — CORS, cookies, rate limiting, multipart uploads — each as an isolated, independently reasoned-about piece (see app.ts).

Table stakes for the API layer, concretely:

  • @fastify/cors — origin allowlisting (any localhost port in dev, a pinned WEB_ORIGIN in production, plus chrome-extension:/// moz-extension:// for the browser extension).
  • @fastify/cookie — the refresh-token cookie.
  • @fastify/rate-limit — an in-memory, per-route configurable limiter (tighter on genuinely expensive routes like /api/tts and /api/auth/* than the general default).
  • @fastify/multipart — PDF/EPUB file uploads.

PostgreSQL + Prisma

The database is PostgreSQL, accessed exclusively through Prisma — never a raw SQL query string anywhere in the codebase.

Why an ORM at all

Prisma's schema file (apps/api/prisma/schema.prisma) is the single source of truth for the data model, and it generates a fully-typed client from it — a query for Article rows is typed against the actual current schema, not a hand-maintained interface that can drift out of sync with the real database. Migrations are generated from schema diffs (prisma migrate dev) rather than hand-written, which matters more the longer a project lives: this schema is already many migrations deep (see apps/api/prisma/migrations/), each one a real, reviewable diff instead of a hand-rolled ALTER TABLE someone has to get exactly right.

What an ORM is, for a beginner: "Object-Relational Mapping" — a library that lets you query a relational (table-based) database using the target language's own objects/functions instead of writing raw SQL strings by hand. prisma.article.findMany({ where: { userId } }) instead of SELECT * FROM "Article" WHERE "userId" = $1. The tradeoff is a layer of abstraction between you and the actual SQL being run — worth it here because of the typed-schema guarantee above, but it's still worth understanding what SQL an ORM call actually compiles to when performance matters (see the query-level omit optimization in Search for a real example of a performance decision made because the underlying query was understood, not despite the ORM hiding it).

The local dev database: PGlite

Running Postgres locally usually means installing it or running Docker. This project ships a zero-install alternative: PGlite, a WASM-compiled Postgres that runs as a real, Postgres-wire-protocol-speaking server (apps/api/scripts/dev-db.ts) on localhost:5432, persisting to a local data directory. It's genuinely real Postgres underneath (not a mock or a compatible-but-different engine) — the tradeoff is that Prisma's own migration engine doesn't reliably speak to it, so schema changes go through a separate script (migrate:pglite) that applies migrations via the plain pg driver instead.

Next.js + React

The web app is Next.js (App Router) with React 19.

Why Next.js specifically

Nearly the entire app is client-rendered in practice — the reader, the library, TTS playback, all of it runs in the browser, often against IndexedDB with no server round-trip at all. What Next.js buys here isn't server-rendering every page; it's the file-based App Router (routes as folders, layouts that compose naturally — see how app/layout.tsx mounts the global TTS player once, at the root, so it survives client-side navigation between pages), first-class TypeScript support, and next/dynamic for code-splitting heavy, conditionally-needed libraries (pdf.js and epub.js are only loaded when a PDF/EPUB reader actually mounts, not on every page load — see the Roads Not Taken entry on this).

Tailwind CSS

Styling is Tailwind CSS v4, utility-first — no CSS-in-JS, no separate stylesheet per component. Theming (light/dark/sepia/ Kindle) is layered on top via CSS custom properties defined once in globals.css (--color-paper, --color-accent, etc.), which Tailwind's utilities then reference — so bg-paper or text-ink automatically repaint correctly under every theme without any component needing to know which theme is active.

pnpm Workspaces + Turborepo

Package management is pnpm, in workspace mode (pnpm-workspace.yaml) — every app and package in the monorepo shares one node_modules install, with real workspace-local dependencies (@booklet/shared: "workspace:*") resolving to the actual local source, not a published version.

Why pnpm over npm/yarn

pnpm's content-addressable store means a dependency installed once on disk is hard-linked into every project that needs it, rather than duplicated per-project the way npm/yarn classic do — meaningfully faster installs and far less disk usage in a multi-app monorepo where every app depends on things like typescript or react independently.

Turborepo sits on top as a task runner with real caching — turbo.json defines the build/typecheck/lint/test pipeline, with dependency ordering (^build means "this package's own workspace dependencies must build first") and content-hash-based caching, so re-running a check against unchanged code replays the cached result instead of redoing the work.

A real measurement

Confirmed by hand: a repeated pnpm typecheck across all five packages with no code changes goes from several seconds (real, from-scratch tsc --noEmit runs) to about 30 milliseconds ("FULL TURBO", every package a cache hit). This was added specifically because the monorepo had zero task caching before — every pnpm build/typecheck/ test/lint always did full work regardless of what actually changed.

Vitest + Playwright

Unit and integration tests run on Vitest (fast, native-ESM, Jest-compatible API). End-to-end tests run on Playwright, driving a real Chromium browser against the real running app — see Testing Philosophy for how these are actually used, which is more specific than "unit tests for logic, e2e for UI."

IndexedDB

The local/anonymous mode's storage engine is IndexedDB — the browser's own built-in, transactional, structured-object database (not localStorage, which is synchronous, string-only, and far too small for a whole reading library). Accessed through a thin wrapper (apps/web/src/lib/local/db.ts) that gives the rest of the app the same repository-style interface the server-backed mode uses — see The Offline-First Model.

Part IVThe Data Model

The full schema lives in apps/api/prisma/schema.prisma, and — unusually for a schema file — it's already extensively commented with the real reasoning behind nearly every field. What follows is a guided tour, not a duplicate of that file; read the schema itself for the complete, current source of truth.

User

The account itself. passwordHash is nullable — an OAuth-only user (Google/GitHub) never gets a random password they'd never know; login-by-password just isn't offered for that account. Holds the resurfacing preferences (resurfaceFrequency, highlightsPerDigest) directly, since they're genuinely account-level settings, not per-device ones.

Article

The center of the schema. One row per saved item, regardless of sourceType (HTML/PDF/ EPUB/BOOK — BOOK being the special case for a Kindle-clippings import with highlights but no actual content, see Import/Export). Two duplicate-detection fields exist side by side on purpose: url (exactly what was saved) and canonicalUrl (tracking params stripped, host/ trailing-slash normalized) — an exact-string check alone would miss a tracking-param or AMP-link variant of something already saved.

Why extractedHtml and extractedText are separate columns

extractedHtml is HTML-only (what the reader actually renders for an HTML-sourced article). extractedText is populated for every source type (HTML/PDF/EPUB alike) — the plain-text form used for full-text search and the reading-time estimate, and, for PDF/EPUB, the only text representation that exists at all (their real content renders via pdfjs-dist/epub.js directly from the uploaded file, not from this column). Both are large enough to matter: see Search for the real, measured cost of fetching them for rows that don't need them, and the fix.

Highlight

position is a discriminated JSON blob, not a fixed set of columns — its shape depends on the article's source type: a W3C TextQuote+TextPosition-style selector for HTML, page number + rects for PDF, an EPUB CFI (Canonical Fragment Identifier) range for EPUB. See The Reader & Highlight Anchoring for what each of those actually means and how they're resolved back to real DOM ranges.

The SM-2 fields (easinessFactor, intervalDays, repetitions, nextDueAt) live directly on the highlight row — see Resurfacing for the algorithm itself.

Collection

Self-referential (parentId/children) for nested, folder-style organization, with onDelete: SetNull rather than Cascade — deleting a parent collection shouldn't take its children down with it; they just become top-level. A filter JSON column (status/tags/text query) makes a collection smart when set: membership is computed live from Article at read time instead of being a fixed list of ArticleCollection join rows.

ApiToken / Webhook / WebhookDelivery

The public-API surface's own tables — see The Public API. Notably, only tokenHash is ever stored for a personal access token (the same hash-not-plaintext pattern used for refresh tokens and password-reset links elsewhere in the schema) — the raw token is shown exactly once, at creation, and can never be retrieved again.

Part VFeature Deep Dives

Authentication & Sessions

Auth supports email/password and OAuth (Google + GitHub) — and every single one of those methods, email/password included, is entirely optional. Every route works signed out; OAuth buttons only even appear once a provider's credentials are actually configured in the environment.

The token scheme is short-lived JWT access tokens plus a longer- lived, revocable refresh token:

  • Access token — a signed JWT, 15-minute lifetime, sent as a bearer token on every authenticated request. Stateless: verifying it is just a signature check, no database round-trip.
  • Refresh token — a random opaque string, 30-day lifetime, stored in an httpOnly cookie. Only its hash is stored server-side (in Session.refreshTokenHash) — a database read alone is never enough to forge a session.
Why this split instead of one long-lived token

A single long-lived token would need to be stateless (for performance) or revocable (for security) — it can't cleanly be both. Splitting the two means the access token can stay fast and stateless (no DB hit per request) while the refresh token — the thing that actually matters for "can this device still get in" — is a real, revocable database row. "Log out" and "log out other devices" are just deleting/marking that row, and a stolen access token is only useful for 15 minutes.

Article Extraction

Four real input shapes, one unifying idea: extraction is a stateless operation, decoupled from persistence, so the exact same code path serves both signed-in and local/anonymous saves.

The Reader & Highlight Anchoring

Three real renderers, one per source type, each anchoring highlights differently because each source has a fundamentally different notion of "position":

  • HTML — rendered as sanitized HTML directly; highlights anchor via a text-offset scheme resolved against the article's own plain-text extraction, with drift-tolerant re-anchoring (a highlight survives minor re-extraction changes by searching nearby, not just an exact offset match).
  • PDF — rendered via pdfjs-dist: real canvas output for the visible page, plus an invisible, precisely-positioned text layer on top for native text selection. Highlights anchor by page number + rectangles in PDF user-space units — genuinely real coordinates, not a text offset, so they never drift.
  • EPUB — rendered via epub.js, paginated, each chapter in its own iframe. Highlights anchor by CFI (Canonical Fragment Identifier) range — EPUB's own standard way of pointing at a specific location inside a specific document within the book.
Why real rendering instead of just showing extracted text everywhere

Flattening a PDF or EPUB to plain text and re-flowing it is simpler to build, but it throws away real information — page numbers a citation might reference, an EPUB's own typography and layout, image placement. Rendering the real thing means highlights can anchor to genuinely stable coordinates (a PDF rect, an EPUB CFI) instead of a text offset that has to survive re-extraction.

OCR

A scanned PDF with an empty or near-empty native text layer automatically falls back to Tesseract.js — no toggle, no "try OCR" button, no API key, and no external service: it's a real WASM OCR engine running in-process on the server. Capped at 20 pages (it runs synchronously inside the upload request), and the reader shows a visible "may contain recognition errors" notice, since Tesseract's real-world error rate is meaningfully higher than a native text layer or Readability extraction.

Text-to-Speech — the Full Story

This is the single most-iterated-on feature in the project's history, and the one with the richest, most concrete record of real measurement driving real architecture changes. It's worth walking through in full, including the parts that got thrown away, because the reasoning at each step is exactly the kind of thing this document exists to preserve.

The model: Kokoro

Speech is generated by Kokoro, an open-weight (Apache-2.0), 82-million-parameter TTS model, via the kokoro-js library on top of ONNX Runtime. The alternative that's always on — needing zero setup, zero model, zero network — is the browser's own native SpeechSynthesis API, kept as a real first-class option in the same voice picker, not just a fallback.

Chapter 1 — Client-side WASM (rejected)

The original implementation ran Kokoro entirely in the browser, over WASM (and, briefly, WebGPU where available). It worked — the voice quality was never in question — but per-sentence generation was measured at a genuine 12-18 seconds, and no amount of client-side engineering closed that gap: not Worker-based pipelining, not quantization, not multi-threading. The WASM sandbox's per-token inference cost turned out to be a hard ceiling, not a configuration problem.

Chapter 2 — Moving generation server-side

The actual unlock was almost embarrassingly simple once tested directly: kokoro-js auto-detects a real Node.js environment and switches to onnxruntime-node — the native, compiled ONNX Runtime binary — instead of the WASM sandbox onnxruntime-web is stuck with in a browser. Confirmed by hand, same model, same voice, same sentence, same machine: ~4.7 seconds instead of 12-18. A real 2.5-3.8x improvement from switching where the exact same code runs, not a config tweak.

Why this was a deliberate exception to "everything works offline"

Moving generation server-side is a genuine departure from this project's default architecture (OCR, extraction, and everything else run entirely client-side/in-process with no server-only dependency). It was accepted explicitly, after the WASM ceiling had been thoroughly explored and confirmed real — not as a first resort.

Chapter 3 — The pause between sentences, and the worker-process pool

Server-side generation alone wasn't enough: a single Kokoro generation call regularly took longer than the resulting audio's own playback duration (measured: up to 9.8 seconds to generate 5.95 seconds of audio). Worse, concurrent requests to a single process serialized — two requests at once took roughly twice as long as one, not the same. No amount of client-side prefetching can outrun a server that's slower than real-time on average; the shortfall just compounds, sentence after sentence, into exactly the growing dead air users actually experienced.

The fix is a small pool of real child processes (apps/api/src/services/tts-pool.ts), each holding its own Kokoro model instance, so multiple chunks generate at genuinely the same wall-clock time. Confirmed by hand: 3 concurrent generations finish in about the same time as 1, not 3x.

A real, hard-won bug: worker_threads crash

The first attempt used Node's built-in worker_threads, not separate processes — cheaper to spawn, no IPC overhead. It crashed the entire Node process the instant generate() ran inside a worker thread, even though loading the model there worked fine. onnxruntime-node's native binding simply isn't safe to run inside a worker_thread on this platform. Real, separate OS processes sidestep the issue entirely — each is just another independent node invocation, exactly like the main server itself, which already worked.

On the client, tts-player-provider.tsx keeps a sliding window of chunks prefetched (matching the pool's size, not just one chunk ahead) so every worker stays busy. The first chunk also gets a much smaller character cap (80 vs. the normal 140) than every chunk after it — nothing can overlap with the very first chunk's generation time, since there's no previous chunk playing yet to hide behind, so only that one pays for a faster start.

The measured result

Real inter-chunk gap after all of the above: 1-2 milliseconds, down from multi-second dead air.

Chapter 4 — The global player, and read-along

Playback moved from a per-page hook to a provider mounted once at the root layout (tts-player-provider.tsx), so it survives navigating away from the article — a persistent, Spotify-style "now playing" bar, not a control that dies the moment you leave the page.

Read-along highlighting tracks the currently-spoken word, not just the current sentence. Kokoro emits no real per-word timestamps, so this is a deliberate estimate: each word's on-screen moment is computed from its proportional share of the chunk's own character length against live playback position (audioEl.currentTime / audioEl.duration). A real bug in this estimate — the highlight jumping to the chunk's last word on every inter-word gap, due to an Array#find() fallback landing on the wrong index — was found and fixed by actually reasoning through what happens in the gap between two words, not just the estimate's average-case accuracy. See Roads Not Taken for why real per-word timing isn't available at all.

A separate, coarser indicator — a left-edge bar on whichever paragraph is currently being read — moves once per chunk rather than per word, giving a steady anchor even while the word cursor is still catching up mid-sentence.

Chapter 5 — Voice curation

Kokoro ships 28 voices; the picker originally offered 13 (every voice the model's own bundled quality grades rated C or better). In practice, six of those were American-female voices sitting in the same quality band right next to each other — technically fine individually, but it read as "the same voice, over and over," not real variety. The list was cut to 7: the single strongest, most differentiated voice per real gender/accent/character combination, with labels describing actual character ("Fenrir — deep & gravelly") instead of just accent and gender.

Chapter 6 — Time to first audio, and the limit of making it faster

Every chapter above is about the gap between chunks. The remaining problem was the gap before the first one: the wait between pressing "Read aloud" and hearing a word. That number has its own name here — TTFA, time to first audio — and it's the one a user actually experiences as "is this app fast."

The investigation started by establishing the ceiling, which turned out to settle the entire design question: Kokoro on CPU generates at roughly 1-2× realtime. An 80-character first chunk is about five seconds of speech, so producing it genuinely costs two-and-a-half to five seconds. ONNX Runtime session tuning, a different quantization, a bigger pool — none of these change that by more than about 2×. Generation cannot be made negligible on a CPU.

The reframing that made the problem solvable

If generation can't be fast enough, then the audio has to already exist before it's asked for. A cache hit costs one network round trip — on the order of 50-150ms. That is not a consolation prize: it's faster than the commercial streaming TTS APIs (Cartesia's real-world median is ~188ms, ElevenLabs Flash ~288ms), so a self-hosted model with warm audio in front of it is the lowest-latency option available, not a compromise for staying open-source.

Which means the work isn't "make the model faster." It's: make the cache hit the common case, and make the fixed overheads around it disappear.

Warming the opening on reader open

Opening an article now starts generating its beginning before anyone asks for it. Chunk one is fetched and held by the player client-side; chunks two and three are generated into the server's cache via a dedicated POST /api/tts/warm that returns 202 immediately without sending any audio back.

The split is deliberate. The player needs chunk one in hand to start instantly, but chunks two and three only need to be cache hits by the time playback reaches them — several seconds later. Fetching them up front would mean a reader who opens an article and never presses play has downloaded most of a megabyte of audio for nothing. It also means the fragile one-shot logic that adopts a warmed chunk at play time never had to learn about multiple indices.

Two extra chunks, specifically, because the pool has exactly three workers: chunk one's real fetch plus these two fill it once, so all three finish in roughly the wall-clock time of a single generation. Warming more would queue behind them and delay the only chunk whose timing anyone can perceive.

Why speculative work can't hurt

The pool gained a second, low-priority queue, drained only when the normal one is empty. Warming enqueues there. This is what makes speculation safe to be generous with — it can only ever consume capacity that would otherwise sit idle, and can never push back a chunk somebody is actually waiting on. Without the split, speculating would sometimes make the very thing it was speculating about slower.

A cache that survives the thing that kept emptying it

The generated-speech cache was in-process only: lost on every restart and every deploy, and not shared between instances. Since generation costs seconds and a hit costs milliseconds, that restart cliff was the largest remaining source of slow starts — the first person to read anything after a release paid full price again for audio the previous instance had already produced.

There are now two tiers: the existing in-memory LRU as L1, and an optional Redis as L2 behind it. L1 stays in front because a Redis round trip, while far cheaper than generating, isn't free, and one listening session asks the same process for the same chunks repeatedly.

A cache is only worth having if it's reliably faster than the thing it caches

This is the part that's easy to get wrong. A Redis that is slow, or down, or reachable-but-unresponsive must never make a request slower than simply generating would have been. Two mechanisms enforce that, and both are load-bearing rather than defensive decoration: every read races a 150ms timeout (past which it's abandoned and treated as a miss), and a circuit breaker skips Redis entirely for 30 seconds after any failure. Without the breaker, a down Redis makes every subsequent request pay the connect timeout before falling through — converting the cache into a pure latency tax at exactly the moment it's providing no value.

Redis stays genuinely optional, in the same sense as RESEND_API_KEY and SENTRY_DSN: with no REDIS_URL set, every L2 call is a no-op and behavior is byte-identical to the single-tier version.

Two chunker bugs that were quietly costing seconds

The 80-character first-chunk cap exists entirely to bound TTFA. It turned out chunk one routinely ignored it, in two separate ways:

  • The hard-wrap loop measured against the 320-character hard-wrap threshold rather than the current cap, so a long opening sentence produced a ~320-character chunk one — four times the intended budget.
  • The accumulator only ever flushed before appending a sentence and never split one, so any single opening sentence between 80 and 320 characters became an unsplit chunk one.

Both are now governed by the real cap. Splitting an opening sentence costs one clause-boundary seam (the wrap logic prefers commas and semicolons, so it reads as an ordinary breath) — a deliberate trade made for chunk one only. Every later sentence still keeps the whole-sentence prosody guarantee that HARD_WRAP_MAX_CHARS exists to protect.

The fixed overheads
OverheadFix
Every chunk request paid a CORS preflight round trip — /api/tts is a JSON POST with credentials, so never a "simple" request, and with no Access-Control-Max-Age the browser re-preflighted every ~5 seconds. Set maxAge. One line, directly in front of chunk one.
Audio shipped as 32-bit float WAV at 24kHz — 96KB per second of speech. Transcode to 16-bit PCM. Halves the bytes over IPC, in both cache tiers, and on the wire, with no audible difference for speech.
Duplicate generation. Nothing is written to the cache until the first request finishes, so concurrent identical requests all missed and all occupied a worker — and warming plus the play loop race for the same chunks by design. An in-flight map keyed identically to the cache, so the second caller rides along on the first. It wraps the L2 lookup too, or the duplicates would each still pay their own Redis round trip.
Chunking ran over the entire article at least twice per play, synchronously on the main thread — and again on every re-render that re-fired the warm effect. A single-entry memo, plus moving the warm path's identity check to before chunking instead of after, so the common no-op case costs nothing.
Two ship blockers found on the way, neither of them about speed

Fastify ran without trustProxy. @fastify/rate-limit keys on request.ip, which behind any reverse proxy — Fly, Railway, Render, nginx, Cloudflare, i.e. every real deployment — resolves to the proxy's address. Every user in the world would have shared a single rate-limit bucket, and read-aloud would have stopped working for everyone within minutes of real traffic. It's invisible locally and in docker-compose, because neither has a proxy in front. Now opt-in via TRUST_PROXY, because trusting X-Forwarded-For with nothing in front to overwrite it is its own hole.

The TTS rate limit was an order of magnitude too low. 60 requests per 10 minutes covers about 8,400 characters — a normal article exhausted it mid-playback, and the client's failure path caught the 429 and silently went idle, so playback just stopped with no explanation. Raised, and failures now surface as a toast instead of silence.

Finally, none of this was measurable from the client before: the only signal was a spinner. There's now real instrumentation — User Timing marks around warm-issued, play-clicked, first-bytes, and first-audible, with the last few runs kept on window.__ttsMetrics and a summary logged when localStorage["booklet:tts-debug"] is set. The server-side benchmark (apps/api/scripts/bench-tts-ttfa.ts) covers generation, cache tiers, and de-duplication, but it never sees CORS, transfer, or audio-element decode — which is exactly why the browser-side numbers have to exist too.

Resurfacing (SM-2)

SM-2 (SuperMemo 2, Wozniak 1987) is the actual algorithm, not a from-scratch approximation of one. Every review has a quality score on a 0-5 scale; this app's UI only ever collects a binary "Remembered" / "Forgot," mapped to quality 4 or 2 respectively (feedbackToQuality in packages/shared/src/resurface.ts). 

// The core update, simplified from resurface.ts:
if (quality < 3) {
  repetitions = 0;
  intervalDays = 1;                          // a miss resets the streak
} else {
  if (repetitions === 0) intervalDays = 1;
  else if (repetitions === 1) intervalDays = 6;
  else intervalDays = round(intervalDays * easinessFactor);
  repetitions += 1;
}
easinessFactor = max(1.3, easinessFactor + /* quality-based nudge */);

A recalled highlight's next-due interval grows (1 day → 6 days → previous interval × its own easiness factor, which itself nudges up or down based on how easy that specific recall felt); a missed one resets to a 1-day interval. This state (easinessFactor/intervalDays/ repetitions/nextDueAt) lives directly on the Highlight row.

Why real SM-2 instead of a simpler heuristic

An earlier version of this feature used weighted-random selection — "show me something plausible." Real SM-2 scheduling replaced it specifically because "resurface" should mean "show me what's actually due for review," a claim only a real spaced-repetition algorithm can back up.

Digests (a resurfacing batch) are generated and persisted per the user's DAILY/WEEKLY frequency preference, then reused — not re-rolled on every visit to the page, which would make "what am I reviewing today" a moving target.

Search

Plain, case-insensitive contains matching across title/excerpt/author/site/body-text/tags — deliberately not Postgres tsvector/GIN full-text search, so signed-in and local/anonymous mode behave identically (IndexedDB has no full-text index at all to match against). This is a real, consciously-accepted tradeoff for consistency over raw search quality, revisitable if it stops being true at the scale this project actually operates at (one person's library, not a multi-tenant search product).

A real, measured query-level fix

The list/search endpoints originally fetched every matching row's full extractedHtml/extractedText from Postgres, then stripped them out of the response shape a moment later — real, wasted database I/O and serialization cost on every request, scaling with exactly what a large library has the most of. Fixed with Prisma's omit at the query level, so those columns are never fetched for a list view in the first place — not a caching fix, a query-shape fix.

Collections

Nested (nested via parentId, folder-style) and smart (membership computed live from a stored filter — see the schema). Deliberately never combined in the UI (the app never offers nesting a smart collection under another), though that constraint isn't hard-enforced at the schema level — a conscious scope decision, not an oversight, to keep that migration small.

Import / Export

Import: Pocket/Instapaper CSV, browser bookmarks, and a real Kindle My Clippings.txt parse — one BOOK- sourced article per book, with every highlight and note attached, even though there's no actual book content to render (see the schema's SourceType.BOOK). Export: Markdown (for Obsidian/Notion/Logseq) and Anki flashcards.

The Public API

/api/v1 is a deliberately separate, versioned surface from the internal routes the web app itself uses — the same integration surface a much bigger product would ship, kept decoupled specifically so a frontend refactor can't silently break someone's external script. Personal access tokens are read- or read+write-scoped, shown once at creation. Webhooks deliver HMAC-SHA256-signed payloads on article.created/ highlight.created, with a visible delivery-history log (the last ~20 attempts, status code, success/failure) — a webhook that's silently failing forever is worse than not having the feature at all.

Browser Extension

Manifest V3, one manifest serving both Chrome and Firefox. Save the current page from the toolbar icon or a right-click context menu; the "Open in Booklet" flow lets highlighting happen on the live web page itself, with the article and its highlights sent to Booklet together.

Mobile App

Expo / React Native, local-first the same way the web app is (AsyncStorage instead of IndexedDB, behind the same repository- pattern seam). Highlighting is a toggled select-then-highlight flow rather than a live text selection — React Native has no single component that both reports a text selection and renders per-range styling the way a browser's own selection API does. PDF/EPUB upload works as extracted text only; real page/CFI rendering would need a WebView bridge to reuse the web app's pdfjs-dist/epub.js code, or a native renderer — real future work, not a scaffold-stage gap.

Part VITesting Philosophy

Three layers, each answering a different question:

  • Unit (Vitest, packages/shared) — pure logic with no I/O: the SM-2 algorithm, highlight-anchor resolution, URL canonicalization, collection filters, Kindle- clippings parsing. Fast, deterministic, no database.
  • Integration (Vitest, apps/api) — the full API surface exercised through Fastify's own .inject() — real route handlers, real Prisma queries against a real (test) Postgres, no HTTP server actually listening on a socket.
  • End-to-end (Playwright, apps/web) — a real Chromium browser driving the real running app: real PDF canvas rendering, real EPUB iframe pagination, real cross-iframe text selection, real Kokoro model generation (not mocked) for the TTS suite.
Why real generation instead of mocking TTS in e2e tests

A mocked TTS response can't catch the class of bug this feature has actually had — real generation timing, a real chunking edge case that exploded one article into 2,283 requests, a real WebGPU-adapter-detection failure. The e2e suite accepts a genuinely longer timeout for these tests specifically because what they're verifying only exists if the real thing runs.

A recurring pattern throughout this project's real debugging history, worth naming explicitly: when a test fails in a way that's hard to explain, the discipline has consistently been to reproduce it in isolation with a minimal script — a raw Node http client bypassing the browser's fetch() entirely, a patched Audio constructor to trace real playback events, a git-stash-isolated re-run to prove a failure predates a specific change — rather than guessing from the failure message alone.

Part VIICI/CD & Deployment

.github/workflows/ci.yml runs on every push/PR: typecheck + lint for every package, the shared/api/web test suites (API and web e2e against a real Postgres service container), the extension's e2e suite under xvfb (a virtual display, since a real browser extension needs a real browser window even in headless CI), and a docker-build job that builds both production images and smoke-tests the API image against a real Postgres container.

Deployment itself (see DEPLOYMENT.md) is Docker-based — a Dockerfile per app, verified by CI's own build-and-smoke-test, but not yet pointed at a real production host (no cloud account exists in this project's own development environment).

The API image bakes Kokoro's ONNX weights in at build time. Without that, the ~90MB model downloads from Hugging Face on the first read-aloud in every fresh container — three times over, since the pool starts three processes that all cold-miss at once — making the first request after a deploy a 10-60 second wait and putting a core feature at the mercy of a third party being reachable at request time.

Don't "fix" the model cache with an environment variable

The installed @huggingface/transformers reads no cache environment variables at all — not HF_HOME, not TRANSFORMERS_CACHE, not HF_HUB_CACHE. Verified against its own env.js, which hardcodes the path and allows overriding it only programmatically via env.cacheDir. It caches into node_modules, which the runtime stage copies wholesale — so running the prefetch during the build is sufficient on its own, and adding an ENV HF_HOME would be silently ignored.

Production-sizing and safety knobs:

VariableWhat it's for
TRUST_PROXY Set to true if — and only if — a reverse proxy you control sits in front. Rate limiting keys on the client IP; without this, behind a proxy, that resolves to the proxy and every user shares one bucket. With nothing in front, leaving it unset is what stops clients spoofing X-Forwarded-For. Invisible in local dev and docker-compose, so test it against the real deployment.
TTS_POOL_SIZE (default 3) Worker processes, each holding a real model instance in memory for its whole lifetime — a genuine memory/CPU tradeoff to size against the host's headroom.
REDIS_URL Optional shared, persistent cache for generated speech. Without it the app uses only its in-process cache. Set maxmemory and allkeys-lru on the Redis itself — these entries are pure cache with a long TTL, so the right behavior under pressure is evicting the coldest, not Redis's default of refusing writes.
TTS_REDIS_TTL_DAYS (default 30) How long cached audio survives unread; refreshed on every hit.
TTS_RATE_LIMIT_MAX (default 600 in production) Requests per IP per 10 minutes against /api/tts — roughly 80 minutes of generated audio. Read together with TRUST_PROXY: set that wrong and no value here is large enough.
TTS_CACHE_MAX_MB (default 200) In-process cache ceiling, evicted LRU.

Part VIIIGlossary

Monorepo
One version-controlled repository containing multiple, separately-deployable projects (here: an API, a web app, a browser extension, a mobile app, and a shared library) — as opposed to each living in its own repository ("polyrepo").
ORM (Object-Relational Mapping)
A library that lets you query a relational database using the host language's own objects/functions instead of hand-written SQL strings. This project's ORM is Prisma.
JWT (JSON Web Token)
A compact, cryptographically-signed token format for representing claims (like "this is user X, issued at time Y, expires at time Z"). Verifying one is just a signature check — no database lookup required, which is what "stateless" means here.
SSR / CSR
Server-Side Rendering (HTML generated on the server per request) vs. Client-Side Rendering (an empty shell shipped to the browser, which then builds the page via JavaScript). This app is overwhelmingly client-rendered in practice, even though it's built on a framework (Next.js) capable of both.
CFI (Canonical Fragment Identifier)
The EPUB standard's own way of pointing at a precise location inside a specific document within a book — the EPUB equivalent of a URL fragment, and what this app anchors EPUB highlights to.
Spaced repetition
A learning technique where review intervals grow over time for things you consistently recall correctly, and shrink (reset) for things you don't — the idea behind flashcard apps like Anki, and the model this app's "resurfacing" feature is built on via the real SM-2 algorithm.
WASM (WebAssembly)
A binary instruction format that runs in browsers (and standalone runtimes) at near-native speed, used here for in-browser OCR (Tesseract.js) and as the fallback execution path for TTS inference before it moved server-side.
ONNX Runtime
A cross-platform engine for running trained ML models. onnxruntime-web runs inside a WASM sandbox in the browser; onnxruntime-node runs as real native code in Node.js — the latter is measurably faster, which is the entire reason Kokoro TTS generation moved server-side.
Worker thread vs. child process
Both let Node.js run code concurrently. A worker thread shares the same OS process (cheaper, but shares certain native-binding constraints); a child process is a fully separate, independent process (more overhead, but fully isolated) — this project uses real child processes for TTS generation specifically because a native binding (onnxruntime-node) was confirmed to crash inside a worker thread.
SM-2
SuperMemo 2, a 1987 spaced-repetition scheduling algorithm by Piotr Wozniak — see Resurfacing.
TTFA (time to first audio)
The wait between pressing "Read aloud" and hearing the first word. Distinct from throughput or the gap between chunks: it's the one latency a user directly experiences as the feature being fast or slow, and the thing Chapter 6 is entirely about.
Realtime factor
How fast a speech model generates relative to the duration of the audio it produces. 1× realtime means one second of synthesis per second of speech; 2× means half that. Kokoro on CPU runs at roughly 1-2×, which is the constraint that shaped the whole caching architecture — below about 10×, generating on demand can never feel instant.
CORS preflight
An automatic OPTIONS request a browser sends before certain cross-origin requests (anything that isn't a "simple" GET/POST — including any JSON POST) to ask the server whether the real request is allowed. It costs a full extra round trip, and without an Access-Control-Max-Age the result is cached for only a few seconds, so it repeats constantly.
Circuit breaker
A pattern where repeated failures against a dependency cause it to be skipped outright for a cooling-off period, rather than every request continuing to pay a timeout to rediscover it's down. Used here so a degraded Redis can never make TTS slower than having no cache at all.
L1 / L2 cache
Tiers of a layered cache, borrowed from CPU terminology: L1 is smaller and closer (here, in the server process's own memory), L2 is larger and slightly further away (here, Redis over the network). A miss in L1 falls through to L2; a hit in L2 is promoted into L1.

Part IXRoads Not Taken

A dedicated index of real ideas that were tried, measured, and deliberately reversed or rejected — preserved here specifically so the same dead end doesn't get walked into twice.

Client-side WASM/WebGPU TTS

Zero server cost, but a hard ~12-18s-per-sentence ceiling that Worker-based pipelining, quantization, and multi-threading all failed to close. Replaced by server-side generation once the real, measured speedup (onnxruntime-node vs. onnxruntime-web) was confirmed. See the full TTS story.

worker_threads for the TTS pool

Cheaper than real child processes, and the obvious first choice — but onnxruntime-node's native binding crashes the whole Node process the instant generate() runs inside one, confirmed by hand. Real, separate OS processes sidestep the issue entirely.

Redis — rejected, then adopted

The original rejection: explored in response to a real question ("would this fix our latency issues?"). It wouldn't have — every reported slowness at the time was either real model-generation latency or an actual logic bug in a specific code path, not a caching-shaped problem. Adding it would have meant real infrastructure complexity, and a departure from this app's "nothing external required" architecture, for no concrete win. The entry closed by naming the conditions under which to revisit: horizontal scaling, or repeated TTS requests becoming common enough to cache.

What changed: the second condition arrived, from an unexpected direction. Once the time-to-first-audio work established that Kokoro on CPU simply cannot generate fast enough to matter (see Chapter 6), the cache stopped being an optimization and became the mechanism — the only way for playback to start quickly is for the audio to already exist. And the in-process cache's real weakness turned out not to be capacity but lifetime: it was wiped by every restart and every deploy, so the first reader after a release always paid full price for audio that had already been generated.

Adopted as a second tier behind the existing in-memory cache, not as a replacement, and strictly optional — with no REDIS_URL the app behaves exactly as it did before. The "nothing external required" principle is intact; what's new is that something external can now make it better.

The lesson worth keeping: the original rejection was correct and the reversal was correct. What made the reversal cheap was that the first entry wrote down its own revisit conditions instead of just saying no.

Real per-word TTS timestamps

Would be strictly better than the character-proportional estimate the read-along feature actually uses — but confirmed by reading kokoro-js's own type definitions: generate() returns only raw audio samples, and even its streaming API exposes phonemes as an untimed string, not per-word timing data. Not available from this model/library without a substantially bigger undertaking (a separate forced-alignment pass against the generated audio), which wasn't judged worth the cost against the estimate's real accuracy once its own logic bug — see Chapter 4 — was fixed.

A commercial streaming TTS API (Cartesia, ElevenLabs, Deepgram)

The obvious answer to "make read-aloud start instantly," and the one that turns out to be worse on the metric it would be bought for. Their best-case figures (~40-90ms) are marketing numbers; real-world medians land around 188ms (Cartesia Sonic) to 288ms (ElevenLabs Flash). A warm cache hit from this app's own server is 50-150ms — faster, free, and with no per-character billing or hard third-party dependency for a core feature. Rejected on measurement, not principle, which is the useful part: self-hosting isn't costing anything here.

GPU inference (CUDA execution provider)

onnxruntime-node already ships the CUDA and TensorRT providers — the repo simply never passes a device, so it always runs on CPU. Wiring it up would genuinely deliver 10-30× and make even uncached generation sub-second. Not taken because it requires deploying the API to a GPU host, which is a real recurring cost for a personal-scale reading app, and because warming plus caching gets TTFA to a network round trip without it. This is the right lever if the app ever serves enough simultaneous readers that cache misses stop being rare.

ONNX Runtime session tuning

The repo passes no session options at all, which means each of the three worker processes spins up a thread pool sized to the whole machine — roughly 3× CPU oversubscription on a small host. Genuinely real, and worth perhaps 2×. Deliberately deferred: 2× on a path that caching removes entirely isn't worth the regression risk immediately before shipping. Revisit together with the dtype question — q8 is hardcoded, and q8 is not reliably faster than fp32 for this model shape on CPU, so that deserves a real benchmark rather than an assumption.

Opus/MP3 audio instead of WAV

Would be 10-20× smaller than even the 16-bit PCM the server now sends. Rejected for now because it needs a native or WASM encoder dependency plus a container format, adds 50-150ms of server CPU on the critical path, and its benefit only materializes on slow connections and only for the first chunk (later chunks hide behind playback). The 32-bit float → 16-bit PCM change captured the free half of this win with no new dependency.

A GET TTS route with a content hash, for real HTTP caching

A GET with no custom headers is a "simple" request — it would skip the CORS preflight entirely and become genuinely HTTP-cacheable with immutable, max-age, unlike the current POST. Rejected because it puts the text of whatever the user is reading into URLs, where it lands in server access logs, any intermediate proxy's logs, and browser history. That's a bad trade for a reading app. The preflight cost was solved with maxAge instead, and a client-side IndexedDB audio cache is the better route to zero-byte replays if that's ever needed.

Postgres full-text search (tsvector/GIN)

Would give relevance-ranked results, real stemming, etc. — not used because local/anonymous mode has no equivalent full-text index over IndexedDB, and giving signed-in users meaningfully better search than signed-out users contradicts this app's "everything behaves the same either way" principle. Revisit if that principle is ever consciously relaxed, or at a scale where plain contains matching genuinely stops being adequate.

epub.js spread mode (side-by-side pages)

epub.js's default "auto" spread pairs two spine items side by side above its own width threshold — a real, physical-book-style feature, but this reader has no two-page visual layout at any width to begin with, and the pairing behavior at a book's very first spine item (the cover, with nothing yet to pair it with) turned out to be the actual cause of a real "cover shows up twice" bug. Forced off (spread: "none") entirely.
