Part IThe Big Picture

What Booklet Is

Booklet is a read-it-later and annotation app: save an article, PDF, or EPUB from anywhere; read it in a clean, distraction-free view; highlight and annotate as you go; and — the part most apps in this space skip — actually see those highlights again later, through a real spaced-repetition schedule instead of a pile that quietly grows forever.

It's a monorepo containing a real backend API, a web app, a browser extension, and a mobile app, all built around one architectural commitment: everything works with zero account. Saving, reading, highlighting, resurfacing, PDF/EPUB rendering, search, OCR, and text-to-speech all run entirely client-side against the browser's own IndexedDB when signed out. An account exists for exactly one reason — syncing a library across devices — and nothing product-facing is gated behind creating one.

Why It Exists

Read-it-later apps have a well-known failure mode. You save something interesting, fully intending to read it later, and it joins a queue that only ever grows. Occasionally you do read something and highlight a passage that actually mattered to you — and then that highlight disappears into a list you never open again, indistinguishable from the hundred other things you saved and forgot.

Booklet's actual thesis is that the second half of that problem — highlights vanishing — is the more interesting one to fix, and that fixing it properly means borrowing the one piece of technology that already solved "how do you make sure you actually remember something": spaced repetition. A highlight in Booklet isn't a stored string; structurally, it's a flashcard whether the person who made it thought of it that way or not. It resurfaces later on a real SM-2 schedule (the same algorithm behind Anki, see Resurfacing), with interval growth on recall and a reset on a miss — not a random reminder, not "here's five things from your library," an actual memory-scheduling algorithm making the call.

Everything else about the project follows from taking a handful of related opinions further than most similar tools bother to: that a saved PDF or EPUB should be rendered, not flattened into plain text; that read-aloud should feel instant, not like a novelty; and that the entire save → read → highlight → resurface loop should work the same way whether or not you've ever created an account.

Design Principles

Offline is the default

Not a fallback mode, not a degraded experience — the primary, first-class way to use the app. See The Offline-First Model.

Render, don't flatten

A PDF's pages and an EPUB's chapters are rendered as themselves — real canvas output, real pagination — not reduced to plain text and re-flowed.

Real algorithms, not heuristics

Where a real, well-understood algorithm exists for a problem (SM-2 for spaced repetition), it's used directly rather than approximated with a simpler-looking heuristic.

The integration surface is a product

The public API, personal access tokens, and webhooks aren't an afterthought bolted onto the internal routes — they're a deliberately separate, versioned surface.

Measure, don't assume

Performance and architecture decisions in this codebase are backed by real, hand-run measurements — see the TTS section for the most extensive example of this discipline.

Fix root causes

When something breaks, the instinct throughout this project's history has been to find the actual mechanism, not to route around the symptom with a workaround.

Part IIArchitecture

The Monorepo

Booklet is one pnpm workspace containing five real packages: 

apps/
  api/            # Fastify API + Prisma schema — the one backend
  web/            # Next.js web app
  extension/      # Browser extension (Manifest V3, Chrome + Firefox)
  mobile/         # Expo / React Native app
packages/
  shared/         # Types + pure logic shared by every app above
                  # (request/response DTOs, highlight anchoring, SM-2, tts-voices, ...)
Why a monorepo

Four real clients (web, extension, mobile, plus the API itself) need to agree on the exact same request/response shapes, highlight-anchoring math, and SM-2 scheduling logic. Splitting those into separate repositories would mean either duplicating that logic four times (and letting the copies drift, silently, the moment one gets fixed and the others don't) or publishing it as a versioned package with all the release-and-bump ceremony that implies for what is, in practice, one team iterating on one product. packages/shared exists specifically so "the highlight-anchoring algorithm" and "what an ArticleSummary looks like on the wire" are each defined exactly once.

The Offline-First Model

Every product surface in the web app is built against one repository-style interface, with two real implementations behind it:

  • Local mode (no account) — reads and writes IndexedDB directly in the browser, via apps/web/src/lib/local/db.ts.
  • Synced mode (signed in) — talks to the real Fastify API, which persists to PostgreSQL.

apps/web/src/lib/data/*.ts is the seam: every page and component calls functions like loadArticles(isAuthenticated) or createHighlight(...) from that layer, and the layer itself decides which backend actually answers, based on whether the caller is authenticated. The UI code never branches on "am I signed in" itself — it just calls the same function either way.

Why this isn't just a demo mode

The local implementation isn't a stripped-down preview meant to get someone to sign up — it implements the exact same contract as the server-backed one: the same save/highlight/ resurface behavior, the same SM-2 scheduling math (imported directly from packages/shared, not reimplemented), the same search semantics. Signing in for the first time migrates whatever's already in IndexedDB onto the new account rather than discarding it, which only makes sense if the two modes were genuinely equivalent the whole time.

Crossing the seam: local → account

That migration is the single riskiest moment in the whole offline-first design, and it is worth understanding why. The instant status becomes authenticated, every module in lib/data/* switches to reading from the server. If the migration hasn't landed by then, the reader sees an empty library — and from behind the screen "the import failed" and "signing up deleted everything I saved" look exactly the same.

A real ship blocker: the silent empty library

migrateLocalDataToAccount() used to POST the entire local library — every article's full extractedHtml included — as one JSON body. Fastify's bodyLimit was never set, so it was the default 1 MB, and the request was rejected with a 413 before the route was even reached. The caller wrapped it in catch {}: no toast, no log, no retry. Signup carried on regardless.

This was not an edge case for large libraries. Extraction inlines images as base64 data URIs up to 15 MB an article, and base64 inflates bytes by about a third — so one ordinary image-heavy save could exceed the limit on its own.

The data was never actually destroyed (IndexedDB is only cleared after a successful import), which is exactly what made it so easy to miss: nothing was lost, and nothing said so.

The fix has four parts, and the interesting thing is that only the first is about the size limit:

  • Batched by real serialized bytes (~4 MB a batch), with each batch dropped from IndexedDB only once the server has accepted it. A failure part-way leaves the remainder intact and a retry resumes rather than restarting. An article larger than the target still goes alone, because an article is the smallest thing the route can accept.
  • A deliberate 32 MB bodyLimit, scoped to that one route — sized for the largest single article rather than left at an accidental default. Fastify parses bodies before preHandler, so this buffer is reachable pre-authentication; that exposure is bounded by the global rate limit and confined to one route rather than raised app-wide.
  • The failure is surfaced: the library says how many articles are still on the device, states plainly that nothing was lost, and offers a retry.
  • The writes are batched server-side. The route issued a findUnique + create per article and per highlight — roughly 4,000 serialized round trips for a 2,000-article Pocket import, inside one HTTP request. Ids are generated up front so createMany can be used and the localId → server-id mapping still comes back without a per-row query. Measured on 502 articles and 501 highlights: 6,754 ms → 1,186 ms.
Batching exposed two more bugs

Both were latent before and would have stayed invisible without it. Two local articles sharing a URL tripped @@unique([userId, url]) and took the whole batch down — fine when rows went in one at a time, fatal in a createMany. And highlights have no unique constraint, so any replay duplicated them. That second one only became reachable because of the retry design: a batch the server committed but whose response was lost gets sent again, and would have silently doubled someone's notebook. Both are now deduplicated and covered by tests.

One suggestion was deliberately not taken: dropping extractedHtml for articles that have a url, on the grounds that the server could re-extract it. It could — but not for a page that has since changed or gone offline, and keeping a readable copy of those is real value this app otherwise provides. Sizing the limit honestly was the better trade.

Anatomy of Saving an Article

Concretely, here's what happens end to end when a signed-in user pastes a URL and clicks Save — a useful worked example of how the pieces above actually fit together:

  1. Client (web app) — lib/data/articles.ts's saveArticleByUrl POSTs to /api/extract.
  2. API (routes/extract.ts) — hands off to extraction-service.ts's fetchAndExtract.
  3. SSRF guard — before fetching anything, the target host is DNS-resolved and checked against private/ loopback/link-local ranges, on every redirect hop, not just the first request.
  4. Fetch + parse — the raw HTML is fetched server-side and run through @mozilla/readability (via jsdom) to pull out the actual article content.
  5. Image inlining — every <img> in the extracted HTML is fetched server-side and re-embedded as a base64 data: URI, so the saved copy survives even if the original page (or its images) later disappears.
  6. Client (again) — the extracted content comes back to the browser, which then POSTs it to /api/articles to actually persist the row (a deliberate two-step split: extraction is a stateless, unauthenticated operation shared with local/anonymous mode; only the second step needs a real account).
  7. Persistence — a new Article row is written, duplicate-checked against both the raw URL and its canonicalized form (so a tracking-param or AMP-link variant of something already saved is caught).

The same /api/extract stateless-extraction step is reused, unmodified, by local/anonymous mode — it just skips step 6 and writes straight to IndexedDB instead.

Part IIIThe Technology Stack

Every major tool this project depends on, and the actual reasoning behind picking it — not just a list of logos.

TypeScript, Everywhere

Every line of application code in this repository — API, web app, extension, mobile, shared package — is TypeScript. There is no plain-JavaScript escape hatch anywhere in the product code.

Why

The most concrete reason is the monorepo itself: packages/shared's whole purpose is to be a single source of truth for shapes — the Article, Highlight, and HighlightPosition types, the request/response DTOs every route and every client agree on. That only actually works as a guarantee (not just a convention someone has to remember to follow) if the compiler is the one enforcing it. A JSON shape drifting silently between the API and one of four different clients is exactly the class of bug static types exist to catch before it ships.

What "TypeScript" means for a beginner: JavaScript is the language web browsers (and Node.js) actually execute — it has no concept of a variable's "type" being checked before the code runs. TypeScript is a superset of JavaScript that adds an optional type system on top: you can annotate a function as taking a string and returning a number, and a separate tool (tsc, the TypeScript compiler) checks that every call site actually respects that before compiling it down to plain JavaScript. The types themselves don't exist at runtime — they're erased during compilation — they exist purely to catch mistakes before the code runs, which is exactly what tsc --noEmit (used throughout this project's CI) does: type-check without even producing output, purely as a correctness gate.

Node.js + Fastify

The API (apps/api) runs on Node.js, using Fastify as the HTTP framework.

What Node.js is, for a beginner: JavaScript was born as a language that only ran inside a web browser. Node.js is that same language engine (V8, the one Chrome uses) lifted out of the browser and given the things a browser deliberately withholds: reading and writing files, opening network sockets, spawning other processes. That's the whole idea — one language on both sides of the wire. In this project it's what makes packages/shared possible at all: the SM-2 scheduling math is imported unchanged by a Fastify route handler on the server and by a React component in a browser tab, because both are running the same language on the same engine.

The other Node fact that matters for reading this codebase is its concurrency model. Node runs your JavaScript on a single thread with an event loop: work that waits on something external (a database query, an HTTP fetch) is handed off and the thread moves on, picking the result up later via a callback or a Promise. That is excellent for an API that mostly waits on Postgres, and terrible for work that actually pins a CPU — because while that work runs, nothing else on that thread can. Speech synthesis is exactly that kind of work, and it is the direct reason the TTS pipeline runs in a pool of separate processes rather than inline (see Chapter 3). OCR is the same shape of problem, which is why it's capped at 20 pages and why a failure inside it once took the entire server down (see OCR).

Why Fastify over Express

Fastify was designed from the ground up around JSON Schema-based request/response validation and a plugin architecture with explicit encapsulation, both of which matter more as an API surface grows past a handful of routes. It's also meaningfully faster in real benchmarks (schema-compiled serialization instead of generic JSON.stringify), though for an app at this project's actual traffic scale, that's a secondary benefit next to the developer-experience one: Fastify's plugin (app.register(...)) model is what makes it natural to compose the exact set of concerns this API needs — CORS, cookies, rate limiting, multipart uploads — each as an isolated, independently reasoned-about piece (see app.ts).

Table stakes for the API layer, concretely:

  • @fastify/cors — origin allowlisting (any localhost port in dev, a pinned WEB_ORIGIN in production, plus chrome-extension:/// moz-extension:// for the browser extension).
  • @fastify/cookie — the refresh-token cookie.
  • @fastify/rate-limit — an in-memory, per-route configurable limiter (tighter on genuinely expensive routes like /api/tts and /api/auth/* than the general default).
  • @fastify/multipart — PDF/EPUB file uploads.

PostgreSQL + Prisma

The database is PostgreSQL, accessed exclusively through Prisma — never a raw SQL query string anywhere in the codebase.

Why an ORM at all

Prisma's schema file (apps/api/prisma/schema.prisma) is the single source of truth for the data model, and it generates a fully-typed client from it — a query for Article rows is typed against the actual current schema, not a hand-maintained interface that can drift out of sync with the real database. Migrations are generated from schema diffs (prisma migrate dev) rather than hand-written, which matters more the longer a project lives: this schema is already many migrations deep (see apps/api/prisma/migrations/), each one a real, reviewable diff instead of a hand-rolled ALTER TABLE someone has to get exactly right.

What an ORM is, for a beginner: "Object-Relational Mapping" — a library that lets you query a relational (table-based) database using the target language's own objects/functions instead of writing raw SQL strings by hand. prisma.article.findMany({ where: { userId } }) instead of SELECT * FROM "Article" WHERE "userId" = $1. The tradeoff is a layer of abstraction between you and the actual SQL being run — worth it here because of the typed-schema guarantee above, but it's still worth understanding what SQL an ORM call actually compiles to when performance matters (see the query-level omit optimization in Search for a real example of a performance decision made because the underlying query was understood, not despite the ORM hiding it).

The local dev database: PGlite

Running Postgres locally usually means installing it or running Docker. This project ships a zero-install alternative: PGlite, a WASM-compiled Postgres that runs as a real, Postgres-wire-protocol-speaking server (apps/api/scripts/dev-db.ts) on localhost:5432, persisting to a local data directory. It's genuinely real Postgres underneath (not a mock or a compatible-but-different engine) — the tradeoff is that Prisma's own migration engine doesn't reliably speak to it, so schema changes go through a separate script (migrate:pglite) that applies migrations via the plain pg driver instead.

How Postgres Full-Text Search Works

Search is the one place this project reaches past Prisma into raw SQL, so it's worth understanding the machinery rather than treating it as a magic incantation. Every term below appears verbatim in apps/api/src/routes/search.ts and in prisma/migrations/20260813000000_article_search_vector/.

TermWhat it actually is
tsvector A Postgres column type holding a document that has been pre-chewed for searching: the text is split into words, each word is reduced to its stem, stop-words ("the", "and") are dropped, and what remains is stored as a sorted list of lexemes with their positions. Storing this instead of re-parsing the article on every query is the entire performance story.
Lexeme A stemmed, normalized word. running, runs and ran all reduce to the lexeme run — which is why searching "run" finds an article that only ever said "running". This is what people mean by stemming, and it is the single biggest reason a real full-text index beats a LIKE '%run%' substring match.
tsquery The search side of the same idea: the user's typed query, stemmed the same way and turned into a boolean expression of lexemes. The @@ operator is "does this tsvector satisfy this tsquery".
websearch_to_tsquery One of three functions that build a tsquery from human input. This one parses the conventions people already know from web search engines: bare words mean AND, "quoted phrases" mean an adjacent phrase, and -word excludes. Chosen over plainto_tsquery (which also ANDs but understands no operators) and to_tsquery (which demands explicit &/| syntax and throws a syntax error on ordinary prose).
setweight / A-B-C-D Postgres lets each lexeme carry one of four weight labels. Booklet assigns A to the title, B to author + site name, C to the excerpt, and D to the full extracted body. The weights are what make a title hit outrank a passing mention buried in ten thousand words of body text.
ts_rank Turns a (vector, query) pair into a relevance score, using those weights plus how often and how densely the query's lexemes occur. This is the ORDER BY.
ts_headline Generates the little snippet under each result with the matched words marked. Note it re-parses the original document to do so — it works from the text, not from the tsvector — which is why the query has to hand it the real column.
GIN index Generalized Inverted Index. "Inverted" means it's built the way a book's index is: instead of row → words, it stores word → the rows containing it. Without it, @@ would mean scanning every row of the table.
Generated / stored column GENERATED ALWAYS AS (...) STORED — Postgres computes the tsvector itself from the title/author/excerpt/body columns and keeps it up to date on every insert and update. No application code, no trigger, and no way for the index to silently drift out of sync with the article it describes.
Why GIN rather than GiST

Postgres offers both for tsvector. GiST is smaller and cheaper to update but lossy — it can return false positives that Postgres must then recheck against the real row. GIN is larger and slower to write but exact and considerably faster to read. A saved-articles table is read constantly and written once per save, so GIN is the obvious side of that tradeoff — and the migration says so in a comment rather than leaving the choice looking arbitrary.

The client-side counterpart: MiniSearch

None of the above exists in a browser, and local/anonymous mode has no server to ask. local-search-index.ts therefore builds an equivalent index in memory with MiniSearch, a small dependency-free JavaScript full-text engine, over the articles already sitting in IndexedDB. It's given the same structure deliberately: the stemmer package supplies Porter stemming to mirror Postgres's english configuration, per-field boosts stand in for the A/B/C/D weights, and its query mode ANDs terms the way websearch_to_tsquery does. MiniSearch scores with a BM25-style formula rather than ts_rank's weighted-position one, so the two rankers are comparable, not identical — see Search for why that's a documented consequence rather than a bug.

Next.js + React

The web app is Next.js (App Router) with React 19.

What React is, for a beginner: the traditional way to change a web page is to find an element and mutate it — set its text, add a class, remove a child. That works until two different pieces of code both think they own the same element, at which point the page's appearance and the program's actual state quietly stop agreeing. React inverts it: you write a function that takes the current state and returns what the page should look like, and React works out the minimal set of real DOM changes to get there. You never write "add this element"; you write "given this state, these elements exist". State changes, the function re-runs, React diffs the result against what's on screen and patches the difference.

Two React words appear constantly in this codebase and are worth knowing precisely. A component is one of those functions — ReaderView, ArticleCard, RenameDialog. A hook is a function starting with use that lets a component hold onto something across re-runs: useState for a value that should trigger a re-render when it changes, useRef for one that shouldn't, useEffect for work that has to happen after rendering (subscribing to an event, starting a timer). That useState/useRef distinction is not academic here — the read-aloud position accumulates into refs specifically because storing it in state would re-render the whole app shell several times a second for a value nothing displays (see Chapter 8).

Why Next.js specifically

Nearly the entire app is client-rendered in practice — the reader, the library, TTS playback, all of it runs in the browser, often against IndexedDB with no server round-trip at all. What Next.js buys here isn't server-rendering every page; it's the file-based App Router (routes as folders, layouts that compose naturally — see how app/layout.tsx mounts the global TTS player once, at the root, so it survives client-side navigation between pages), first-class TypeScript support, and next/dynamic for code-splitting heavy, conditionally-needed libraries (pdf.js and epub.js are only loaded when a PDF/EPUB reader actually mounts, not on every page load — see the Roads Not Taken entry on this).

One Next.js behavior that has real consequences here: NEXT_PUBLIC_

Next.js splits environment variables in two. An ordinary variable is read on the server at runtime. A variable prefixed NEXT_PUBLIC_ is textually substituted into the JavaScript bundle at build time — it is baked into files a browser downloads, so it is public by construction and fixed at the moment the image was built.

Both halves of that have bitten this project. Supplying NEXT_PUBLIC_SENTRY_DSN through Docker Compose's environment: was too late to ever reach a browser, so the container would start cleanly with error monitoring silently doing nothing — the failure mode that looks exactly like success. It's passed as a build ARG now. And the rule is why the Datadog RUM client token is correctly NEXT_PUBLIC_ (it is publishable and write-only) while a Datadog API key must never be — see Observability.

Tailwind CSS

Styling is Tailwind CSS v4, utility-first — no CSS-in-JS, no separate stylesheet per component. Theming (light/dark/sepia/ Kindle) is layered on top via CSS custom properties defined once in globals.css (--color-paper, --color-accent, etc.), which Tailwind's utilities then reference — so bg-paper or text-ink automatically repaint correctly under every theme without any component needing to know which theme is active.

What "utility-first" means: instead of inventing a semantic class name (.article-card) and writing its rules in a stylesheet somewhere else, you compose the element out of many tiny single-purpose classes right where it's written — class="flex items-center gap-3 rounded-lg p-4". It looks noisy at first and buys two specific things. Styles are local: deleting a component deletes its styling with it, and no rule written for one screen can leak into another, which is the failure mode of every large hand-written stylesheet. And there is no naming problem, which sounds trivial until you've spent an afternoon arguing about whether something is a card, a tile, or a panel.

What CSS custom properties add on top: a custom property (--color-paper: #EDEBE2) is a variable the browser itself resolves at paint time, not a build-time constant. Redefine it under a different selector — [data-theme="sepia"] — and every element referencing it repaints, with no JavaScript and no component re-render. That's why switching between Booklet's four reader themes is instant and why no component contains the word "sepia" anywhere. This documentation page uses the same technique, which is why it follows your system's light/dark setting.

pnpm Workspaces + Turborepo

Package management is pnpm, in workspace mode (pnpm-workspace.yaml) — every app and package in the monorepo shares one node_modules install, with real workspace-local dependencies (@booklet/shared: "workspace:*") resolving to the actual local source, not a published version.

Why pnpm over npm/yarn

pnpm's content-addressable store means a dependency installed once on disk is hard-linked into every project that needs it, rather than duplicated per-project the way npm/yarn classic do — meaningfully faster installs and far less disk usage in a multi-app monorepo where every app depends on things like typescript or react independently.

Turborepo sits on top as a task runner with real caching — turbo.json defines the build/typecheck/lint/test pipeline, with dependency ordering (^build means "this package's own workspace dependencies must build first") and content-hash-based caching, so re-running a check against unchanged code replays the cached result instead of redoing the work.

A real measurement

Confirmed by hand: a repeated pnpm typecheck across all five packages with no code changes goes from several seconds (real, from-scratch tsc --noEmit runs) to about 30 milliseconds ("FULL TURBO", every package a cache hit). This was added specifically because the monorepo had zero task caching before — every pnpm build/typecheck/ test/lint always did full work regardless of what actually changed.

One React for the Workspace

This deserves its own section because it is the clearest example in the repo of a dependency-hygiene problem presenting as an unrelated, incomprehensible bug — and of the difference between fixing that and configuring around it.

Background: what a package manager's "linker" does. pnpm's headline feature is that it does not copy a dependency into every project that needs it. It keeps one copy in a content-addressable store and builds each package's node_modules out of symlinks into it, arranged in a strict nested tree where a package can only see what it actually declared. That strictness is a feature: it catches code importing something it never listed as a dependency.

Booklet cannot use it. pnpm-workspace.yaml sets nodeLinker: hoisted, which produces a flat, npm-style node_modules instead — because Metro, the React Native bundler behind apps/mobile, could not resolve past the NTFS junctions pnpm's default linker creates on Windows. The comment that recorded that decision also predicted its cost, correctly: a flat tree has exactly one winner per package name, and anything that can't use the winner gets its own nested copy.

Three Reacts, and a failure that lies about its cause

The workspace ended up resolving three React installs: apps/mobile pinned 19.0.0 for Expo, apps/web pinned 19.2.4, and what landed at the root was neither — at one point a react@19.0.0 paired with a react-dom@19.2.8, a combination React does not support at all.

React keeps the currently-rendering component's hook state in module-level scope. Two copies of React means two of those, and a component rendered by one while calling hooks from the other reads a null internals object. What you get is Cannot read properties of null (reading 'useState') — an error that points at your component and says nothing whatsoever about module resolution. Sometimes it doesn't even error; it just renders nothing.

The trap worth remembering: a component with no hooks renders fine across two copies. The first test written against this rendered a forwardRef button, passed, and proved nothing. Only rewriting it against RenameDialog — useState, useRef, useEffect and createPortal, so it exercises react-dom too, which was the mismatched half — reproduced the real failure. The test is deliberately kept on that component so a regression can't hide behind a hookless render.

The fix is four lines: a workspace-wide overrides block pinning react and react-dom to 19.2.4 for every package. An override tells the package manager to force one version for a dependency no matter who asked for what — the blunt instrument, appropriate here precisely because the goal is "there is exactly one of these". 19.2.4 rather than mobile's 19.0.0 because web is where the rendering, the testing, and any production traffic actually are.

Why not just alias it in the test config

The tempting fix was to make Vitest resolve React to one copy — resolve.alias, resolve.dedupe, server.deps.inline. All three were tried and none work, because the renderer resolves React through Node before Vite ever sees the import. But even if one had worked it would have been the wrong fix: it would make tests agree about React while the application kept shipping three copies, which is configuring around a real defect rather than removing it. The packages were left uninstalled and the issue filed (#166) instead of leaving a test setup in place that looked functional.

The same cleanup removed three root dependencies that were npm residue rather than intended work (@sentry/node, @sentry/profiling-node, @sentry/react — nothing imports the latter two; the code uses @sentry/browser and @sentry/node, and the root copy merely duplicated apps/api's own declaration at a different range). Dropping them also dropped @sentry/node-cpu-profiler, whose install script compiles native bindings through node-gyp — which is what had left an unanswered build-script approval prompt sitting in pnpm-workspace.yaml making every real pnpm install exit non-zero. The prompt was deleted rather than answered, because the dependency that provoked it should never have been there.

Vitest, jsdom + Playwright

Vitest is the test runner for everything that isn't a browser test. A "test runner" is the program that finds your test files, executes them, catches the assertions that fail, and reports what happened; Vitest is built on Vite, so it transforms TypeScript on the fly with no separate build step and runs native ES modules rather than transpiling everything down to CommonJS the way Jest historically did. Its API is deliberately Jest-compatible (describe, it, expect, vi.mock), so existing knowledge transfers directly.

jsdom is a pure-JavaScript implementation of the DOM and a chunk of the browser's other APIs, running inside Node. It gives a test a real document, real Element and Range objects, real event dispatch — everything a browser provides except actually drawing anything. That exception is the important part and defines the boundary between two of this project's test layers: jsdom does no layout, so getBoundingClientRect() and Range#getClientRects() return zeros. Any logic that depends on where something physically is on screen must be a Playwright test; logic that only walks the tree — offset-to-node bridging, section anchoring, popover dismissal rules — belongs in jsdom, where it costs milliseconds instead of seconds.

jsdom is also load-bearing on the server here, which surprises people: article extraction runs Mozilla Readability, and Readability needs a DOM to walk. Parsing fetched HTML into jsdom is how apps/api gets one.

@testing-library/react renders a real component into a jsdom document and hands back queries that find elements the way a user would — by visible text, by accessible role, by label — rather than by CSS selector. That bias is the whole philosophy: a test that finds a button by its accessible name keeps passing through a refactor that renames a class, and starts failing if the button stops being reachable to a screen reader.

Playwright drives a real browser — a real Chromium process, real rendering, real network — against the real running app. It is the only layer that can see a PDF canvas actually paint, an EPUB iframe actually paginate, or audio actually play. It's also the most expensive layer by an order of magnitude, which is why Testing Philosophy is largely a story about moving work out of it.

Two Playwright features this repo leans on specifically: webServer in playwright.config.ts starts processes the suite depends on (including the local article fixture server) and waits for them before running anything, so the suite is one command rather than a README instruction; and tag-based filtering, which is how the seven specs that genuinely need the public internet are marked @live and can be excluded wholesale on a network-restricted runner.

IndexedDB

The local/anonymous mode's storage engine is IndexedDB — the browser's own built-in, transactional, structured-object database (not localStorage, which is synchronous, string-only, and far too small for a whole reading library). Accessed through a thin wrapper (apps/web/src/lib/local/db.ts) that gives the rest of the app the same repository-style interface the server-backed mode uses — see The Offline-First Model.

The concepts, precisely, because IndexedDB's API is famously awkward and several real bugs in this project came from getting one of them subtly wrong:

  • Database → object store → record. An object store is roughly a table, but it stores whole JavaScript objects rather than rows of typed columns. Each record has a key; an index can be declared on any property to allow lookups and ordered scans by something other than that key.
  • Everything is asynchronous and event-based. Not promise-based — an operation returns an IDBRequest that later fires onsuccess or onerror. Modern code wraps that in a Promise, which is what db.ts does.
  • Transactions auto-close. A transaction stays alive only while it has pending work; awaiting anything unrelated inside one lets it commit out from under you. And crucially, a request firing onsuccess does not mean the data is durable — the transaction can still roll back afterwards. Writes here therefore await the transaction's oncomplete, not the request's onsuccess. Getting this backwards lets a write report success and then silently vanish.
  • Structured clone, not JSON. IndexedDB stores values using the structured-clone algorithm, which handles Date, Map, Set, ArrayBuffer and cyclic references — things JSON.stringify cannot. That power has an edge: cloning a Blob stores a reference to a browser-owned backing store rather than the bytes, and a Blob whose backing store came from somewhere unusual can read back as something that is no longer the audio you put in. That exact trap is why the TTS audio cache reads arrayBuffer() before writing — see Chapter 7.
  • Storage is a quota, not a promise. The browser can evict an origin's data under pressure, private-browsing modes may refuse to open a database at all (Firefox throws synchronously from open() rather than firing onerror), and quota is shared across the origin. Any code here that uses IndexedDB for a cache degrades to "just use the network" on every one of those paths.
Testing it: fake-indexeddb

IndexedDB doesn't exist in Node, so the unit tests run against fake-indexeddb, a full in-memory implementation of the specification. It is real enough to exercise transaction semantics, index ordering, and key collisions — which is how the audio cache's LRU eviction bug was caught by a test rather than by hand.

Bundling: esbuild, and why production ≠ dev

A bundler reads an application's entry point, follows every import transitively, and emits a small number of files with the whole graph flattened into them. It exists because shipping a thousand separate modules means a thousand separate fetches in a browser, and because minification and tree-shaking (dropping code nothing references) need a whole-program view.

The API's production build (apps/api/scripts/build.mjs) uses esbuild, a bundler written in Go that is roughly two orders of magnitude faster than the JavaScript-based generation before it. The web app's bundling is handled by Next.js itself.

The production build is a different execution environment, and it breaks differently

In development this API runs under tsx, which resolves modules at runtime through Node's own algorithm. In production it is one esbuild-flattened file run by plain node. Those are not the same environment, and the gap has produced real, silent breakage more than once.

The sharpest example: tsc resolves imports through node_modules and never asks who declared a package. So importing a transitive dependency — something you got only because another package depends on it — typechecks perfectly and then fails in esbuild. That's exactly how a direct @huggingface/transformers import broke the Docker build with "No loader is configured for '.node' files" while every other CI job stayed green. The response was to declare the dependency properly and to run the production bundle in the cheap typecheck job, so that signal arrives about two minutes earlier than waiting for a Docker layer to report it.

Bundling is also why auto-instrumentation was rejected for tracing: it needs to patch modules as they load, and a flattened single file has no load events left to intercept. See Observability.

ONNX Runtime, WASM & WebGPU

These three names appear throughout the TTS story and are usually left unexplained, so:

  • ONNX (Open Neural Network Exchange) is a portable file format for a trained neural network — the network's layer graph plus its learned weights, saved in a way that isn't tied to the framework it was trained in. ONNX Runtime is the engine that loads such a file and actually runs it, with backends for CPU, CUDA, WebGPU and more. Kokoro is distributed as ONNX, which is precisely why the same 82-million-parameter model can run in a browser tab and in a Node process with no separate Python service anywhere in this architecture.
  • WASM (WebAssembly) is a portable binary instruction format that browsers execute in a sandbox at near-native speed. It is how C/C++/Rust code reaches the web — and in this project it's how the browser-side Kokoro attempt ran, how Tesseract.js does OCR, and how PGlite runs a genuine Postgres with nothing installed.
  • WebGPU is the browser's modern GPU API, the successor to WebGL, and unlike WebGL it exposes general-purpose compute rather than only graphics. It's the fast path for in-browser inference where available — availability being the problem: it was still gated behind flags or absent in much of the real installed base during this project's client-side TTS attempt, and adapter detection itself was a source of failures.
Why "single-threaded WASM" was a ceiling and not a tuning problem

The rejected client-side implementation measured 12–18 seconds per sentence. That number is not the model being large — it's the per-token cost of running matrix math inside a sandbox that, in the general case, gets one thread and no GPU. Worker-based pipelining, quantization and multi-threading were all tried; none of them changed the shape of the problem, because none of them changed the per-token cost. Moving the same ONNX file to a Node process, where ONNX Runtime uses native code and real threads, did — and it took one afternoon. See Chapters 1 and 2.

Docker & Containers

What a container is: a process running on the host kernel, with its own isolated view of the filesystem, network and process table. Not a virtual machine — there's no second kernel and no emulated hardware, which is why a container starts in milliseconds where a VM takes tens of seconds. What it gets isolation from is the host's software: the exact Node version, the exact system libraries, the exact file layout are all fixed inside the image rather than assumed to exist on whatever machine runs it.

Image versus container: an image is a read-only stack of filesystem layers plus metadata (what command to run, what ports, what environment). A container is one running instance of an image with a thin writable layer on top. A Dockerfile is the script that builds an image, one layer per instruction, and each layer is cached — so reordering a Dockerfile so that dependency installation comes before source-code copying is the single most common build-speed fix, since source changes then don't invalidate the dependency layer.

Booklet has a Dockerfile per app plus a docker-compose.yml that wires the API, the web app and Postgres together for a one-command local stack. Compose is the "several containers that need to see each other" layer: it creates a network, gives each service a DNS name, and starts them in dependency order.

What containerizing actually bought this project

Not deployment — there is no production host yet. Two other things. First, it's the only way to run the real production execution path in CI: tsc/esbuild to a bundle, then plain node dist/index.js with no dev-time module resolution helping, against a real Postgres, with the health route actually polled. That path has broken while every other check stayed green (see Bundling). Second, it's where Kokoro's ~90MB of ONNX weights are baked in at build time, turning a 10–60 second first-request download into zero — see Deployment.

OpenTelemetry & the Vocabulary of Tracing

OpenTelemetry (OTel) is a vendor-neutral standard — and set of SDKs — for producing telemetry: traces, metrics and logs. The reason it exists is that every monitoring vendor used to ship its own agent and its own SDK, so instrumenting your code meant choosing a vendor and then re-doing the work to leave. OTel separates producing telemetry from where it goes: your code emits standard spans, an exporter ships them over OTLP (the OpenTelemetry Protocol) to whatever backend is configured, and switching backends is a URL.

TermMeaning
SpanOne timed operation — a name, a start and end time, and a bag of key/value attributes. "Generate this TTS chunk" is a span.
TraceA tree of spans sharing an id, representing one end-to-end request as it moves through the system. Spans nest: the parent's duration contains its children's.
AttributeA labelled value on a span (tts.queue_wait_ms, tts.cache_tier). This is where the information you'll actually query lives; a span with a duration and no attributes tells you something was slow and nothing about why.
ExporterThe component that batches finished spans and ships them out. Buffered, which is why flushing it on shutdown matters — and why a stray process.exit() elsewhere silently discarded them (see Observability).
InstrumentationThe code that creates spans. Manual means you wrote it at the call site; automatic means a library patches known frameworks at load time to create them for you.
RUMReal User Monitoring — telemetry collected in the actual browser of an actual user, as opposed to from your servers or a synthetic benchmark. The only place a number like "time to first audio on a real laptop over real wifi" can come from.

The account itself. passwordHash is nullable — an OAuth-only user (Google/GitHub) never gets a random password they'd never know; login-by-password just isn't offered for that account. Holds the resurfacing preferences (resurfaceFrequency, highlightsPerDigest) directly, since they're genuinely account-level settings, not per-device ones.

The center of the schema. One row per saved item, regardless of sourceType (HTML/PDF/ EPUB/BOOK — BOOK being the special case for a Kindle-clippings import with highlights but no actual content, see Import/Export). Two duplicate-detection fields exist side by side on purpose: url (exactly what was saved) and canonicalUrl (tracking params stripped, host/ trailing-slash normalized) — an exact-string check alone would miss a tracking-param or AMP-link variant of something already saved.

Why extractedHtml and extractedText are separate columns

extractedHtml is HTML-only (what the reader actually renders for an HTML-sourced article). extractedText is populated for every source type (HTML/PDF/EPUB alike) — the plain-text form used for full-text search and the reading-time estimate, and, for PDF/EPUB, the only text representation that exists at all (their real content renders via pdfjs-dist/epub.js directly from the uploaded file, not from this column). Both are large enough to matter: see Search for the real, measured cost of fetching them for rows that don't need them, and the fix.

The one column Prisma cannot describe: searchVector

Article.searchVector is declared in the schema as Unsupported("tsvector")?. Prisma has no tsvector type, and Unsupported is its explicit escape hatch: the column is acknowledged so migrations don't try to drop it and the generated client knows the field exists, but it can't be read or filtered through the normal query API. Its actual definition — the weighted setweight(...) expression and the GIN index — lives in the migration SQL, and querying it means dropping to $queryRaw. That's the honest cost of using a database feature richer than the ORM's type system, paid deliberately in one file. See How Postgres Full-Text Search Works for what each piece does.

The listening-position trio

Three columns added together (#152) so read-aloud can resume across devices, and each one earns its place:

listeningFraction Float? — how far through the article listening reached, as a fraction of its text. Deliberately not a chunk index. Chunk boundaries are a function of the TTS chunker's size constants, which are latency knobs that have already moved once (200 → 140 characters), and re-extracting an article changes the text underneath any index anyway — either would silently resume at the wrong place. A fraction survives both, and matches how progressFraction already normalizes across source types.

Nullable, unlike progressFraction — "never listened" has to be distinguishable from "listened, then paused at the very start", or the resume prompt fires on every article nobody has ever played. Every construction site sets it to null explicitly, apps/mobile included: mobile has no read-aloud yet, but it shares the Article type and syncs the same rows, so it must not write a position the web reader would then offer to resume from.

listeningUpdatedAt DateTime? — a server timestamp, which makes conflict resolution honest: two devices playing the same article at once is rare and no reconciliation of two positions is more correct than "whichever was most recent", so the rule is last-write-wins, stated rather than implied. Using the server's clock means a wrong or lying client clock can't decide what "recent" means.

listeningDeviceId String? — exists because the resume prompt claims "last played on another device" and that claim needs a source. Without it, the tab that just wrote the position offers to resume from itself. It identifies a browser, not a person, is generated locally (crypto.randomUUID with a fallback, since that is unavailable outside a secure context — plain HTTP on a LAN address is a real way people open this on a phone), and is never displayed.

Highlight

position is a discriminated JSON blob, not a fixed set of columns — its shape depends on the article's source type: a W3C TextQuote+TextPosition-style selector for HTML, page number + rects for PDF, an EPUB CFI (Canonical Fragment Identifier) range for EPUB. See The Reader & Highlight Anchoring for what each of those actually means and how they're resolved back to real DOM ranges.

The SM-2 fields (easinessFactor, intervalDays, repetitions, nextDueAt) live directly on the highlight row — see Resurfacing for the algorithm itself.

Self-referential (parentId/children) for nested, folder-style organization, with onDelete: SetNull rather than Cascade — deleting a parent collection shouldn't take its children down with it; they just become top-level. Part VFeature Deep Dives

Authentication & Sessions

Auth supports email/password and OAuth (Google + GitHub) — and every single one of those methods, email/password included, is entirely optional. Every route works signed out; OAuth buttons only even appear once a provider's credentials are actually configured in the environment.

The token scheme is short-lived JWT access tokens plus a longer- lived, revocable refresh token:

  • Access token — a signed JWT, 15-minute lifetime, sent as a bearer token on every authenticated request. Stateless: verifying it is just a signature check, no database round-trip.
  • Refresh token — a random opaque string, 30-day lifetime, stored in an httpOnly cookie. Only its hash is stored server-side (in Session.refreshTokenHash) — a database read alone is never enough to forge a session.
Why this split instead of one long-lived token

A single long-lived token would need to be stateless (for performance) or revocable (for security) — it can't cleanly be both. Splitting the two means the access token can stay fast and stateless (no DB hit per request) while the refresh token — the thing that actually matters for "can this device still get in" — is a real, revocable database row. "Log out" and "log out other devices" are just deleting/marking that row, and a stolen access token is only useful for 15 minutes.

The Reader & Highlight Anchoring

Three real renderers, one per source type, each anchoring highlights differently because each source has a fundamentally different notion of "position":

  • HTML — rendered as sanitized HTML directly; highlights anchor via a text-offset scheme resolved against the article's own plain-text extraction, with drift-tolerant re-anchoring (a highlight survives minor re-extraction changes by searching nearby, not just an exact offset match).
  • PDF — rendered via pdfjs-dist: real canvas output for the visible page, plus an invisible, precisely-positioned text layer on top for native text selection. Highlights anchor by page number + rectangles in PDF user-space units — genuinely real coordinates, not a text offset, so they never drift.
  • EPUB — rendered via epub.js, paginated, each chapter in its own iframe. Highlights anchor by CFI (Canonical Fragment Identifier) range — EPUB's own standard way of pointing at a specific location inside a specific document within the book.
Why real rendering instead of just showing extracted text everywhere

Flattening a PDF or EPUB to plain text and re-flowing it is simpler to build, but it throws away real information — page numbers a citation might reference, an EPUB's own typography and layout, image placement. Rendering the real thing means highlights can anchor to genuinely stable coordinates (a PDF rect, an EPUB CFI) instead of a text offset that has to survive re-extraction.

OCR

A scanned PDF with an empty or near-empty native text layer automatically falls back to Tesseract.js — no toggle, no "try OCR" button, no API key, and no external service: it's a real WASM OCR engine running in-process on the server. Capped at 20 pages (it runs synchronously inside the upload request), and the reader shows a visible "may contain recognition errors" notice, since Tesseract's real-world error rate is meaningfully higher than a native text layer or Readability extraction.

Tesseract needs trained data — a language model file (eng.traineddata.gz) describing what English letterforms look like — which tesseract.js fetches from a CDN on first use. That one detail is how OCR took down the entire API.

A failed download crashed the whole server (#163)

The CDN fetch for the trained data returned 403. The API process died mid-request, and every subsequent request in that run failed for want of an API rather than for anything to do with OCR. A remote CDN returning 403 or 5xx is an ordinary production event, not a sandbox quirk.

The mechanism is worth understanding, because it defeats the obvious defense. tesseract.js reports worker failures from inside its own message callback, and with no errorHandler installed its fallback is a bare throw on that callback's stack. That stack belongs to the worker's message plumbing, not to your call — so no try/catch around the OCR call and no .catch() on its promise can reach it. Node sees an uncaught exception and exits. Wrapping the call site, the instinctive fix, would have done nothing at all.

The containment has four parts, and the second is the non-obvious one:

  • Install an errorHandler. Its mere presence skips the throwing branch entirely and routes the failure back into normal control flow as a typed OcrError.
  • Race it against createWorker's own promise. tesseract.js does not reliably settle that promise when the failure happens during trained-data load — it rejects whichever internal job it associated the message with, which need not be the one you're awaiting. Awaiting it alone therefore hangs rather than throwing; confirmed as a 30 second test timeout rather than an error.
  • Drop the dead worker so a later call retries. A fetch that 403s once can succeed later, and the pool shouldn't stay poisoned for the life of the process.
  • Share the startup promise. A pre-existing race fixed while in there: two concurrent recognitions each saw a null worker and built their own, leaking one and paying WASM startup twice.

Above that, PDF extraction now treats OCR as best-effort, the same way it already treats inlining an article's images: if OCR fails, fall back to whatever native text there was rather than failing the upload. If there genuinely was none, the existing "couldn't find any extractable text" message still says so.

Why there are two OCR test files

ocr.test.ts does real recognition, so it can only observe this failure where the CDN is genuinely unreachable — a test that only fails on someone else's bad day. ocr-failure.test.ts stubs tesseract.js so the containment is asserted identically everywhere, including the exact shape that caused the outage: the handler fires and createWorker's promise never settles at all. All five were verified to fail against the old implementation — two of them by hanging — and pass against the new one.

A side effect worth noting because it's the kind of thing that looks like an unrelated win: the API suite dropped from 51.6s to 12.3s, because the CDN-dependent test now fails in under a second instead of hanging for thirty.

Text-to-Speech — the Full Story

This is the single most-iterated-on feature in the project's history, and the one with the richest, most concrete record of real measurement driving real architecture changes. It's worth walking through in full, including the parts that got thrown away, because the reasoning at each step is exactly the kind of thing this document exists to preserve.

The model: Kokoro

Speech is generated by Kokoro, an open-weight (Apache-2.0), 82-million-parameter TTS model, via the kokoro-js library on top of ONNX Runtime. The alternative that's always on — needing zero setup, zero model, zero network — is the browser's own native SpeechSynthesis API, kept as a real first-class option in the same voice picker, not just a fallback.

Chapter 1 — Client-side WASM (rejected)

The original implementation ran Kokoro entirely in the browser, over WASM (and, briefly, WebGPU where available). It worked — the voice quality was never in question — but per-sentence generation was measured at a genuine 12-18 seconds, and no amount of client-side engineering closed that gap: not Worker-based pipelining, not quantization, not multi-threading. The WASM sandbox's per-token inference cost turned out to be a hard ceiling, not a configuration problem.

Chapter 2 — Moving generation server-side

The actual unlock was almost embarrassingly simple once tested directly: kokoro-js auto-detects a real Node.js environment and switches to onnxruntime-node — the native, compiled ONNX Runtime binary — instead of the WASM sandbox onnxruntime-web is stuck with in a browser. Confirmed by hand, same model, same voice, same sentence, same machine: ~4.7 seconds instead of 12-18. A real 2.5-3.8x improvement from switching where the exact same code runs, not a config tweak.

Why this was a deliberate exception to "everything works offline"

Moving generation server-side is a genuine departure from this project's default architecture (OCR, extraction, and everything else run entirely client-side/in-process with no server-only dependency). It was accepted explicitly, after the WASM ceiling had been thoroughly explored and confirmed real — not as a first resort.

Chapter 3 — The pause between sentences, and the worker-process pool

Server-side generation alone wasn't enough: a single Kokoro generation call regularly took longer than the resulting audio's own playback duration (measured: up to 9.8 seconds to generate 5.95 seconds of audio). Worse, concurrent requests to a single process serialized — two requests at once took roughly twice as long as one, not the same. No amount of client-side prefetching can outrun a server that's slower than real-time on average; the shortfall just compounds, sentence after sentence, into exactly the growing dead air users actually experienced.

The fix is a small pool of real child processes (apps/api/src/services/tts-pool.ts), each holding its own Kokoro model instance, so multiple chunks can generate at genuinely the same wall-clock time.

Correction: how parallel the pool actually is depends on the host

This document previously claimed three concurrent generations finish in about the same wall-clock time as one. That was measured on a developer machine with cores to spare, and it does not generalize. Re-measured on CI's 2-vCPU runner, three concurrent chunks took 18,725 ms against 6,542 ms for one — 2.86×, not 1×. At that size the pool is mostly queueing, not parallelizing.

The cause is that each worker sizes its ONNX Runtime thread pool to the whole machine, so three workers on two cores oversubscribe and contend rather than share. This also invalidated the reasoning behind warming exactly two chunks ahead, which assumed the extra work was close to free.

Fixed since (#162). Each worker's ONNX session now gets an explicit thread budget — cores / pool size — instead of being left to claim the machine, and the pool is sized from real cores rather than a fixed three, so a 2-vCPU host runs two workers rather than three fighting over two cores.

Being honest about that ratio

2.86× → 2.61× is a modest improvement, and it would be easy to present it as more than it is. The larger correction is that the target was never 1.00×. With more chunks than workers, the best achievable result is ceil(chunks / workers) rounds — three chunks on a two-worker host cannot beat 2.00× however well threading is tuned. Measured against that floor, the pool is now at about 77% of the parallelism the hardware allows, where before it was contending for cores it didn't have.

The benchmark prints the floor and that percentage rather than a bare ratio, because the bare ratio is what made a hardware-bound result look like a broken pool. The real user-visible win here is the absolute numbers: every scenario got 10–25% faster, on the same machine, from doing less fighting.

The warm-ahead count stayed at two, but its justification did not. It is no longer "the extra chunks are free because the pool is parallel"; it is that speculative work runs on a low-priority queue tier that only ever consumes capacity which would otherwise sit idle, so it cannot push back the chunk a listener is actually waiting for even when the pool is effectively serial.

Worth recording as a correction rather than a quiet edit: the original number was real, it just measured a machine nobody deploys to. It is also precisely the kind of drift the queue-wait vs. generation split now exists to catch without anyone reaching for a stopwatch.

A real, hard-won bug: worker_threads crash

The first attempt used Node's built-in worker_threads, not separate processes — cheaper to spawn, no IPC overhead. It crashed the entire Node process the instant generate() ran inside a worker thread, even though loading the model there worked fine. onnxruntime-node's native binding simply isn't safe to run inside a worker_thread on this platform. Real, separate OS processes sidestep the issue entirely — each is just another independent node invocation, exactly like the main server itself, which already worked.

On the client, tts-player-provider.tsx keeps a sliding window of chunks prefetched (matching the pool's size, not just one chunk ahead) so every worker stays busy. The first chunk also gets a much smaller character cap (80 vs. the normal 140) than every chunk after it — nothing can overlap with the very first chunk's generation time, since there's no previous chunk playing yet to hide behind, so only that one pays for a faster start.

The measured result

Real inter-chunk gap after all of the above: 1-2 milliseconds, down from multi-second dead air.

Chapter 4 — The global player, and read-along

Playback moved from a per-page hook to a provider mounted once at the root layout (tts-player-provider.tsx), so it survives navigating away from the article — a persistent, Spotify-style "now playing" bar, not a control that dies the moment you leave the page.

Read-along highlighting tracks the currently-spoken word, not just the current sentence. Kokoro emits no real per-word timestamps, so this is a deliberate estimate: each word's on-screen moment is computed from its proportional share of the chunk's own character length against live playback position (audioEl.currentTime / audioEl.duration). A real bug in this estimate — the highlight jumping to the chunk's last word on every inter-word gap, due to an Array#find() fallback landing on the wrong index — was found and fixed by actually reasoning through what happens in the gap between two words, not just the estimate's average-case accuracy. See Roads Not Taken for why real per-word timing isn't available at all.

A separate, coarser indicator — a left-edge bar on whichever paragraph is currently being read — moves once per chunk rather than per word, giving a steady anchor even while the word cursor is still catching up mid-sentence.

Chapter 5 — Voice curation

Kokoro ships 28 voices; the picker originally offered 13 (every voice the model's own bundled quality grades rated C or better). In practice, six of those were American-female voices sitting in the same quality band right next to each other — technically fine individually, but it read as "the same voice, over and over," not real variety. The list was cut to 7: the single strongest, most differentiated voice per real gender/accent/character combination, with labels describing actual character ("Fenrir — deep & gravelly") instead of just accent and gender.

Chapter 6 — Time to first audio, and the limit of making it faster

Every chapter above is about the gap between chunks. The remaining problem was the gap before the first one: the wait between pressing "Read aloud" and hearing a word. That number has its own name here — TTFA, time to first audio — and it's the one a user actually experiences as "is this app fast."

The investigation started by establishing the ceiling, which turned out to settle the entire design question: Kokoro on CPU generates at roughly 1-2× realtime. An 80-character first chunk is about five seconds of speech, so producing it genuinely costs two-and-a-half to five seconds. ONNX Runtime session tuning, a different quantization, a bigger pool — none of these change that by more than about 2×. Generation cannot be made negligible on a CPU.

The reframing that made the problem solvable

If generation can't be fast enough, then the audio has to already exist before it's asked for. A cache hit costs one network round trip — on the order of 50-150ms. That is not a consolation prize: it's faster than the commercial streaming TTS APIs (Cartesia's real-world median is ~188ms, ElevenLabs Flash ~288ms), so a self-hosted model with warm audio in front of it is the lowest-latency option available, not a compromise for staying open-source.

Which means the work isn't "make the model faster." It's: make the cache hit the common case, and make the fixed overheads around it disappear.

Warming the opening on reader open

Opening an article now starts generating its beginning before anyone asks for it. Chunk one is fetched and held by the player client-side; chunks two and three are generated into the server's cache via a dedicated POST /api/tts/warm that returns 202 immediately without sending any audio back.

The split is deliberate. The player needs chunk one in hand to start instantly, but chunks two and three only need to be cache hits by the time playback reaches them — several seconds later. Fetching them up front would mean a reader who opens an article and never presses play has downloaded most of a megabyte of audio for nothing. It also means the fragile one-shot logic that adopts a warmed chunk at play time never had to learn about multiple indices.

Two extra chunks, specifically, because the pool has exactly three workers: chunk one's real fetch plus these two fill it once, so all three finish in roughly the wall-clock time of a single generation. Warming more would queue behind them and delay the only chunk whose timing anyone can perceive.

Why speculative work can't hurt

The pool gained a second, low-priority queue, drained only when the normal one is empty. Warming enqueues there. This is what makes speculation safe to be generous with — it can only ever consume capacity that would otherwise sit idle, and can never push back a chunk somebody is actually waiting on. Without the split, speculating would sometimes make the very thing it was speculating about slower.

A cache that survives the thing that kept emptying it

The generated-speech cache was in-process only: lost on every restart and every deploy, and not shared between instances. Since generation costs seconds and a hit costs milliseconds, that restart cliff was the largest remaining source of slow starts — the first person to read anything after a release paid full price again for audio the previous instance had already produced.

There are now two tiers: the existing in-memory LRU as L1, and an optional Redis as L2 behind it. L1 stays in front because a Redis round trip, while far cheaper than generating, isn't free, and one listening session asks the same process for the same chunks repeatedly.

A cache is only worth having if it's reliably faster than the thing it caches

This is the part that's easy to get wrong. A Redis that is slow, or down, or reachable-but-unresponsive must never make a request slower than simply generating would have been. Two mechanisms enforce that, and both are load-bearing rather than defensive decoration: every read races a 150ms timeout (past which it's abandoned and treated as a miss), and a circuit breaker skips Redis entirely for 30 seconds after any failure. Without the breaker, a down Redis makes every subsequent request pay the connect timeout before falling through — converting the cache into a pure latency tax at exactly the moment it's providing no value.

Redis stays genuinely optional, in the same sense as RESEND_API_KEY and SENTRY_DSN: with no REDIS_URL set, every L2 call is a no-op and behavior is byte-identical to the single-tier version.

"Optional" means degrades gracefully — not "leave it off"

Worth stating plainly, because the wording invites the wrong reading: production should run Redis. docker-compose.yml already does. "Optional" here describes the failure behavior — a down, slow, or absent Redis degrades to "no cache", never to "slow app" — not a recommendation to skip it.

Without it, L1 is lost on every restart and every deploy, and is per-process, so nothing is shared between instances or between a reader's own devices. Since generation costs seconds and a cache hit costs milliseconds, that restart cliff is the single largest remaining source of slow time-to-first-audio once warming is in place: the first person to read anything after a release pays full generation cost again for audio the previous instance had already produced.

Two chunker bugs that were quietly costing seconds

The 80-character first-chunk cap exists entirely to bound TTFA. It turned out chunk one routinely ignored it, in two separate ways:

  • The hard-wrap loop measured against the 320-character hard-wrap threshold rather than the current cap, so a long opening sentence produced a ~320-character chunk one — four times the intended budget.
  • The accumulator only ever flushed before appending a sentence and never split one, so any single opening sentence between 80 and 320 characters became an unsplit chunk one.

Both are now governed by the real cap. Splitting an opening sentence costs one clause-boundary seam (the wrap logic prefers commas and semicolons, so it reads as an ordinary breath) — a deliberate trade made for chunk one only. Every later sentence still keeps the whole-sentence prosody guarantee that HARD_WRAP_MAX_CHARS exists to protect.

Chapter 7 — The client-side audio cache, and a bug that looked impossible

Chapter 6 made a repeat request fast: the server caches generated audio in-process and, optionally, in Redis. But it is still a request. Every replay of an article and every page reload re-downloaded every chunk — paying CORS preflight, transfer time and server work again for bytes that had not changed and could not change. Chapter 7 (#150) makes the second play cost nothing at all: no network, no server, no pool worker.

The mechanism is a third cache tier in front of the two server-side ones — generated WAV chunks stored in IndexedDB, keyed by exactly what determines the audio: the text, the voice, and the speed.

The first attempt was written, debugged, and reverted — it never produced a single hit

Key derivation, transaction commit, and the circuit-breaker flag were each eliminated as the cause. The hypothesis that survived is what this version changes: it stored the fetch Blob directly.

A Blob is a handle, not bytes. Structured-cloning one into IndexedDB (see IndexedDB) stores a reference to a backing store the browser owns — and a Blob whose backing store came from somewhere unusual, such as a streamed cross-origin response, can clone in and read back as something that is no longer the audio. Reading arrayBuffer() before the put removes that entire class of problem for the cost of one ~96KB copy per chunk; the Blob is reconstructed on read, where only the MIME type needs preserving.

The reason this was hard is that every layer reported success. The write resolved, the transaction committed, the read returned an object. Nothing in the failure said "the bytes you got back are not the bytes you stored" — which is exactly the kind of bug that costs a rewrite to find and one sentence to explain afterwards.

Four other decisions in that file are each a real defect avoided:

DecisionThe failure it prevents
Transactions await oncomplete, not the request's onsuccess A request can succeed and its transaction still roll back afterwards. Awaiting only the request lets a write report success and then quietly not exist.
Keys are FNV-1a hashes, with the full voice/speed/text tuple stored alongside crypto.subtle is secure-context-only, so a proper cryptographic hash isn't always available — plain HTTP on a LAN address is a real way people open this on a phone. FNV-1a is a fast non-cryptographic hash, which means collisions are possible; storing the tuple means a collision is detected on read instead of silently playing one article's audio for another's text.
Its own IndexedDB database (booklet-tts-audio), not the booklet one That database holds the user's irreplaceable data. This one holds regenerable bytes that want their own eviction policy and must be discardable wholesale on a format change. Mixing them makes "clear the cache" indistinguishable from "delete the library".
Eviction stamps are a monotonic counter, not Date.now() A prefetch window writes several chunks inside one millisecond, giving them identical lastUsedAt values — which leaves their order in the index undefined, so eviction drops an arbitrary tied record rather than the least-recently-used one. That is how an LRU quietly stops being an LRU. Found by the eviction test, not by hand.

The cache runs against a default budget of 48MB and evicts least-recently-used when it's exceeded. Every failure path degrades to just use the network: a blocked origin, private browsing (where Firefox throws synchronously from open() rather than firing onerror), or an unsatisfiable quota disables the cache for the session rather than ever making playback worse than it was without it.

What the 12 unit tests cover

Round-trip byte fidelity, key stability and separation, forged-collision safety, LRU eviction under a forced small budget, and graceful degradation — all over fake-indexeddb.

What they structurally cannot answer is the feature's actual acceptance criterion: that a real replay is served from IndexedDB rather than the network. That needed a browser, and it is now covered by a dedicated @live e2e spec — the design of which is worth reading, because two obvious ways to write it are both wrong.

Why that test is deliberately unstubbed, and asserts on texts rather than a count

Unstubbed, on purpose. The reverted first attempt was "verified" against a Playwright route.fulfill()ed response — and the surviving hypothesis for its failure was precisely that such a Blob may not survive a structured clone into IndexedDB the way a real network Blob does. That is to say: the harness may have been the broken part. Stubbing the replacement test would have rebuilt that exact blind spot, so it runs against real Kokoro weights, three loaded pool workers and a real database.

It asserts on which chunk texts were requested, not on a request count. A count cannot separate the two things a replay legitimately does — re-fetching audio it should have had cached (the bug) versus fetching chunks further into the article than the first play ever reached (correct behavior). A count-based version of this test failed with 4 requests that were all legitimate prefetches past the cached region, and making a bare count meaningful would mean playing an entire article to completion, costing minutes of real generation per run. Comparing texts tests the claim directly: nothing already fetched is fetched twice.

And it was checked for discrimination, not just greenness. With readCachedAudio patched to always miss, the replay re-fetches 5 already-cached chunks and the test fails. With the cache live it re-fetches 0, and replay TTFA lands under 2 seconds against real generation of several. A test that has never been observed failing is a hypothesis; this one has been observed both ways.

One scoping note that is a real finding rather than a limitation: the replay is same-session, never across a reload. Device preferences hydrate from localStorage in an effect, so a just-reloaded page is still on the system voice and routes to SpeechSynthesis — exercising none of this machinery.

Chapter 8 — Where you stopped listening

Read-aloud position lived entirely in memory, so starting an article on a phone and picking up a laptop started from the beginning. #152 persists it and offers to resume — shipped in two parts, the column and sync path first, then the player wiring and the prompt.

The schema decisions (a fraction rather than a chunk index, nullable rather than defaulted, a server timestamp, a device id) are covered in the data model; they are the interesting half. What follows is the runtime half.

Why the flush lives in the player provider, not the reader page

Playback deliberately outlives the reader route — that is the entire reason tts-player-provider is mounted in the root layout rather than the page. A flush owned by the page would therefore stop recording the moment someone navigated away while still listening, which is exactly the situation in which a cross-device position matters most. Otherwise it uses the same triggers as the reader's own progress flush: a 10-second interval, visibilitychange (which, on mobile, is what closing the app looks like), and unmount.

Position accumulates into refs on every timeupdate and only leaves the tab on those triggers — satisfying the requirement of no per-timeupdate network traffic. Refs rather than state because nothing renders from the value; as state it would re-render the whole app shell several times a second for no visible change (see React on that distinction). The value interpolates within the current chunk rather than using the bare chunk index: chunks are 80–140 characters, so a boundary-only position would discard up to a whole chunk on every resume.

Resuming rounds down, on purpose

A chunk's audio is one generated utterance and cannot be meaningfully seeked into, so a resume has to land on a chunk boundary one way or the other. Rounding down to the chunk containing the position means re-hearing part of a sentence; rounding up means skipping one. Re-hearing is a much better failure.

Three places in the player had quietly assumed playback starts at chunk 0, and each had to learn otherwise — a good illustration of how a feature's real cost is rarely in the feature's own code:

  • The prewarmed chunk 0 is bypassed on a resume. Reusing it would start from the beginning despite the user having explicitly asked not to — the optimization actively defeating the feature.
  • TTFA is marked at the first chunk actually waited for, not at chunk 0, or a resume would report a time-to-first-audio for audio nobody was waiting on.
  • The "stopped early" error copy no longer claims a resume that failed on its very first chunk had started.

The prompt is offered, never forced — the issue calls that half the feature. It renders nothing unless there is a position worth returning to (past 1%, before 98%), says "on another device" only when the stored device id actually proves it rather than guessing, and is skipped entirely for the native SpeechSynthesis voice, which speaks the whole text in one call and has no position to resume to. normalizeArticle backfills the three fields for records saved before any of this existed, so an older local article reads as null rather than undefined.

Nine unit tests cover the resume decision specifically — the part that is easy to get quietly wrong, and cheap to pin now that apps/web has a unit runner.

Resurfacing (SM-2)

SM-2 (SuperMemo 2, Wozniak 1987) is the actual algorithm, not a from-scratch approximation of one. Every review has a quality score on a 0-5 scale; this app's UI only ever collects a binary "Remembered" / "Forgot," mapped to quality 4 or 2 respectively (feedbackToQuality in packages/shared/src/resurface.ts). 

// The core update, simplified from resurface.ts:
if (quality < 3) {
  repetitions = 0;
  intervalDays = 1;                          // a miss resets the streak
} else {
  if (repetitions === 0) intervalDays = 1;
  else if (repetitions === 1) intervalDays = 6;
  else intervalDays = round(intervalDays * easinessFactor);
  repetitions += 1;
}
easinessFactor = max(1.3, easinessFactor + /* quality-based nudge */);

A recalled highlight's next-due interval grows (1 day → 6 days → previous interval × its own easiness factor, which itself nudges up or down based on how easy that specific recall felt); a missed one resets to a 1-day interval. This state (easinessFactor/intervalDays/ repetitions/nextDueAt) lives directly on the Highlight row.

Why real SM-2 instead of a simpler heuristic

An earlier version of this feature used weighted-random selection — "show me something plausible." Real SM-2 scheduling replaced it specifically because "resurface" should mean "show me what's actually due for review," a claim only a real spaced-repetition algorithm can back up.

Digests (a resurfacing batch) are generated and persisted per the user's DAILY/WEEKLY frequency preference, then reused — not re-rolled on every visit to the page, which would make "what am I reviewing today" a moving target.

Search

Real ranked full-text search, in both modes. Signed-in mode matches against a weighted, generated tsvector column with a GIN index — ts_rank orders results, so a title hit outranks a passing mention in a long body; websearch_to_tsquery makes a bare multi-word query mean AND; ts_headline returns the snippet. Local/anonymous mode builds a MiniSearch index with Porter stemming over the IndexedDB articles, which already carry full extractedText. Both return the same SearchResponse, so lib/data/search.ts remains the single swap point.

This replaced plain, case-insensitive contains matching, which had a sharper failure than "unranked": the whole query was one literal substring, so flow state attention matched nothing unless those words were adjacent. That version was chosen to keep the two modes identical, on the belief that local mode could not have an index — see Roads Not Taken for why that premise was wrong and what replaced it. The consistency principle was never relaxed; local mode was brought up to meet it.

The two rankers are comparable rather than identical — BM25-ish against weighted lexeme position, Porter against Snowball — so near-ties can order differently between modes. That is expected and documented, not a latent bug.

A real, measured query-level fix

The list/search endpoints originally fetched every matching row's full extractedHtml/extractedText from Postgres, then stripped them out of the response shape a moment later — real, wasted database I/O and serialization cost on every request, scaling with exactly what a large library has the most of. Fixed with Prisma's omit at the query level, so those columns are never fetched for a list view in the first place — not a caching fix, a query-shape fix.

Semantic search in progress

Being built now (#156), and described here as partial on purpose — the schema and the shared ranking logic exist, the routes and client wiring do not. Keyword search finds articles containing your words; semantic search aims to find articles about what you meant, by embedding text into vectors and comparing directions rather than matching lexemes. Two decisions are already committed and both were recorded at the point of decision rather than reconstructed later:

  • Several embeddings per article, not one. all-MiniLM-L6-v2 truncates at 256 word pieces, so embedding a whole article does not average it — it embeds the opening and silently discards the rest, which would make any mid-article passage permanently unfindable. Articles are therefore chunked into windows, one ArticleEmbedding row each.
  • A plain Float[] column, not pgvector. pgvector isn't available in the postgres:16 image that CI and docker-compose both run, so adopting it means changing the image in three places plus taking on an extension the app otherwise has no use for. At one person's library, similarity over a few thousand 384-float vectors is milliseconds in process. The condition to revisit is named rather than left vague: when a full scan is actually the bottleneck, which is the point at which an approximate-nearest-neighbour index earns its dependency.

The similarity, chunking and result-fusion code lives in packages/shared for exactly the reason the TTS chunker does: the server will embed with transformers.js under Node and the browser will embed with transformers.js under WASM, and if those two ranked results by separately written maths, "signed-in and local mode behave the same" would hold only until one of them was edited. One implementation, two callers.

A small thing worth copying: the defensive cosine

cosineSimilarity divides by both magnitudes even though the model is normally asked for normalized output, where cosine collapses to a plain dot product. The reasoning is about failure modes rather than performance: the assumption is invisible when it breaks — a caller forgetting normalize, a vector round-tripped through a lossy store — and it produces silently wrong ordering rather than an error, which is the worst possible kind of bug in a ranking function. Two extra multiply-accumulates per dimension over 384 floats is a cheap premium against that. A zero vector likewise returns 0 rather than NaN, so it is merely irrelevant instead of poisoning every comparison it takes part in.

.inject() in that third row is worth explaining, since it's what makes the API layer fast enough to run constantly: Fastify can construct a request object and push it straight through its own routing, hooks, validation and handler chain in process, returning the response object without ever opening a TCP socket. You get genuine end-to-end route behavior — real middleware, real serialization, real database — without the per-test cost of a server listening and a client connecting.

Why real generation instead of mocking TTS in e2e tests

A mocked TTS response can't catch the class of bug this feature has actually had — real generation timing, a real chunking edge case that exploded one article into 2,283 requests, a real WebGPU-adapter-detection failure. The e2e suite accepts a genuinely longer timeout for these tests specifically because what they're verifying only exists if the real thing runs.

A recurring pattern throughout this project's real debugging history, worth naming explicitly: when a test fails in a way that's hard to explain, the discipline has consistently been to reproduce it in isolation with a minimal script — a raw Node http client bypassing the browser's fetch() entirely, a patched Audio constructor to trace real playback events, a git-stash-isolated re-run to prove a failure predates a specific change — rather than guessing from the failure message alone.

The 19,000 Untested Lines

Until recently that four-layer table had a hole in the middle of it. packages/shared had Vitest, apps/api had Vitest, and roughly 19,000 lines of the web app's own logic had no test runner at all — covered only by Playwright, at whole-browser cost and whole-browser latency, or not at all.

The argument for closing it wasn't hygiene, it was a bill that had already been paid. Four real bugs shipped that a unit test here would have caught in under a second each:

  • Both chunk-0 sizing bugs in the TTS chunker — already the reason that chunker was moved into packages/shared.
  • The read-along section anchor resolving to the wrong element at a text-node boundary (see the e2e story below, where it masqueraded as a flaky test for a full CI cycle).
  • The highlight popover dismissing itself on a scroll event that arrived after it opened.

Every one of them surfaced as a slow, intermittent e2e failure that read like flakiness. The last two cost a full CI cycle each just to locate. That is the real argument for a fast layer: not that unit tests catch more bugs than e2e tests, but that they describe the ones they catch, immediately, instead of presenting them as a timeout somewhere else.

The runner is apps/web/vitest.config.ts — jsdom rather than node, because most of what's worth testing there is DOM logic with no meaning without a document. Playwright's own e2e/ directory is excluded explicitly rather than by naming convention, so that adding a src/**/*.spec.ts later can't quietly pull the whole browser suite into the unit run.

Proving the tests earn their place

Writing tests after fixing the bugs they describe is how suites fill up with assertions that have never once failed. So the verification here was to reintroduce both of that session's real bugs and confirm 6 failures across the two files, then restore the fixes. A test that has never been observed failing is a hypothesis, not a regression guard.

One test in particular is documentation as much as verification. dom-range.test.ts pins the offset↔DOM bridging including its deliberate asymmetry at a text-node boundary: the helper resolves to the end of the earlier node on purpose, because highlight rendering shares it and biasing it forward would change which text nodes get wrapped in <mark>. That is exactly the kind of thing a later "obvious fix" breaks silently, so it is now written down somewhere the compiler can enforce.

The first version of this runner shipped without React component rendering, and the reason is a story in itself — see One React for the Workspace. Because of it, the popover's scroll rule was initially tested through a small extracted hasScrolledAway() helper rather than a rendered component: less coverage than a real interaction test, and documented as such rather than glossed over. Rendering works now, and the first rendered component test deliberately targets RenameDialog — a component with enough hooks to actually exercise the thing that was broken.

The e2e suite was switched off, and why it is back on

The web e2e job spent a period disabled in CI (if: false) for being too slow. The usual suspect was wrong: the two TTS specs that generate real audio were not the cost. 31 of 47 specs were each fetching a real Wikipedia URL and running a full extraction as setup, serialized behind Playwright's single worker.

Almost none of those specs were testing extraction. They needed an article to exist so they could test collections, trash, highlights, or tags. So the suite now runs against a local fixture HTTP server (apps/web/e2e/fixture-server/server.mjs), started by Playwright's own webServer config. One spec — save-real-url.spec.ts, tagged @live — still fetches a genuine public URL so real-world extraction stays covered.

Beyond speed, this bought determinism: a real Wikipedia page can be edited out from under a test that asserts on its text. The fixtures are generated from parameters rather than stored as eight near-identical HTML files, because the interesting variation between them is structural — how long, how many paragraphs, what shape the opening sentence is.

Fixture HTML is not arbitrary — Readability rewrites it

Two details in that generator exist because of specific failures, and both look like noise until they bite:

Paragraphs are joined with a blank line, not a newline. Extraction derives its plain text from the DOM's own whitespace, and the paragraph-citation feature counts \n{2,} boundaries to say which paragraph a highlight is in — so tightly-packed source HTML makes every citation read "Paragraph 1".

And the fixtures have no byline element at all. Several specs highlight "the first paragraph" via [data-article-content] p:first, and Readability normalizes even a <div> byline into a <p> in its cleaned output — so avoiding <p> is not enough to keep the byline from silently becoming the first paragraph. The author reaches the app through <meta name="author">, which is where extraction reads it from anyway.

Re-enabling the job took several rounds, and the failures were mostly real rather than test-harness noise: the API refused to fetch loopback addresses (its SSRF guard, correctly — relaxed for e2e by an environment variable that is ignored outright under NODE_ENV=production); the whole suite hammering one IP tripped the global rate limit; and the pool's three workers all cold-missed the model cache simultaneously and raced writing the same file, producing a truncated model and a "Protobuf parsing failed" crash rather than merely wasted bandwidth.

The last failure was a product bug, not a slow test

One spec kept failing on the read-along section bar (.reading-section-active) never appearing. The tempting fix — widen the timeout — would have buried a genuine bug.

A TTS chunk that begins exactly where a text node ends resolves to that earlier node. For a Range that is the same document position, but the section indicator reads the node's parentElement to decide which block to mark. The shape that exposes it is completely ordinary: whitespace sitting directly inside a wrapping element — an <article>, a Readability page <div> — just before its first real <p>, which is what indented source HTML produces. Chunk 0 starts at that paragraph's first character, so it resolved to the whitespace, whose parent is the wrapper. The wrapper contains every other paragraph too, so the indicator's own "is this scoped to one section?" guard correctly refused it — and nothing highlighted at all until playback reached a chunk starting mid-paragraph, one full chunk of real audio later.

The fix is scoped to the section indicator alone. The shared offset-to-DOM-point helper was deliberately left unchanged: highlight rendering uses it too, and there the end point decides which text nodes get wrapped in <mark>, so biasing it forward would have quietly changed what gets highlighted.

Result: the suite runs green in about 8.7 minutes, with no dependency on Wikipedia being up or unedited.

Part VIICI/CD & Deployment

What CI Actually Does Here

Continuous Integration, stripped of the ceremony, is one idea: every push runs the same checks, on a clean machine nobody has configured by hand, before anyone is asked to trust the change. The "clean machine" half is what makes it worth paying for — it is the only environment in which "works on my machine" is not a possible explanation.

Booklet's pipeline exists twice, in two dialects, and both are real and current: .github/workflows/ci.yml for GitHub Actions and .gitlab-ci.yml for GitLab CI/CD. Six jobs, in three stages:

JobWhat it does, and why it's separate
typecheck-and-lint Four tsc --noEmit passes (api, web, extension, mobile) plus lint — and, deliberately, the API's production esbuild bundle. The bundle is here rather than only in docker-build because tsc never asks who declared a package, so a transitive import typechecks cleanly and then fails in esbuild. Moving the cheapest half of that signal here reports it about two minutes earlier. See Bundling.
test-unit packages/shared and apps/web's Vitest suites together in one job — neither needs a database, a browser, or built artifacts, and the whole thing is a couple of seconds. A dedicated job per suite would spend longer on checkout and install than on the tests.
test-api The API integration suite against a real Postgres service container — a second container the CI system starts alongside the job and connects to the same network. Real Postgres rather than the PGlite dev database, so the normal Prisma migration engine applies.
test-web-e2e Playwright against the real stack: API, web app, Postgres, and the local article fixture server, all running at once.
test-extension-e2e The browser extension's suite under xvfb — a virtual X display. A real extension needs a real background service worker, which (confirmed empirically) does not register under Chromium's headless mode, so the browser has to run headed against a display that doesn't physically exist. Also runs Mozilla's own manifest validator, which catches Firefox-specific manifest.json regressions nothing else here would, since the e2e suite itself only drives Chromium.

Why a build-and-run job earns its keep

Every other job runs under tsx or Vitest, where module resolution is generous. The production path — tsc/esbuild to a bundle, then plain node dist/index.js — is a genuinely different execution environment and has broken silently before while every other check stayed green. That is the specific class of failure this job exists to catch, and it has caught it.

The Day the Allowance Ran Out

Mid-branch, CI started failing with runner_id: 0 — an error that describes nothing. The cause was billing: the GitHub Actions allowance was exhausted, and the repository was left with no automated checks at all.

Two responses followed, and they're independent. The first was to cut what the pipeline burns, because at roughly 22 minutes of billable runner time per full run, the spending pattern turned out to be mostly waste:

  • Cancel superseded runs. Pushing five times in an afternoon meant five concurrent full runs, four of them already obsolete and none of which anyone would read. This is by far the biggest lever — everything else on this list is rounding error next to it. The final push on a branch still gets a complete run; only the already-pointless ones are dropped.
  • Skip prose-only changes. A commit touching only markdown or docs/ cost a full run and contained no code to typecheck, bundle, or drive a browser against.
  • Stop running the TTS benchmark on pull requests. It is a measurement, not a gate: it has no pass/fail criteria, so it cannot fail a PR and nobody reads it per-push. It still runs on the default branch, where the trend line is the point, and can be asked for by hand on any branch — which is how the numbers in the pool-parallelism entry were taken anyway.
The docs-skip has a caveat, recorded in the workflow itself

Skipping the workflow means a docs-only PR reports no checks at all. That's harmless today. If required status checks are ever enabled on this repository, it becomes a PR that can never merge — and the fix at that point is a no-op job that reports success, not a skipped workflow. The note lives in the YAML rather than in someone's memory.

A bug found only because CI was gone

Verifying by hand in CI's absence, /api/health reported loaded: 1 for a model that had definitively failed to load — the exact lie the readiness reporting had been added to stop telling.

The worker awaited warmTtsModel(), which catches its own errors and resolves either way, so it could never report ok: false. It awaits loadTtsModel() now, which propagates. warmTtsModel keeps its swallowing behavior for server startup, where not taking the whole API down over a TTS model is the right call — and the comment on each now says which is which and why. Confirmed against a running API with the weights CDN unreachable: health reports status: ok with workers: 2, loaded: 0, and the pool logs both failed loads.

Three tests pin it, two of which fail against the old version — including one asserting which function is awaited, since the two are indistinguishable by return type. That is an unusual test to write and the right one here: the defect was never in the values, only in which of two identically-shaped functions was called.

Porting the Pipeline to GitLab

The second response was to port the whole thing to GitLab CI/CD, which is where the pipeline runs now. Every job is a deliberate translation of its Actions counterpart rather than a fresh design, so the two can be compared side by side while both exist, with every non-cosmetic difference commented at the point it occurs.

Four translation hazards account for most of the work, and each one silently produces a broken-but-green or mysteriously-red pipeline if missed. They generalize well beyond this repo:

HazardGitHub ActionsGitLab CI
Service hostnames Maps a service container's ports onto localhost. Does not. A service is reachable at its own hostname on a shared network — so every DATABASE_URL says postgres:5432, not localhost:5432.
Service readiness --health-cmd pg_isready waits until Postgres will actually answer. No equivalent — it only waits for the port to open, which Postgres does before it will answer queries. Without an explicit wait, the first prisma migrate deploy intermittently dies on a connection the server closes during startup.
Shell lifetime Each run: step is a fresh shell on a persistent VM. The whole script: runs in one shell. Backgrounding (… &) works more naturally, but an early cd or exported variable leaks into every later line.
Privileges sudo apt-get … is normal. The docker executor already runs as root and sudo isn't installed — every sudo simply comes out.

The readiness wait is a small piece of engineering worth reading: it polls with bash's /dev/tcp rather than installing pg_isready (so it costs no apt), then confirms real readiness by letting the migration itself retry five times. Checking that the port is open is necessary and not sufficient; the only proof Postgres will answer a query is a query.

Several smaller decisions in that file are each a paid-for lesson:

  • pnpm's store is relocated into the project directory. GitLab only caches paths inside the build directory, and pnpm's default store lives in $HOME, which is outside it — so the cache silently does nothing until you move it.
  • Corepack's download prompt is disabled. Corepack asks before downloading a pnpm it doesn't already have, and on a non-interactive runner that is an indefinite hang rather than a failure.
  • Playwright's own image, not node + playwright install --with-deps. The browser and its ~100 system packages are already baked in, saving a couple of minutes of apt per run in each of two jobs. The image tag has to track @playwright/test in package.json; the install call is kept on top because it's a cheap no-op when they agree and a correct repair when a lockfile bump makes them disagree — a drifted tag then costs seconds instead of failing outright.
  • The TTS model is pre-fetched in a single process before anything that starts the pool. Three workers cold-missing the Hugging Face cache simultaneously race to write the same file, which was observed producing a truncated model and a "Protobuf parsing failed" crash — not merely wasted bandwidth.
  • docker-build uses Docker-in-Docker, and curls the API from a throwaway container on the same network rather than a published port — because with dind the docker daemon is a separate container, so -p publishes onto the daemon's network namespace, not the job's.
  • Publishing lives inside docker-build, not in a separate job. dind gives every job a brand-new daemon with an empty layer cache, so nothing built in one job survives into another — a separate publish job would rebuild both images from scratch, including baking in Kokoro's weights, twice per push. An exhausted CI allowance is what started this migration; spending it that way would be an odd way to finish.
Deliberately not ported: the docs paths-ignore

GitLab's rules:changes means "run if these paths changed", which cannot express "skip only if nothing but docs changed". The naive inversion skips the whole pipeline on any merge request that touches a doc alongside real code — which is most of them.

Silently not running CI on a real code change is a far worse failure than spending a runner on a prose-only merge request, so the optimization is left out until it can be done correctly. The asymmetry is the point: one mistake wastes money, the other ships a bug.

Gating Jobs on the Tree, Not on a Flag

The first real GitLab pipeline failed on main, and the cause was instructive: the config had been written against the branch carrying the TTS pool work and then cherry-picked to a branch that has none of it. Both failures were the same missing module.

The wider version of that same mistake was worse and quieter. On the Actions side, test-web-e2e carried a hard if: false — the suite had been switched off for being too slow to gate merges on (see the e2e story), and what made it viable again was the local fixture server. Porting the job without porting that flag quietly re-enabled a suite the branch could not run.

A job that cannot run should not exist, rather than fail

So each of these jobs is now gated with rules:exists on the file that makes it possible: the fixture server for test-web-e2e, the benchmark script for bench-tts-ttfa.

That states the same decision as a fact about the tree rather than a flag someone has to remember to flip. Branches without the work skip the job; the job switches itself on the moment that work merges, with no second edit and no window in which the config and the code disagree. The failure mode of a forgotten if: false is a permanently disabled test suite nobody notices; this construction has no such mode.

The model pre-fetch keeps a shell guard on top of the rule anyway, because exists is OR across its list and cannot express "this other exact file is also present".

The same run also proved the port on the first attempt for typecheck-and-lint, test-unit, test-api and test-extension-e2e — which between them cover every one of the four translation hazards above: the service hostname, the readiness wait standing in for --health-cmd, the Playwright image, and xvfb without sudo.

Verification when there is no CI to verify with

Worth recording as a practice, since this branch spent real time with no working pipeline: the commits made during that window carry an explicit local-verification record in place of a green check — every suite, every typecheck, lint, the production bundle, and the full e2e run, with the failures enumerated and individually accounted for (blocked outbound network to xkcd, dictionaryapi.dev, Wikipedia and Hugging Face; the PDF text layer not rendering in that sandbox at all). "104 passed, 12 failed, and here is why each of the twelve is not about this change" is a usable substitute for CI. "Tests pass locally" is not.

Deployment & Environment

Deployment (see DEPLOYMENT.md) is Docker-based — a Dockerfile per app plus a docker-compose.yml, verified by CI's own build-and-smoke-test, but not yet pointed at a real production host (no cloud account exists in this project's own development environment). That gap is stated rather than papered over: what follows is real and tested, but it has not yet met real traffic.

The API image bakes Kokoro's ONNX weights in at build time. Without that, the ~90MB model downloads from Hugging Face on the first read-aloud in every fresh container — three times over, since the pool starts three processes that all cold-miss at once — making the first request after a deploy a 10-60 second wait and putting a core feature at the mercy of a third party being reachable at request time.

Don't "fix" the model cache with an environment variable

The installed @huggingface/transformers reads no cache environment variables at all — not HF_HOME, not TRANSFORMERS_CACHE, not HF_HUB_CACHE. Verified against its own env.js, which hardcodes the path and allows overriding it only programmatically via env.cacheDir. It caches into node_modules, which the runtime stage copies wholesale — so running the prefetch during the build is sufficient on its own, and adding an ENV HF_HOME would be silently ignored.

The general rule that hides behind that last row

That is a real operational constraint, not a quirk: it means the web image is environment-specific, and pointing an existing image at a different Sentry project or Datadog application requires a rebuild rather than a restart. Worth knowing before designing a deployment pipeline around it, and worth recognizing in the failure mode it produces — everything comes up healthy and one feature is invisibly inert.

Observability

Sentry has been wired for errors since early on. What did not exist until recently was any way to measure latency — and after an entire release spent on read-aloud speed, that was the gap that mattered most. Every number in TTS Chapter 6 came from a local run or the CI benchmark, and neither of those is a user: the benchmark never pays a CORS preflight, real transfer time, or audio-element decode, and it runs on a 2-vCPU runner that resembles nobody's laptop.

Tracing is OpenTelemetry, exported over OTLP (apps/api/src/lib/telemetry.ts). Datadog is the intended backend and is a first-class OTLP consumer, so which backend receives the spans is a single environment variable rather than a code change.

Considered and rejected: Datadog's own dd-trace SDK

Marginally simpler to set up and slightly deeper on Datadog-specific features. Rejected because it makes the vendor a code dependency rather than a configuration value — moving to Grafana/Tempo or Honeycomb later would mean re-instrumenting rather than re-pointing. Since Datadog ingests OTLP natively, nothing is actually given up for that portability.

Considered and rejected: auto-instrumentation

@opentelemetry/auto-instrumentations-node would trace Fastify, HTTP, and Prisma with no call sites. It works by patching modules as they load, which under Node ESM requires a loader hook installed before any instrumented module is imported. This app is ESM and bundled by esbuild for production (scripts/build.mjs flattens the whole import graph into one file), so there is no reliable "before" for such a hook to occupy.

The deciding argument is the failure mode, not the difficulty: an auto-instrumentation that silently patches nothing is worse than none at all, because traces still appear — just missing the spans you were relying on, with nothing announcing their absence. And the spans this app actually needs are internal to the TTS pool, so no library-boundary hook could have produced them regardless.

The span that carries the real information is tts.generate_pooled. It records queue wait and generation separately rather than as one duration:

AttributeWhat a bad value means
tts.queue_wait_ms Time spent waiting for a free worker. High means the pool is undersized for the load, or speculative warming is competing with real playback — fixed by TTS_POOL_SIZE or by the priority split.
tts.generate_ms Time the model was actually running. High means generation is slow on this hardware — a different problem, in a different place, with different fixes.
tts.cache_tier l1 (in-process), l2 (Redis), or miss. "Served instantly from this process" and "served after a Redis round trip" are different answers to why a chunk was fast, and a boolean hit/miss cannot tell them apart.
Why splitting these two numbers was not optional

One end-to-end duration cannot distinguish "we waited" from "it was slow", and that exact ambiguity is what let the pool's parallelism shortfall sit unnoticed. The documented claim was that three concurrent chunks cost roughly the same wall-clock as one. Measured on a 2-vCPU runner, three cost 2.86× one — the pool queues far more than it parallelizes at that size. That was found by hand, with a stopwatch, because nothing in the system reported it. These two attributes are what stop the next such regression needing to be discovered the same way.

/api/tts also returns a Server-Timing header (cache, queue, gen) on every successful response, readable from the browser via PerformanceResourceTiming.serverTiming whether or not any tracing backend is configured.

Server-Timing is invisible cross-origin without Timing-Allow-Origin

The API is always a different origin from the web app here. On a cross-origin response a browser exposes serverTiming as an empty array unless the response also carries Timing-Allow-Origin — no error, no warning, just no data, which makes the header pure overhead. Booklet echoes the caller's own origin, gated by the same check CORS uses, rather than *: a wildcard would hand these timings to any site that fetched the route, and a bare WEB_ORIGIN would miss both local development (any localhost port) and the browser extension.

On the client, Datadog RUM (apps/web/src/lib/rum.ts) reports the TTFA sample that tts-metrics.ts was already measuring but had nowhere to send. It goes out as a tts.ttfa action tagged with prewarm_hit — warm and cold plays kept separable rather than averaged, since averaging them produces a number that describes neither, and moving readers from the cold group into the warm one was the entire point of the warming work. The SDK is imported dynamically, so a deployment without RUM configured never downloads it at all. Session replay is explicitly disabled: it would record whatever the reader is reading.

All of it is opt-in by environment variable and a complete no-op without one, matching how REDIS_URL, SENTRY_DSN, and RESEND_API_KEY already behave — verified both ways, by running the API against a local OTLP sink and confirming spans arrive with the expected attributes, then unsetting the endpoint and confirming the server is healthy and exports nothing.

A latent shutdown bug this work surfaced

Flushing buffered spans on shutdown is asynchronous, and it did not work — because tts-pool.ts's own SIGINT/SIGTERM handlers called process.exit(0) themselves. Registering a listener for those signals replaces Node's default terminate-on-signal behavior, so whichever module happened to be imported first was effectively deciding when the process died, silently cancelling any shutdown work registered after it. The entry point owns the exit now; the pool keeps its process.on("exit") handler, which still covers every other way the process ends. Worth noting because it was invisible until something else needed to run at shutdown.

Part VIIIGlossary

Monorepo
One version-controlled repository containing multiple, separately-deployable projects (here: an API, a web app, a browser extension, a mobile app, and a shared library) — as opposed to each living in its own repository ("polyrepo").
ORM (Object-Relational Mapping)
A library that lets you query a relational database using the host language's own objects/functions instead of hand-written SQL strings. This project's ORM is Prisma.
JWT (JSON Web Token)
A compact, cryptographically-signed token format for representing claims (like "this is user X, issued at time Y, expires at time Z"). Verifying one is just a signature check — no database lookup required, which is what "stateless" means here.
SSR / CSR
Server-Side Rendering (HTML generated on the server per request) vs. Client-Side Rendering (an empty shell shipped to the browser, which then builds the page via JavaScript). This app is overwhelmingly client-rendered in practice, even though it's built on a framework (Next.js) capable of both.
CFI (Canonical Fragment Identifier)
The EPUB standard's own way of pointing at a precise location inside a specific document within a book — the EPUB equivalent of a URL fragment, and what this app anchors EPUB highlights to.
Spaced repetition
A learning technique where review intervals grow over time for things you consistently recall correctly, and shrink (reset) for things you don't — the idea behind flashcard apps like Anki, and the model this app's "resurfacing" feature is built on via the real SM-2 algorithm.
WASM (WebAssembly)
A binary instruction format that runs in browsers (and standalone runtimes) at near-native speed, used here for in-browser OCR (Tesseract.js) and as the fallback execution path for TTS inference before it moved server-side.
ONNX Runtime
A cross-platform engine for running trained ML models. onnxruntime-web runs inside a WASM sandbox in the browser; onnxruntime-node runs as real native code in Node.js — the latter is measurably faster, which is the entire reason Kokoro TTS generation moved server-side.
Worker thread vs. child process
Both let Node.js run code concurrently. A worker thread shares the same OS process (cheaper, but shares certain native-binding constraints); a child process is a fully separate, independent process (more overhead, but fully isolated) — this project uses real child processes for TTS generation specifically because a native binding (onnxruntime-node) was confirmed to crash inside a worker thread.
SM-2
SuperMemo 2, a 1987 spaced-repetition scheduling algorithm by Piotr Wozniak — see Resurfacing.
TTFA (time to first audio)
The wait between pressing "Read aloud" and hearing the first word. Distinct from throughput or the gap between chunks: it's the one latency a user directly experiences as the feature being fast or slow, and the thing Chapter 6 is entirely about.
Realtime factor
How fast a speech model generates relative to the duration of the audio it produces. 1× realtime means one second of synthesis per second of speech; 2× means half that. Kokoro on CPU runs at roughly 1-2×, which is the constraint that shaped the whole caching architecture — below about 10×, generating on demand can never feel instant.
CORS preflight
An automatic OPTIONS request a browser sends before certain cross-origin requests (anything that isn't a "simple" GET/POST — including any JSON POST) to ask the server whether the real request is allowed. It costs a full extra round trip, and without an Access-Control-Max-Age the result is cached for only a few seconds, so it repeats constantly.
Circuit breaker
A pattern where repeated failures against a dependency cause it to be skipped outright for a cooling-off period, rather than every request continuing to pay a timeout to rediscover it's down. Used here so a degraded Redis can never make TTS slower than having no cache at all.
L1 / L2 cache
Tiers of a layered cache, borrowed from CPU terminology: L1 is smaller and closer (here, in the server process's own memory), L2 is larger and slightly further away (here, Redis over the network). A miss in L1 falls through to L2; a hit in L2 is promoted into L1. Since Chapter 7 there is effectively an L0 in front of both: the browser's own IndexedDB, where a hit costs no network at all.
LRU (least recently used)
An eviction policy: when a cache is over budget, discard whatever was used longest ago. Cheap and usually close to optimal — but only if "longest ago" is actually well-ordered, which is why the audio cache stamps records with a monotonic counter rather than Date.now().
Lexeme / stemming
A lexeme is a word reduced to its root form; stemming is the process that does it. running, runs and ran all stem to run, which is why a full-text search for one finds the others and a substring match never will. See How Postgres Full-Text Search Works.
tsvector / tsquery / GIN
Postgres's full-text machinery: a tsvector is a document pre-parsed into weighted, positioned lexemes; a tsquery is a boolean expression of lexemes to match against it; a GIN (Generalized Inverted) index maps lexeme → rows so that matching doesn't mean scanning the table.
Generated column
A column whose value the database computes from other columns and maintains itself on every write (GENERATED ALWAYS AS (…) STORED). Booklet's searchVector is one, which is why the search index can never drift out of sync with the article it describes — there is no application code that could forget to update it.
Span / trace / OTLP
A span is one timed, labelled operation; a trace is the tree of spans making up one end-to-end request; OTLP is the wire protocol OpenTelemetry uses to ship them to a backend. See the tracing vocabulary.
RUM (Real User Monitoring)
Telemetry gathered in real users' browsers rather than from servers or a synthetic benchmark — the only source for a number like "time to first audio on a real laptop over real wifi".
Image vs. container
An image is an immutable stack of filesystem layers plus metadata about how to run it; a container is one running instance of an image with a thin writable layer on top. Building is what produces an image; docker run is what produces a container.
Docker-in-Docker (dind)
Running a Docker daemon inside a container so a CI job can build images. Its practical consequence in this repo: the daemon is a separate container, so a published port lands in the daemon's network namespace rather than the job's — and every job gets a brand-new daemon with an empty layer cache, so nothing built in one job survives into another.
Service container
A supporting container (here, Postgres) that a CI system starts alongside a job. GitHub Actions maps its ports onto localhost; GitLab CI does not, exposing it under its own hostname instead — one of the four hazards in the GitLab port.
xvfb
"X virtual framebuffer" — an X11 display server that renders to memory instead of a screen. It lets a program that insists on a real display run on a machine that has none, which is how the extension's e2e suite drives a headed Chromium in CI (a browser extension's background service worker does not register in headless mode).
Override (dependency)
A package-manager instruction forcing one version of a dependency across the whole tree regardless of what individual packages requested. A blunt tool, correct in exactly the case where the goal is "there must be only one of these" — see One React for the Workspace.
Transitive dependency
A package you didn't declare but can reach because something you did declare depends on it. Importing one typechecks fine (tsc resolves through node_modules and never asks who declared what) and then breaks the production bundle — a real failure in this repo, and why the bundle now runs in the cheapest CI job.
Structured clone
The browser algorithm used to copy values across boundaries such as IndexedDB or postMessage. Richer than JSON (it handles Date, Map, ArrayBuffer, cycles) but with sharp edges — cloning a Blob stores a reference to browser-owned bytes, not the bytes themselves.
jsdom
A JavaScript implementation of the DOM that runs in Node. Real elements, real events, real Range objects — but no layout, so anything geometric measures as zero. It's both this project's server-side HTML parser (Readability needs a DOM) and its unit-test environment for browser logic.

Part IXRoads Not Taken

A dedicated index of real ideas that were tried, measured, and deliberately reversed or rejected — preserved here specifically so the same dead end doesn't get walked into twice.

Client-side WASM/WebGPU TTS

Zero server cost, but a hard ~12-18s-per-sentence ceiling that Worker-based pipelining, quantization, and multi-threading all failed to close. Replaced by server-side generation once the real, measured speedup (onnxruntime-node vs. onnxruntime-web) was confirmed. See the full TTS story.

worker_threads for the TTS pool

Cheaper than real child processes, and the obvious first choice — but onnxruntime-node's native binding crashes the whole Node process the instant generate() runs inside one, confirmed by hand. Real, separate OS processes sidestep the issue entirely.

Redis — rejected, then adopted

The original rejection: explored in response to a real question ("would this fix our latency issues?"). It wouldn't have — every reported slowness at the time was either real model-generation latency or an actual logic bug in a specific code path, not a caching-shaped problem. Adding it would have meant real infrastructure complexity, and a departure from this app's "nothing external required" architecture, for no concrete win. The entry closed by naming the conditions under which to revisit: horizontal scaling, or repeated TTS requests becoming common enough to cache.

What changed: the second condition arrived, from an unexpected direction. Once the time-to-first-audio work established that Kokoro on CPU simply cannot generate fast enough to matter (see Chapter 6), the cache stopped being an optimization and became the mechanism — the only way for playback to start quickly is for the audio to already exist. And the in-process cache's real weakness turned out not to be capacity but lifetime: it was wiped by every restart and every deploy, so the first reader after a release always paid full price for audio that had already been generated.

Adopted as a second tier behind the existing in-memory cache, not as a replacement, and strictly optional — with no REDIS_URL the app behaves exactly as it did before. The "nothing external required" principle is intact; what's new is that something external can now make it better.

The lesson worth keeping: the original rejection was correct and the reversal was correct. What made the reversal cheap was that the first entry wrote down its own revisit conditions instead of just saying no.

Real per-word TTS timestamps

Would be strictly better than the character-proportional estimate the read-along feature actually uses — but confirmed by reading kokoro-js's own type definitions: generate() returns only raw audio samples, and even its streaming API exposes phonemes as an untimed string, not per-word timing data. Not available from this model/library without a substantially bigger undertaking (a separate forced-alignment pass against the generated audio), which wasn't judged worth the cost against the estimate's real accuracy once its own logic bug — see Chapter 4 — was fixed.

A commercial streaming TTS API (Cartesia, ElevenLabs, Deepgram)

The obvious answer to "make read-aloud start instantly," and the one that turns out to be worse on the metric it would be bought for. Their best-case figures (~40-90ms) are marketing numbers; real-world medians land around 188ms (Cartesia Sonic) to 288ms (ElevenLabs Flash). A warm cache hit from this app's own server is 50-150ms — faster, free, and with no per-character billing or hard third-party dependency for a core feature. Rejected on measurement, not principle, which is the useful part: self-hosting isn't costing anything here.

GPU inference (CUDA execution provider)

onnxruntime-node already ships the CUDA and TensorRT providers — the repo simply never passes a device, so it always runs on CPU. Wiring it up would genuinely deliver 10-30× and make even uncached generation sub-second. Not taken because it requires deploying the API to a GPU host, which is a real recurring cost for a personal-scale reading app, and because warming plus caching gets TTFA to a network round trip without it. This is the right lever if the app ever serves enough simultaneous readers that cache misses stop being rare.

ONNX Runtime session tuning

The repo passes no session options at all, which means each of the three worker processes spins up a thread pool sized to the whole machine — roughly 3× CPU oversubscription on a small host. Genuinely real, and worth perhaps 2×. Deliberately deferred: 2× on a path that caching removes entirely isn't worth the regression risk immediately before shipping. Revisit together with the dtype question — q8 is hardcoded, and q8 is not reliably faster than fp32 for this model shape on CPU, so that deserves a real benchmark rather than an assumption.

Opus/MP3 audio instead of WAV

Would be 10-20× smaller than even the 16-bit PCM the server now sends. Rejected for now because it needs a native or WASM encoder dependency plus a container format, adds 50-150ms of server CPU on the critical path, and its benefit only materializes on slow connections and only for the first chunk (later chunks hide behind playback). The 32-bit float → 16-bit PCM change captured the free half of this win with no new dependency.

A GET TTS route with a content hash, for real HTTP caching

A GET with no custom headers is a "simple" request — it would skip the CORS preflight entirely and become genuinely HTTP-cacheable with immutable, max-age, unlike the current POST. Rejected because it puts the text of whatever the user is reading into URLs, where it lands in server access logs, any intermediate proxy's logs, and browser history. That's a bad trade for a reading app. The preflight cost was solved with maxAge instead, and a client-side IndexedDB audio cache is the better route to zero-byte replays if that's ever needed.

Update — that alternative was built. The client-side IndexedDB cache this entry named as the better route now exists (Chapter 7), delivering the zero-byte replay without putting anyone's reading material into a URL. The rejection stands and is now cheaper than it was: the thing it gave up has been recovered by other means.

Storing the fetch Blob directly in IndexedDB

The obvious implementation of the audio cache, and the one that was written first, debugged for a while, and reverted for never producing a single cache hit. A Blob is a handle to a browser-owned backing store, not bytes; structured-cloning one can store a reference that reads back as something which is no longer the audio, with every layer reporting success throughout. Reading arrayBuffer() before the write costs one ~96KB copy per chunk and removes the entire class of problem. See Chapter 7.

Date.now() as the LRU recency stamp

Small, but a good example of a correct-looking implementation of a well-known algorithm that isn't one. A prefetch window writes several audio chunks inside a single millisecond, giving them identical timestamps — which leaves their relative order in the index undefined, so eviction drops an arbitrary tied record rather than the least-recently-used one. A monotonic counter replaced it. Caught by the eviction test, which is the only reason it was caught at all.

A chunk index for the listening position

The natural representation — the player already thinks in chunks — and wrong in two independent ways. Chunk boundaries are a function of the chunker's size constants, which are latency knobs that have already moved once (200 → 140 characters); and re-extracting an article changes the text underneath any index. Either would silently resume at the wrong place, with no error and no way for a reader to tell it had happened. A fraction over the article's text survives both. See Chapter 8.

Resolver aliases to paper over three React copies

resolve.alias, resolve.dedupe and server.deps.inline were each tried to make Vitest resolve a single React. None work — the renderer resolves React through Node before Vite sees the import — but the deciding argument is that a working version would have been worse: it would make tests agree about React while the application kept shipping three copies, hiding a real defect behind a green suite. The dependency was fixed instead, with a workspace-wide override. See One React for the Workspace.

GitLab rules:changes as a docs-only pipeline skip

The direct translation of Actions' paths-ignore, and not expressible: rules:changes means "run if these paths changed", which cannot state "skip only if nothing but docs changed". The naive inversion skips CI on any merge request that touches a doc alongside real code — which is most of them. Left out entirely rather than approximated, because wasting a runner on a prose-only change is a much cheaper mistake than silently not testing a real one.

Postgres full-text search (tsvector/GIN) — rejected, then adopted

The original rejection: it would give relevance-ranked results and real stemming, but local/anonymous mode has no equivalent full-text index over IndexedDB, and giving signed-in users meaningfully better search than signed-out users contradicts this app's "everything behaves the same either way" principle. The entry closed by naming the conditions to revisit under: that principle being consciously relaxed, or plain contains matching genuinely ceasing to be adequate.

What changed: neither of those, as it turned out — the reasoning had a false premise. The objection treated "local mode cannot have an index" as fixed, when it was only unbuilt. Local mode already holds full extractedText for every article (there is no summary/full split for IndexedDB), so it had everything a real index needs all along. The principle was right and was never relaxed; what was wrong was concluding that upholding it meant holding the server back, rather than bringing local mode up.

The second condition was also arriving independently. Plain contains was worse than "unranked": a multi-word query was matched as one literal substring, so flow state attention found nothing unless those words happened to be adjacent — the failure looked like an empty library rather than a weak search.

What was built: a weighted, generated tsvector column with a GIN index server-side (ts_rank for ordering, ts_headline for snippets, websearch_to_tsquery so multi-word means AND), and a MiniSearch index with Porter stemming client-side. Both return the same SearchResponse, so lib/data/search.ts stays the single swap point.

Comparable, not identical — and deliberately so. MiniSearch scores BM25-ish while ts_rank scores by weighted lexeme position, and Porter and Snowball disagree on a handful of words, so the two modes will order near-ties differently. That is a documented consequence, not a defect to be filed later: what is held equal is everything a reader notices — stemming, multi-word AND, title hits outranking body mentions, and snippets showing why a result matched.

epub.js spread mode (side-by-side pages)

epub.js's default "auto" spread pairs two spine items side by side above its own width threshold — a real, physical-book-style feature, but this reader has no two-page visual layout at any width to begin with, and the pairing behavior at a book's very first spine item (the cover, with nothing yet to pair it with) turned out to be the actual cause of a real "cover shows up twice" bug. Forced off (spread: "none") entirely.

Part XDelivery Boundaries & Known Gaps

An honest statement of where this project actually stops — merged here from an earlier architecture document (July 2026) that this one has otherwise superseded. Being able to answer "what isn't done, and why" precisely is worth as much as describing what is.

The headline: what remains is mostly constrained by external accounts, hosting choices and target hardware, not by missing core reading behavior. The save → read → highlight → resurface loop is complete and works signed out.

The production critical path

  • Hosting for the API, the web app and a real PostgreSQL instance. The Docker images build and boot and are smoke-tested in CI (see Deployment) — they have simply never been pointed anywhere.
  • Production OAuth redirect URIs registered with Google and GitHub. Provider buttons only render once credentials are configured, so this fails closed rather than visibly broken.
  • Resend and Sentry credentials. Both integrations are wired and both treat an absent key as "feature off" rather than an error — the same opt-in pattern as REDIS_URL and the OTLP endpoint. Note the browser-side Sentry DSN is a build argument, not a runtime one.

Store publishing and mobile

  • Publishing needs Apple, Google Play, Chrome Web Store and Mozilla developer accounts. Safari support additionally depends on Apple's own tooling.
  • Mobile needs real device or simulator verification, and a navigation layer once the screen count justifies one.
  • Native PDF/EPUB page and CFI rendering on mobile needs either a WebView bridge back to the browser reader or a dedicated native renderer. Displaying extracted text is deliberately not presented as an equivalent substitute — see Mobile App.

Engineering guardrails for the next phase

Four recommendations recorded before any of this meets real users, annotated with where each one now stands:

GuardrailStatus
Define explicit backup/export and retention behavior before launch, particularly for local-only libraries. open — and the sharpest of the four. A local-only library lives in IndexedDB, which the browser may evict under storage pressure and which a user can destroy by clearing site data. Markdown and Anki export exist; a deliberate, stated retention and backup story does not.
Introduce idempotency and conflict semantics before promising robust offline multi-device mutation. partial — the listening position now has a stated rule (last-write-wins on a server timestamp, see Chapter 8), and the local→account migration batches with resume-on-retry (Crossing the seam). Neither generalizes to every mutation, and the highlights-have-no-unique-constraint finding recorded there is exactly the idempotency hole this warned about.
Instrument extraction failures, blocked SSRF attempts, digest delivery outcomes and reader-render errors with privacy-conscious operational metrics. partial — Observability covers TTS latency in real detail and Sentry catches errors, but none of these four specific signals is measured. TTS got the attention because a release was spent on its speed; these got none because nothing forced them.
Document production secret rotation, database backup/restore, and refresh-token revocation procedures alongside deployment. open — revocation works (that's what the Session table is for), but a runbook is not a feature and none exists. Rightly blocked on there being a production host to write one against.
Why this section exists at all

A technical document that only describes what works reads as marketing. The useful version tells you where the edges are, so the next person to touch it — including future-you — knows which parts are load-bearing and which are a demo that hasn't been asked a hard question yet. Everything above is a real gap, stated before anyone had to discover it.
