Technical architecture · July 2026

Booklet

A local-first read-it-later system that preserves saved material, supports reader-native annotations, and turns highlights into a durable review loop.

Expanded technical documentation for the private jguapp/Booklet repository. Scope reflects the implementation and project documentation reviewed on July 29, 2026.

Architectural thesis. Anonymous, on-device reading is the default product state. Accounts are an opt-in synchronization capability, not a prerequisite for saving, reading, highlighting, or reviewing. This reverses the conventional cloud-first dependency: the API enriches and synchronizes clients, while the local client remains usable when no identity or backend configuration exists.

1. System goals and boundaries

Booklet addresses the gap between capture and retention. It ingests web articles, PDFs, and EPUBs; renders each in an appropriate reading surface; captures selections with a position model suited to that medium; and schedules highlights for later recall. The important distinction is that Booklet does not treat a saved URL as the artifact. It extracts and retains a usable representation so reading does not depend on the original page surviving unchanged.

The product has three operating modes: a browser-only web library stored in IndexedDB, an equivalent mobile library stored in AsyncStorage, and an account-backed library persisted through the API. The web, browser extension, and mobile application use the same domain shapes and REST API when signed in. The implementation deliberately preserves comparable behavior across anonymous and account modes; for example, search is simple case-insensitive matching rather than a server-only ranked full-text feature.

2. Runtime architecture

The repository is a pnpm workspace monorepo. Shared TypeScript domain logic is imported by all applications and bundled at build time, keeping data-transfer objects, highlight resolution, and the resurfacing algorithm consistent across client and server. The Fastify API is the server boundary for authenticated persistence, extraction, identity, and integrations; it is not required for anonymous local reading.

On the web, Next.js App Router hosts the primary reading experience. The extension uses Manifest V3 and esbuild with no UI framework; it saves the active page from the toolbar or context menu. Mobile is an Expo/React Native application whose web target has end-to-end verification. Native iOS and Android builds are type-checked but require separate device or simulator validation.

3. Data model and ownership

PostgreSQL is modeled with Prisma ORM 7 using the generated ESM client and driver adapters. All user-owned records are explicitly keyed to a user, and destructive ownership relationships use cascading deletes. This provides a simple authorization rule at route boundaries: the current subject must own the record being read or changed.

An Article separates the source type (HTML, PDF, or EPUB) from extraction status. It holds extracted HTML for web rendering, plain text for search and estimates, and a storage key for an original upload or source snapshot. Progress is normalized to a fraction, allowing a common library presentation while preserving medium-specific resume information in reader behavior.

4. Local-first behavior and account migration

When unauthenticated, web data is stored in IndexedDB and mobile data in AsyncStorage. The client repository layer presents the same logical operations to UI code regardless of backing store: list, save, update progress, create a highlight, organize, search, and review. That separation prevents account state from leaking throughout reader components.

Creating an account does not strand prior reading history. The initial sign-in migration transfers locally held articles, highlights, and collections into the account-backed library. Once an account is active, the API becomes the synchronization source for the client family. The design intentionally does not claim a general-purpose offline conflict-resolution protocol; it favors a straightforward local-default then account-sync transition. Any future background/offline multi-device editing would need explicit conflict semantics, idempotency keys, and a change cursor before it should be described as full bidirectional offline sync.

Search parity is deliberate. Signed-in records live in PostgreSQL, but search is not delegated to database relevance ranking. Plain case-insensitive matching across article metadata, body text, tags, selected text, and notes retains predictable results in local-only mode, which has no server-side full-text index.

5. Ingestion, extraction, and retained content

A stateless server-side extraction endpoint accepts URLs, PDFs, and EPUBs for both anonymous and signed-in flows. URL content is processed with Mozilla Readability and jsdom. PDFs are parsed with pdfjs-dist; EPUB archives are read with jszip and jsdom. Extraction supplies normalized text for search and reading-time estimates but does not replace native rendering for uploaded books.

URL ingestion and SSRF boundary

Fetching untrusted user URLs is a server-side request forgery boundary. Booklet checks targets for private, loopback, and link-local addresses at every redirect hop, rather than validating only the initial hostname. The same protected fetch path is reused while retrieving referenced remote images. This matters because a public URL can redirect to a local address, and because embedded image URLs are additional outbound requests.

Durability of saved material

Extracted remote images are fetched through that guarded path and embedded as base64 data: URIs. The resulting saved article remains visually useful if the publisher changes its markup, removes an image, or disappears. The stored file key represents the raw snapshot for HTML or the original uploaded binary for PDF/EPUB; these source artifacts are not the normal hot-path reader payload. A storage abstraction permits filesystem storage now and a future object-store implementation without changing article semantics.

6. Reader rendering, progress, and annotation anchoring

Reader surfaces are selected by source type instead of flattening every format into extracted text. HTML uses the extracted reading view. PDF uses pdfjs-dist canvas rendering with a precisely positioned text layer for native selection. EPUB uses epub.js pagination in a real iframe. This keeps typographic and structural behavior close to the source format while exposing a consistent selection-to-highlight interaction.

Progress is saved periodically and on visibility changes, not only during navigation away from a page; a tab close or hard reload can abort an asynchronous final write. Resume state is appropriate to the reader: scroll location for HTML, page for PDF, and epub.js location index for EPUB. Every reader also supports theme changes, adjustable type size where applicable, inline dictionary lookup from a selected word, and browser-native text-to-speech controls. Native Web Speech keeps read-aloud local and free, but voice quality and availability depend on the operating system and browser.

7. Identity, OAuth, and session security

Identity methods are peers: password login and Google/GitHub OAuth may both be present, while neither is required to use the product. The API reports configured OAuth providers so client UI does not advertise a path that cannot succeed. An OAuth callback resolves an existing provider account; if there is no provider row but the provider has verified an email already held by a user, it links the account instead of creating a duplicate user.

Access tokens are short-lived JWTs, minimizing the time a bearer token is useful. Refresh tokens are opaque, rotate on use, and are stored as hashes server-side; a database read alone therefore cannot be used to impersonate a session. The persisted session row makes device listing, individual revocation, and “log out other devices” meaningful rather than cosmetic. Password-reset and email-verification tokens follow the same storage principle: only a hash is retained, with expiry and single-use state.

API rate limiting applies at the public server boundary. Sentry integrations are intentionally no-ops when no DSN is configured, matching the wider principle that optional operations infrastructure should not break a working local product.

8. Resurfacing engine and digest lifecycle

Highlights are review items, not merely annotations. Each stores SM-2 state: easiness factor, interval in days, repetition count, next-due timestamp, feedback, and archival state. A new item with no due date is eligible immediately. “Remembered” advances interval growth through the SM-2 update; “forgot” resets the learning progression; archive removes the highlight from future eligibility without deleting the original annotation record.

Digest generation is persistent. For a user’s daily or weekly cadence, the application creates and reuses a batch rather than sampling a different set every time the dashboard reloads. The digest retains membership, generation time, viewed time, and email state, which makes review stable across refreshes and email delivery attempts. When configured, sending uses Resend; otherwise the system logs the intended delivery rather than treating the missing integration as a feature failure.

The TTS end-to-end assertion is capability-aware: headless environments with no system voice skip it rather than failing an unavailable platform feature. Multi-stage Dockerfiles exist for the API and web app, with docker-compose.yml for the service composition. Local development can run a PGlite-backed process speaking the PostgreSQL wire protocol on port 5432, avoiding a separate database installation. Because Prisma’s migration engine is unreliable against that development configuration, a project-specific migrate:pglite path is used instead of normal Prisma migration commands.

10. Delivery boundaries and next technical decisions

The current work is largely constrained by external accounts, hosting choices, and target hardware rather than missing core reading behavior. The production critical path is hosting the API, web app, and PostgreSQL database; registering production OAuth redirects; then configuring Resend and Sentry credentials. Store publishing needs Apple, Google, Chrome Web Store, and Mozilla developer accounts; Safari support additionally depends on Apple tooling.

Mobile requires real device or simulator verification and a navigation layer once the screen count justifies it. Real native PDF/EPUB page and CFI rendering will require a WebView bridge to the established browser reader or a dedicated native renderer; displaying extracted text is intentionally not presented as an equivalent substitute. Exports and sharing remain product work beyond the present core loop.

Recommended engineering guardrails for the next phase

  • Define explicit backup/export and retention behavior before production launch, particularly for local-only libraries.
  • Introduce idempotency and conflict semantics before promising robust offline multi-device mutation.
  • Instrument extraction failures, blocked SSRF attempts, digest delivery outcomes, and reader-render errors with privacy-conscious operational metrics.
  • Document production secret rotation, database backup/restore, and refresh-token revocation procedures alongside deployment.
